## Architecture et décisions

**Chargement des modèles MoE et priorité de MTP.** Le moteur compile une liste explicite de sources dans `backend/src/CMakeLists.txt`. Les implémentations de décodeurs exclusivement denses ont été supprimées. Les graphes partagés appartiennent aux implémentations MoE qui les utilisent (notamment Phi-MoE, Granite, Nemotron, Ernie et Nomic) ; les blocs denses à l'intérieur d'un modèle MoE restent nécessaires. `mgs_model_create` vérifie le nombre d'experts avant de charger les poids et rejette les modèles principaux denses. Un GGUF ne contenant qu'une tête et chargé explicitement comme MTP fait exception : une tête de prédiction dense peut servir une cible MoE. Qwen35 ne conserve que son graphe MTP.

Le placement de MTP prend en compte chaque GPU sélectionné, les tailles d'allocation et l'alignement des backends, et inclut la tête de sortie (ou le plongement de jetons qui lui est lié). Il cherche d'abord un GPU capable d'accueillir toutes les têtes ; à défaut, il répartit les groupes les plus grands entre les GPU. Un groupe ne se replie sur la RAM que lorsqu'aucun GPU sélectionné ne peut l'accueillir. Les `dMtpContexts` séparés sont alloués et transférés avant les contextes du tronc ; les surcharges de tenseurs ne peuvent pas remplacer ce placement. Les poids MTP externes sont préchargés avant la cible, y compris avec `--fit off`, et transmis à l'initialisation spéculative sans charger de seconde copie. L'estimation de l'ajustement réserve leur mémoire de contexte et de calcul sans compter deux fois leurs poids déjà alloués.

**Conventions du code source et validation de la CLI.** Les identifiants du projet utilisent le CamelCase avec les préfixes de fonctions, de méthodes, de paramètres et de valeurs définis par les règles du projet. Les API C publiques, les noms GGUF, les champs de protocole, les noms tiers et les noms de callbacks et de composants imposés par les frameworks conservent leurs contrats. Le formatage C++ utilise deux espaces. La nomenclature couvre aussi les branches du préprocesseur qu'aucune compilation Linux ne compile (Windows, macOS, macros de débogage, `MGS_LLGUIDANCE`, `#if 0`) : le compilateur ne peut pas y détecter un ancien nom, si bien que tout renommage doit être vérifié à la main dans ces branches. `--chat-template-kwargs` rejette `vEnableThinking` ; utilisez `--reasoning on` ou `--reasoning off`. Les graphies d'options avec des traits de soulignement ne sont pas réécrites, et les options répétées sont rejetées, sauf `--spec-type`, explicitement répétable. `Github-Repo-Push.sh` utilise `set -euo pipefail`, `fCleanup`, son trap EXIT et un `fMain` vérifié explicitement ; toute étape de publication qui échoue arrête le script.

`frontend/` contient l'interface ; `backend/`, le moteur, le serveur et les dépendances ;
`deploy/`, les installateurs, les services et les scripts de ressources ; `build/`, le script de compilation locale
autonome et son lanceur déplaçable ; `doc/`, la documentation ; `_/`, le matériel de travail local. Les dépendances importées sont conservées.

L'interface Svelte se trouve dans `frontend/`, le moteur et le serveur C++ dans `backend/`, et l'installation dans `deploy/`. Le moteur conserve les relations relatives entre `src/`, `common/`, `include/`, `ggml/`, `vendor/` et `tools/`. Le point d'entrée CMake de `build/CMakeLists.txt` délègue au backend ; la bibliothèque de l'interface est construite à partir de `frontend/` et intégrée à l'exécutable. Les cibles CMake sont `mgs-engine` (la bibliothèque du moteur, `backend/src/`), `mgs-common-base` et `mgs-common` (`backend/common/`), `mtmd`, `server-context` et `mgs-server-impl` (`backend/tools/`), `mgs-ui` (l'interface intégrée) et la cible exécutable `mgs` ; la sortie de compilation comme l'installation utilisent `mgs`.

**Nomenclature.** Le code hérité de llama.cpp utilise les noms propres au projet : l'API C publique de `backend/include/mgs.h` et `mgs-cpp.h` utilise les préfixes `mgs_` et `MGS_`, les sources du moteur sont `backend/src/mgs*.{h,cpp}`, la fonction d'entrée du serveur est `mgs_server`, les variables d'environnement sont `MGS_*` (`MGS_ARG_*`, `MGS_API_KEY`, `MGS_CACHE`, `MGS_MOE_CACHE*`, `MGS_SERVER_*`), les options CMake sont `MGS_*`, les métriques Prometheus sont `mgs:*`, le préfixe des en-têtes du proxy CORS est `x-mgs-proxy-header-`, le stockage du navigateur utilise `MgsUi`, le cache de téléchargements est `~/.cache/mgs/` et les noyaux CPU tinyBLAS sont `GGML_TINYBLAS` dans `ggml-cpu/tinyblas/`. Les graphies `llama` restantes sont délibérées : les avis de licence de llama.cpp (`LICENSE`, `build/licenses/LICENSE-llama.cpp`) et le slogan du README ; les mentions du projet amont en tant que tel (provenance, comparaisons), sans liens vers son dépôt ; les valeurs stockées dans les fichiers GGUF (le modèle de tokeniseur SentencePiece `llama` et les prétokeniseurs `llama-bpe` et `llama4`, avec leurs identifiants `cMgsVocabPreTypeLlama3`/`LLAMA4` et `fUnicodeRegexSplitCustomLlama3`) ; les noms de modèles et de code tiers dans les commentaires (CodeLlama, Llama-3_1-Nemotron, LLaDA, le modèle Ultravox et l'implémentation de référence de YaRN `LlamaYaRNScaledRotaryEmbedding.py`) ; une référence bibliographique dans les sources de tinyBLAS ; les variables `APIR_LLAMA_CPP_*` de l'API remoting de virglrenderer qu'utilise le backend virtgpu ; et des mots espagnols comme « llamada ». Les architectures Llama de Meta (`llama`, `llama4`, `llama-embed`), leurs modèles de conversation intégrés et le projecteur de vision de Llama 4 ont été supprimés.

L'enregistrement HTTP applique le préfixe de l'API à chaque route publiée. Les gestionnaires reçoivent des chemins canoniques sans le préfixe ; le routeur ajoute `/api` lorsqu'il relaie les requêtes vers les processus enfants des modèles. Les listes d'autorisation de l'authentification publique utilisent les chemins externes complets. L'interface reste sur `/` ; `/api/config.js` publie le préfixe avant le chargement des modules de l'application. Swagger et OpenAPI se trouvent sous `/api/doc/`, y compris pendant le chargement du modèle. Le registre des routes et des méthodes fournit l'inventaire en direct ; les paramètres de complétion proviennent de `server-schema`.

Les catalogues JSON contiennent les traductions de l'interface pour 15 locales : `de-DE`, `en-GB`, `en-US`, `es-AR`, `es-ES`, `fr-FR`, `he-IL`, `hi-IN`, `it-IT`, `ja-JP`, `ko-KR`, `pt-BR`, `pt-PT`, `ru-RU` et `zh-CN`. `aLanguages` et `dCatalogs` les enregistrent dans l'ordre alphabétique des codes de locale ; `en-US` reste la langue par défaut et la langue de repli des messages. Chaque catalogue contient les noms localisés des 15 langues. `fTranslate` interpole des valeurs nommées sans modifier les données des conversations. Les nouvelles traductions utilisent des libellés de comptage dans les messages de suppression et d'importation au lieu d'interpoler des suffixes de pluriel anglais. Changer de langue enregistre ce choix dans le document de paramètres du serveur et recharge l'interface, afin que les libellés calculés à l'importation des modules changent aussi ; `/api/config.js` publie la langue enregistrée avant le chargement des modules, et `?lang=` dans l'URL la remplace. Le layout racine définit la langue et la direction du HTML (`rtl` uniquement pour l'hébreu) ; la navigation utilise un positionnement logique, la saisie du chat et le texte brut de l'utilisateur utilisent `dir="auto"`, et le texte du code et du terminal reste de gauche à droite. Les contrats des frameworks, les champs de protocole et les symboles importés conservent leurs noms d'origine ; les fonctions propres au projet suivent les préfixes de nomenclature requis.

**Langues de la documentation.** Les documents README, MANUAL et CODE existent dans les mêmes 15 locales que l'interface : `README.md` (en-US) se trouve à la racine et ses traductions sont `doc/README.<locale>.md` ; le manuel et ce guide sont `doc/MANUAL.md` et `doc/CODE.md` (en-US) ainsi que `doc/MANUAL.<locale>.md` et `doc/CODE.<locale>.md`. Chaque variante s'ouvre sur une barre de langues qui renvoie à toutes les autres dans l'ordre alphabétique des codes de locale. Les titres portent les mêmes ancres `<a id>` dans toutes les langues, de sorte que les liens entre documents (comme `MANUAL.<locale>.md#local-build`) fonctionnent dans chacune d'elles. Les blocs de code, les commandes, les chemins, les options et les identifiants sont identiques dans chaque traduction ; seule la prose change. Les variantes en hébreu sont du Markdown simple : GitHub et Gitea détectent la direction de chaque paragraphe, si bien que le texte se lit de droite à gauche tandis que les blocs de code restent de gauche à droite.

L'installation exige root, gère explicitement les échecs de commandes et ne prépare ses fichiers que sous `_/temp/`. L'interface est construite en local au lieu de télécharger une interface amont dépourvue des modifications du projet. Le déploiement crée des services d'inférence et web non privilégiés. Son instance Apache dédiée cherche à chaque démarrage un port HTTP à partir de 11080 et un port HTTPS à partir de 11443 ; l'inférence reste sur loopback:8080. Aucun HAProxy n'est configuré. La configuration du programme se trouve dans `/opt/moe-gguf-server/.mgs/config/`, le `~/.mgs/config/` du compte de service, qui en est propriétaire, avec le mode 0600 : `api.key`, `web-domain` et `apache2.conf.in` (le `ServerRoot` d'Apache), écrits par `configure-web.sh`, et `ui-settings.json`, écrit par `mgs` ; seule l'intégration au système (unités systemd ou OpenRC) reste sous `/etc`. Les conversations sont conservées dans le navigateur ; il n'y a pas de base de données d'utilisateurs côté backend.

Le serveur lui-même active HTTPS par défaut : `common_params` commence à 11443 et `server_http_context` se lie au premier port libre, puis au port HTTP à partir de 11080. Le second écouteur répond 308 vers le port HTTPS sélectionné, en conservant l'hôte, le chemin et la chaîne de requête, avec `Cache-Control: no-store`. `--port` fixe le port principal (0 en délègue le choix au système d'exploitation) ; `--http-port` modifie le point de départ de la recherche HTTP. Seuls les conflits d'adresse déjà utilisée font avancer la recherche ; les autres erreurs arrêtent le démarrage. `server-tls.cpp` charge la paire PEM fournie ou, à défaut, l'identité autosignée de `~/.mgs/certificates/` (`fPersistentServerIdentity`) : il réutilise `fullchain.pem` et `privkey.pem` tant qu'ils correspondent et que le certificat n'a pas expiré ; sinon, il génère un certificat ECDSA P-256 (365 jours, SAN pour localhost, le loopback, l'hôte configuré, le nom de la machine et les adresses de ses interfaces) et l'enregistre au moyen de fichiers temporaires et de renommages (dossier 0700, clé 0600), de sorte que chaque exécution et chaque compilation servent le même certificat et que les navigateurs conservent leur exception de confiance. Aucune commande externe n'est appelée ; si le dossier n'est pas accessible en écriture, l'exécution utilise son identité en mémoire. Sans prise en charge d'OpenSSL, HTTPS échoue explicitement. `--http` sélectionne délibérément le HTTP en clair, qu'utilisent les processus enfants du routeur et le backend d'Apache sur 8080 ; les sockets Unix et Vertex AI conservent HTTP. Le destructeur arrête les deux écouteurs et attend leur fin. Ces décisions se trouvent dans le C++, indépendamment des installateurs et des lanceurs.

`build/build-local.sh` couvre l'utilisation manuelle sur un poste de travail : il ne nécessite pas root, n'installe ni paquets ni services et ne laisse rien en cours d'exécution. Il copie une arborescence de sources locale complète ou télécharge l'archive `main` de GitHub sans Git lorsqu'il est appelé via `curl | bash` ou comme script autonome, compile la cible `mgs` dans `/tmp/moe-gguf-server-build.XXXXXXXX/` et installe une copie déplaçable et autonome sous un préfixe (par défaut `~/.local`, uniquement pour l'utilisateur courant ; `--prefix` le modifie) : `bin/mgs`, `lib/mgs/` et `share/doc/mgs/licenses/`. `lib/mgs/` contient le binaire du serveur, la fermeture transitive de ses dépendances selon `ldd`, le chargeur dynamique de glibc et les modules NSS que glibc ouvre avec `dlopen`. Le noyau n'accepte qu'un `PT_INTERP` absolu ; `bin/mgs` est donc un lanceur statique (`build/mgs-launcher.c`) qui lit `/proc/self/exe`, remonte de `bin/` jusqu'au préfixe et exécute `lib/mgs/<loader> lib/mgs/mgs` avec les arguments restants ; rien dans le préfixe ne dépend de son emplacement absolu. Le binaire du serveur et les bibliothèques incluses portent `DT_RPATH` `$ORIGIN`, choisi délibérément parce qu'il a priorité sur `LD_LIBRARY_PATH`. Comme l'image du processus du serveur est alors le chargeur, le lanceur exporte `MGS_EXECUTABLE` et `fGetServerExecPath` le renvoie, si bien que les processus enfants du routeur repassent par le lanceur. Les bibliothèques du pilote NVIDIA (`libcuda`, `libnvidia-*`) ne sont jamais incluses, car elles doivent correspondre au module du noyau. Un fichier marqueur dans `lib/mgs/` empêche de remplacer une installation que le script n'a pas créée.

Chaque exécution locale utilise un nouveau répertoire privé créé par `mktemp -d /tmp/moe-gguf-server-build.XXXXXXXX`. L'archive téléchargée, la liste de ses membres, les sources copiées ou extraites, la sortie de CMake, les caches npm/Node/CUDA, les fichiers de travail, le journal et le `bundle/` assemblé y restent. La mise en cache automatique du compilateur est désactivée (`GGML_CCACHE=OFF`, `CCACHE_DISABLE=1`), de sorte qu'aucun serveur de cache ne survit à la compilation. Une fois les artefacts prêts, le script verrouille le répertoire du préfixe lui-même avec `flock`, copie les fichiers terminés vers des entrées temporaires situées à côté de leur emplacement définitif, puis les renomme à leur place sur le même système de fichiers. `fCleanup` attend le processus qui écrit le journal et supprime l'espace de travail privé en cas de succès, d'échec et de signaux INT/TERM/HUP gérés. Aucun fichier de compilation n'est écrit dans l'arborescence des sources ni dans `/opt/` ; le script de compilation locale n'a pas d'option `--build-dir`.

Le chemin du script d'entrée est capturé avec `${BASH_SOURCE[0]:-}` avant l'appel de `fMain`, de sorte que l'exécution depuis stdin fonctionne aussi avec `set -u`. Les options sont analysées avant la recherche des sources ; `--help` ne nécessite ni arborescence de sources ni téléchargement des sources. `fHasProjectSources` vérifie les points d'entrée de la compilation, le lanceur, les manifestes du frontend et le répertoire des licences. Une copie locale complète est préparée avec les exclusions existantes. Sinon, `fDownloadSources` exige que curl et gzip soient déjà présents, télécharge en HTTPS avec de nouvelles tentatives, valide les chemins de l'archive et l'extrait dans le répertoire privé `source/` avant de vérifier les fichiers requis. `fMain` s'exécute avec stdin redirigé depuis `/dev/null`, afin que les outils de compilation ne puissent pas consommer le script transmis par le tube. Les options distantes utilisent `bash -s --` ; aucun paquet n'est jamais installé.


Le point d'entrée Debian est autonome : il détecte une copie locale complète ou télécharge `main` depuis GitHub. Le mode distant utilise `/opt/moe-gguf-server-source` (modifiable avec `MGS_INSTALL_SOURCE_DIR`), vérifie le marqueur d'origine des sources et conserve un verrou pendant la synchronisation et la compilation. `rsync --checksum --no-times --delete` supprime les sources obsolètes, préserve `_/` et attribue de nouveaux horodatages aux fichiers modifiés. Le script auxiliaire s'exécute dans un Bash séparé, avec stdin fermé et sans dupliquer le flux de journal de son parent.

Aucune couche de rétrocompatibilité n'est conservée. Les alias obsolètes de la CLI et les marqueurs des options supprimées, les noms d'options longs en double (chaque option garde un nom court et un nom long), les replis d'environnement `MGS_ARG_NO_*` et les variables d'environnement nommées d'après d'anciennes options, les alias de routes HTTP hérités (`/completion`, `/embedding`, `/reranking`) et les champs de requête en double (`thinking_budget_tokens`, `content` dans les routes d'embedding), le format de raisonnement `deepseek-legacy`, le moteur de modèles non Jinja (`--jinja`/`--no-jinja`, les modèles C++ intégrés de `mgs-chat.cpp` et `mgs_chat_apply_template` : tout modèle de conversation passe par Jinja, et `chatml` désigne la source ChatML intégrée), les anciens noms de variables CMake, les migrations des données du navigateur et les cales de compatibilité des installateurs ont été supprimés, de sorte que chaque option, route, variable et valeur stockée n'a qu'un seul nom, l'actuel. Comme le projet n'a jamais été déployé, les API C publiques mgs/GGML/mtmd ne conservent pas non plus de symboles obsolètes : seules leurs fonctions actuelles restent (celles qui ont été supprimées sont listées dans [MANUAL.fr-FR.md](MANUAL.fr-FR.md#removed-compatibility)). Les exceptions sont délibérées : le chargement de fichiers GGUF au moyen des replis dont dépendent encore les conversions actuelles ou les GGUF publiés les plus téléchargés des familles prises en charge, vérifiés d'après leurs en-têtes sur Hugging Face (la disposition récurrente de Qwen3.6 déduite de `full_attention_interval` et la disposition intégrée de l'indexeur de GLM-5.2 pour les fichiers GLM-5.2/5.3 sans `attention.indexer.types`), les garde-fous liés aux versions de la chaîne de compilation et du système d'exploitation, et l'interopérabilité avec les protocoles externes (OpenAI, Anthropic, TEI/Jina, GCP Vertex, MCP) et avec des pairs externes tels que les invités virglrenderer de ggml-virtgpu. Les cales de compatibilité pour les anciens fichiers ont été supprimées : Grok-1, MiniCPM, le chemin `attn_kv_b` non scindé (non MLA) de Kimi-Linear, le chemin `ssm_in` de Qwen3-Next, l'absence des clés `expert_gating_func`, `rope.scaling.finetuned` et `full_attention_interval`, la période SWA scalaire de Cohere2-MoE, l'absence de prétokeniseurs et de fusions Kimi-K2, les noms de prétokeniseurs `llama3`, `llama-v3`, `jina-es`, `jina-de` et `llada-moe`, `rope.scale_linear`, les premiers Gemma 2, les versions 1 et 2 de GGUF, les anciennes clés `tokenizer.ggml.prefix/suffix/middle_token_id` et, dans `mtmd`, les projecteurs des anciens scripts ponctuels (`mlp`, `mlp_norm`, `ldp`, `ldpv2`, `resampler`, `adapter`, fichiers sans type de projecteur), le FFN permuté des anciennes conversions par chirurgie et les valeurs par défaut des clés manquantes de Kimi-K2.5 et Step3-VL. Des architectures entières ont également été supprimées par décision de l'utilisateur : Gemma 4 et toutes les architectures DeepSeek antérieures à V4.1 (voir les familles prises en charge ci-dessous).

Pour configurer manuellement, exécutez `cmake -S build -B _/temp/cmake` depuis la racine du projet. Les scripts de compilation préparent `build/` à côté des sources et sélectionnent `source/build` comme répertoire source de CMake. Les scripts de déploiement conservent les fichiers générés sous `_/temp/` et réinitialisent `CMakeCache.txt` et `CMakeFiles/` si une configuration en cache pointe vers un autre répertoire source. La compilation locale utilise toujours un nouvel espace de travail jetable sous `/tmp/`. La bibliothèque TLS de cpp-httplib est choisie dans `backend/vendor/cpp-httplib/CMakeLists.txt` à partir des options déclarées dans `backend/CMakeLists.txt` : `MGS_BUILD_BORINGSSL` et `MGS_BUILD_LIBRESSL` (toutes deux désactivées) téléchargent et compilent la bibliothèque correspondante et, dans cet ordre, ont priorité sur `MGS_OPENSSL` (activée, l'OpenSSL du système) ; sans aucune d'elles, le serveur n'a pas de HTTPS.

**Version.** La version du projet est définie en un seul endroit, `MGS_VERSION` dans `backend/cmake/build-info.cmake` (à partir de `0.1.0`), et chaque modification du projet augmente son numéro de correctif (0.1.1, 0.1.2, etc.). La compilation locale et l'installateur Debian configurent la même arborescence CMake, si bien que tous deux produisent la même version : CMake affiche `mgs version: …`, `build-info.cpp` la renvoie depuis `mgs_version()`, et elle définit aussi les versions de fichier des bibliothèques partagées (le soname reste `.so.0`), de `mgs.pc`, de `mgs-config.cmake` et du `build.json` de l'interface. Le projet n'utilise pas Git, il n'y a donc ni numéro de compilation ni commit : `--version`, la propriété `build_info` de `/api/props`, le `system_fingerprint` d'OpenAI, le `serverInfo.version` du MCP de shell et le `User-Agent` des téléchargements (`mgs/0.1.0`) indiquent tous cette version. `deploy/scripts/ui-assets.cmake` reconstruit l'interface lorsque `build.json` contient une autre version, de sorte qu'un changement de version atteint une arborescence de compilation `_/temp/` réutilisée sans toucher aux sources de l'interface.

La configuration du formatage est propre à chaque dossier : `.clang-format` est présent dans `backend/`, `frontend/` et `build/` ; `.editorconfig` est présent dans ces dossiers ainsi que dans `deploy/` et `tests/`. Les avis de licence de `build/licenses/` héritent de `build/.editorconfig`. Gardez des réglages équivalents synchronisés. Les fichiers de la racine du projet et de `doc/` exigent des réglages d'éditeur pour l'UTF-8, les fins de ligne LF et une indentation de deux espaces.

Le dossier `doc/` contient la documentation de lecture. La page Swagger se trouve dans `frontend/api.html` et CMake l'intègre au serveur. Le backend génère `/api/doc/openapi.json` à partir des routes enregistrées, à chaque requête ; il n'existe pas de fichier source `openapi.json` statique.

Le fork conserve le serveur, la prise en charge multimodale et les backends GGML de llama.cpp, avec
des optimisations MoE pour les poids répartis entre la mémoire du GPU et la RAM du système. L'enregistrement
de la mémoire de l'hôte et le préchargement des experts proviennent
des branches `fable5/host-register` et `fable5/prefetch-experts` du
fork de thecodacus.
Les emplacements de préchargement contiennent les tenseurs d'experts gate/up/down et superposent leurs transferts
au calcul. Le MTP automatique vérifie `nextn_predict_layers`, le tronc du modèle
et toutes les têtes intégrées avant de sélectionner `draft-mtp` ; les vérifications portent sur chaque
fragment GGUF. Consultez le [manuel](MANUAL.fr-FR.md#performance) pour le réglage et les limitations.

**Cache MoE des experts.** `backend/src/mgs-expert-cache.{h,cpp}` conserve les experts les plus récemment utilisés de
chaque couche dont les experts restent en mémoire système dans un pool de périphérique par GPU, partagé par les couches qui lui sont attribuées (une liste LRU par
groupe de couches d'un même GPU dont les types et les formes des tenseurs par expert sont identiques). Un emplacement contient tous les tenseurs par expert d'un
expert : poids, biais et échelles par expert, avec des projections gate/up séparées ou fusionnées. Pour les micro-lots
inférieurs à la limite de déport des opérations (32 jetons, `GGML_OP_OFFLOAD_MIN_BATCH`), `mBuildMoeFfn` construit la chaîne des experts
deux fois : une branche de périphérique qui lit le pool au moyen d'identifiants d'emplacements et une branche CPU qui lit les poids
de l'hôte. Une opération de partition sur le CPU (`mPartition`) s'exécute d'abord : elle compte les succès, transfère une
part des défauts équilibrée selon la bande passante (environ m·B_upload/(B_upload+B_cpu), au moins un) et met en file d'attente les identifiants d'emplacements et les
transferts sur le flux du périphérique avant la branche de périphérique ; la branche CPU calcule ensuite les défauts restants en
même temps. Les experts traités par l'autre branche reçoivent l'identifiant -1 sur le CPU (les noyaux CPU `mul_mat_id`/`add_id`
les ignorent et écrivent des zéros) et un emplacement vide sur le périphérique (la position k utilise l'emplacement vide k, de sorte qu'aucun emplacement
ne se répète au sein d'un jeton, comme l'exige l'assistant MMQ de CUDA), si bien que la somme des deux branches est égale à l'exécution
normale, aux arrondis près. L'ordonnanceur ne synchronise un segment du graphe sans entrées avec le segment précédent que lorsque ce
segment avait copié des entrées ou que son backend peut accéder au type de tampon actuel ; cela conserve la correction amont #26040
et permet aux deux branches de se chevaucher. La bande passante de transfert est mesurée à la création avec de vrais experts et la
bande passante du CPU est estimée en continu à partir de la durée de la branche CPU. Les grands micro-lots conservent le préchargement des experts :
`ggml_backend_sched_set_weight_upload` permet au cache de copier ses experts de périphérique à périphérique dans l'emplacement de préchargement
et de ne transférer que les autres depuis la mémoire de l'hôte. Le cache prend la mémoire du périphérique qui reste après le contexte, moins
`--moe-cache-reserve` et les emplacements de préchargement. Il est créé par la première requête une fois chaque contexte et chaque
projecteur chargés (le préchauffage commun le diffère), peut être redimensionné à l'exécution (`mgs_set_expert_cache_size`,
`POST /api/expert-cache`) et rapporte ses compteurs via `mgs_get_expert_cache_info`, `/api/expert-cache`
et `/api/metrics`. Les réglages transitent par les variables d'environnement `MGS_MOE_CACHE*`, définies par les
options `--moe-cache*`, ce qui laisse l'API publique inchangée. Avec le cache activé et suffisamment de
RAM, `--fit` garde tous les experts en mémoire système et laisse la mémoire libre du périphérique au cache, car un cache LRU
sert mieux le décodage que des couches d'experts statiques entières ; avec plusieurs GPU, il répartit les couches exclusivement denses
entre eux selon un objectif de mémoire, de sorte que chaque GPU met en cache les experts de ses propres couches. La bande passante de transfert est mesurée
par GPU, une taille demandée est répartie entre les GPU en fonction des experts de l'hôte qu'ils mettent en cache, et le cache reste désactivé avec le
parallélisme de pipeline, qui maintient plusieurs micro-lots en cours de traitement. `--fit` compte aussi les couches nextn (MTP), que
le chargeur range parmi les couches qu'il décharge sur le GPU ; sinon, la première couche restait sur le CPU lorsque MTP était désactivé.

**Taille du contexte avec `--fit`.** L'étape 2 de `fCommonParamsFitImpl` réduit un contexte que l'utilisateur n'a pas défini comme
si tous les poids devaient tenir dans la mémoire du périphérique, si bien qu'un modèle plus grand que les périphériques retombait toujours à `--fit-ctx`
(4096 jetons), alors même que ses experts restent ensuite en mémoire système, et les réponses de raisonnement étaient tronquées. Une fois que les poids denses tiennent, `fRaiseContext` mesure le placement où seuls les poids denses sont sur le périphérique,
avec le contexte réduit et avec le contexte d'entraînement, interpole linéairement et augmente le contexte (arrondi par défaut à un multiple de 256 et
vérifié par une mesure supplémentaire) jusqu'à ce que le cache KV et les tampons qui croissent avec lui occupent au plus un quart
(`cContextShare`) de la mémoire du périphérique restant après les poids denses. Cette étape s'exécute après le choix du placement où tous les
experts sont en RAM (cache des experts) et avant que des couches d'experts entières ne remplissent les périphériques, de sorte que les experts
conservent toujours au moins les trois quarts de cette mémoire. Un `--ctx-size` explicite n'est jamais modifié, `--fit-ctx` reste le
minimum, et rien ne change lorsque le cache KV réside en mémoire système. Le contexte du modèle brouillon prend la taille de contexte de
la cible (`vParamsDft.n_ctx = n_ctx` dans `mLoadModel`) : avec une taille de contexte de 0, il allouait auparavant son cache KV
pour le contexte d'entraînement du modèle, ce qui prenait de la mémoire du périphérique au cache des experts.

**Configuration automatique.** `mgs --model FILE` doit choisir seul les réglages les plus rapides pour la machine ;
les options explicites prévalent toujours. Avec les experts en mémoire système, chaque micro-lot d'une invite fait transiter par PCIe les experts
qui ne sont pas sur le périphérique (environ 2 s par micro-lot pour Qwen3.6-35B-A3B Q8_0 sur une RTX 4060 Ti), si bien que
la vitesse de traitement de l'invite croît de façon presque linéaire avec le micro-lot, tandis que la génération n'en dépend pas : une invite de 2514 jetons
est passée de 215 jetons/s avec 512 à 408 avec 2048 et à 737–755 avec 4096, avec la même vitesse de génération. Avant que le
contexte ne soit augmenté, `fRaiseBatch` essaie des micro-lots de 4096, 2048 et 1024 jetons avec le placement choisi et conserve
le plus grand dont la mémoire supplémentaire ne dépasse pas un huitième (`cBatchShare`) de la mémoire du périphérique restant après les poids
denses ; le lot logique croît avec lui. Elle ne s'exécute que lorsque `-b`/`-ub` (ou leurs variables) n'ont pas été fournis
(`common_params::vBatchExplicit`, transmis comme `pAutoBatch`). `common_init_result` recopie le `n_batch` obtenu
dans les paramètres, car les contextes du modèle brouillon et de MTP les copient et reçoivent chaque lot de la cible dans un tampon de
leur propre `n_batch` ; leur micro-lot conserve sa valeur par défaut. Le nombre de threads CPU par défaut (`fCommonDefaultThreads`,
appliqué par `fPostprocessCpuParams` en l'absence de `-t`) est le nombre de cœurs utiles au calcul, plafonné à la moitié des
CPU logiques du masque d'affinité du processus : la part CPU de l'inférence MoE est limitée par la bande passante mémoire, et
utiliser tous les CPU logiques d'une machine virtuelle sans SMT visible mettait les threads de calcul en concurrence avec le thread qui
pilote le GPU (16 vCPU : de 4 à 12 threads, des résultats équivalents aux variations de mesure près ; 16 threads, 13 % plus lent). Avec un SMT visible, le
plafond est égal au nombre de cœurs physiques, de sorte que les machines physiques conservent l'ancienne valeur par défaut. `common_init_result` journalise le
nombre de threads ; `--fit` journalise le micro-lot et le contexte qu'il a choisis.

**Placement de MTP.** Les poids MTP résident dans la mémoire du périphérique, avant toute autre règle de placement : les couches nextn
greffées sur un modèle et toutes les couches d'un GGUF exclusivement MTP passé avec `--spec-draft-model`.
`mgs_model_base::mLoadTensors` attribue leurs couches et la couche de sortie à un GPU même lorsque `n_gpu_layers`
les laisse sur le CPU, et `mgs_model_loader::mCreateTensor` ignore les surcharges qui les enverraient vers la mémoire
de l'hôte (couches partielles de `--fit`, `--cpu-moe`, `--n-cpu-moe`, `--override-tensor` et leurs équivalents `--spec-draft-*`).
Les plongements de jetons restent sur le CPU comme ceux du tronc, car la lecture d'une ligne ne gagne rien sur
le GPU. Lorsque les couches MTP ne tiennent pas dans la mémoire libre du périphérique avec une marge de 512 Mio, le placement
normal s'applique. `--fit` mesure en chargeant le modèle sans l'allouer : il voit donc les poids MTP sur le
périphérique et ajuste le reste autour d'eux ; le cache des experts prend ce qui reste. Avec un GGUF MTP séparé,
`fCommonModelParamsToMgs` laisse non chargées les couches MTP greffées sur la cible au lieu de conserver une copie
inutilisée.

**Familles prises en charge.** Les familles MoE qui doivent fonctionner sont Qwen3.6 (`qwen35moe`), Qwen3.8-Flash-Next (`qwen4exp`), GLM-5.3 (`glm-dsa`), GLM-5.3-Flash (`glm5-next`), Kimi-K3 (`kimi-k3`), DeepSeek-V4.1-Flash (`deepseek41`), MiniMax-M3 (`minimax-m3`), Nemotron-3 (`nemotron_h_moe`) et MiMo-V2.6 (`mimo2`). Par décision de l'utilisateur, Gemma 4 (`gemma4`, `gemma4-assistant`, les projecteurs `gemma4v`, `gemma4uv`, `gemma4a` et `gemma4ua` et le format de conversation `peg-gemma4`) et toutes les architectures DeepSeek antérieures à V4.1 ont été supprimés : `deepseek`, `deepseek2` (qu'utilisaient aussi Kimi-K2.x, GLM-4.7-Flash, Moonlight, GigaChat3, Kanana-2, Mistral-Large-3 et Youtu), `deepseek2-ocr` avec les projecteurs `deepseekocr`, `deepseek32`, `mistral4` et `deepseek4`. Leurs GGUF sont rejetés comme architectures inconnues.

**Kimi-K3 (`models/kimi-k3.cpp`).** Des couches d'attention linéaire KDA (porte de rang plein `ssm_g` avec une décroissance en sigmoïde bornée, le `fBuildGdnL2Norm` partagé et la porte par canal de `mBuildRecurrentAttn`) alternent avec des couches MLA sous la forme absorbée `k_b`/`v_b`, avec une porte de sortie sigmoïde. Un mélange résiduel entre couches, construit avec `ggml_dsv4_hc_pre`, lit `attn_res_score`, `ffn_res_score` et `output_res_score`. Le MoE est latent : le routeur travaille à pleine largeur et les 896 experts à la largeur latente (`ffn_routed_down` → experts → `ffn_routed_norm` → `ffn_routed_up`), avec l'activation `situ` (`cLlmFfnSitu`) gérée dans `mBuildMoeFfn` ; `MGS_MAX_EXPERTS` vaut 1024 pour ce modèle. L'état récurrent prend en charge le retour arrière (`n_rs_seq`). Les GGUF publiés ne contiennent pas de MTP. Le modèle de conversation utilise `<|open|>`/`<|sep|>`/`<|close|>` et est analysé par `fCommonChatParamsInitKimiK3` ; le tokeniseur conserve le prétokeniseur `kimi-k2`.

**GLM-5.3-Flash (`models/glm5-next.cpp`) et `glm5v`.** Des couches KDA et des couches MLA uniquement nope avec l'indexeur DSA à k-pool (`indexer_kpool_gate`, `indexer_kpool_ape`), des flux d'hyperconnexion avec les opérations hc fusionnées et un MoE de style DeepSeek avec `ggml_swiglu_clamp`, une nouvelle opération (CPU, CUDA et Vulkan) qui préserve la fusion mat-vec + GLU de CUDA pendant le décodage. Le bloc NextN est une couche DSA : MTP s'active avec le seul `--model` et ses poids bénéficient du placement prioritaire en VRAM. La mémoire est `mgs_memory_hybrid_idx`. Le projecteur `glm5v` réutilise le graphe de glm4v avec une normalisation post-convolution facultative, un SwiGLU borné, son propre préprocesseur et les marqueurs `<|begin_of_image|>`/`<|end_of_image|>`. Les prétokeniseurs `glm4` et `glm5` utilisent ChatGLM4 avec `ignore_merges`.

**Qwen3.8-Flash-Next (`models/qwen4exp.cpp`).** Un mélangeur et une combinaison d'hyperconnexion de rang faible (`ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_post` avec un mélange identité), des plongements par couche hachés par n-grammes dont la table `per_layer_token_embd` (environ 29 Go) reste mappée et est lue à la demande avec préchargement des lignes, un historique de convolution dilatée dans le cache récurrent (`cache_ple_r_l`), des couches gated delta-net avec retour arrière, des couches d'attention QSA creuses par blocs (cache d'indexeur k-pool, score `ggml_lightning_indexer`, un masque de sélection top-k appliqué par-dessus le masque KQ, calculées avec la flash attention dense parce que les noyaux creux de l'amont ne sont pas portés), un MoE avec un expert partagé à porte, IMROPE et un bloc MTP avec son propre mélangeur d'hyperconnexion et sa mémoire de brouillon. `mgs_memory_hybrid_idx` (`mgs-memory-hybrid-idx.{h,cpp}`) combine le cache KV, le cache récurrent et le cache d'indexeur k-pool pour qwen4exp et glm5-next ; les cellules KV enregistrent l'identifiant du jeton (`vTok`) pour les recherches de n-grammes et `seq_pos` est un ensemble de paires (position, cellule).

**DeepSeek-V4.1-Flash (`models/deepseek41.cpp`, `mgs-kv-cache-dsv41.{h,cpp}`).** Deux dispositions publiées déclarent cette architecture : les fichiers DwarfStar d'antirez (clés reprises de la configuration Hugging Face, comme `deepseek41.hidden_size`, une chaîne JSON `deepseek41.config` et une table Engram I8 de valeurs E4M3 avec des échelles E8M0, 264 octets par ligne) et les fichiers de l'écosystème llama.cpp (clés standard, table Engram dans un type ggml). `fMgsDeepseek41AdaptMetadata` traduit la première disposition en clés standard avant la création du modèle (fonction de score → énumération de gating, `swiglu_limit` scalaire → tableaux par couche, 40 ou 43 taux de compression, décalages Engram calculés comme la somme cumulée des nombres premiers), et le chargeur accepte les deux noms des projections Engram. Les rôles des couches (source KV, propriétaire des clés d'index, source top-k) découlent des tenseurs présents. La table Engram (environ 188 Gio) est créée avec `cTensorExternal` : elle est comptabilisée mais jamais allouée, le préchargement s'arrête avant elle, et les lignes de chaque jeton sont lues avec `pread` sur un descripteur privé (`mEngramReadRows`, qui décode E4M3+E8M0 ou déquantifie avec `to_float`). Le cache conserve un groupe par taux de compression (pooling à porte pour le taux 2, un flux de longueur complète pour le taux 1 à partir de la couche 20), des caches de clés d'index uniquement sur les couches propriétaires des clés, et des couches lectrices qui adressent le stockage de leur couche source ; Engram prend les jetons précédents dans les cellules brutes du cache. Le graphe utilise des mélanges d'hyperconnexion décalés (une première copie one-hot, un effondrement final avec le dernier mélange FFN, sans tête HC), pas de normalisation de tête q, des clés d'index issues de la représentation latente avant RoPE, la réutilisation du top-k et le pool de blocs candidats à deux niveaux, Engram avant les couches 1 et 14, et `ggml_swiglu_clamp` dans les experts routés et partagés. Lorsque le GGUF n'a pas de modèle de conversation, `DEEPSEEK41_TEMPLATE_SRC` (une source Jinja) est utilisé ; les balises DSML commencent par un espace et le serveur transmet `reasoning_effort` (1–100) au modèle de conversation. Il n'y a ni MTP/DSpark ni vision. Les opérations ggml `dsv4_*` et `lightning_indexer` et les hyperparamètres `vDsv4HcMult`/`aDsv4CompressRatios` sont conservés parce que Kimi-K3, GLM-5.3-Flash et Qwen3.8 les utilisent ; sur Vulkan et Metal, ces opérations s'exécutent sur le CPU.

**Points de contrôle du contexte.** Les modèles dont la mémoire ne peut pas revenir en arrière (couches récurrentes ou SWA) se restaurent à partir de
points de contrôle. Ceux-ci sont créés au début d'un lot qui commence un message de l'utilisateur, de l'assistant ou d'un outil (les
limites où les agents modifient le contexte), près de la fin de l'invite, et à n'importe quel lot dès que le point de contrôle
précédent se trouve `--checkpoint-min-step` jetons en arrière (1024 par défaut). Une limite de message ne coupe un lot que si son
dernier micro-lot est rempli au moins aux 3/4, car chaque micro-lot supplémentaire fait de nouveau transiter les experts déchargés.
Lorsque `--ctx-checkpoints` est atteint, le point de contrôle dont les voisins sont les plus proches est supprimé, de sorte que les autres
restent répartis sur tout le contexte.

**Supervision et barre d'état.** `GET /api/monitor` rapporte l'utilisation du CPU (globale, par processeur physique et par CPU logique, à partir des écarts de `/proc/stat` ; chaque CPU logique est identifié par son numéro et regroupé selon le `physical_package_id` de sysfs, et chaque processeur prend son modèle dans ses blocs de `/proc/cpuinfo`), la RAM (`/proc/meminfo`) et chaque GPU (NVML via `dlopen("libnvidia-ml.so.1")`, puis chaque carte DRM d'un pilote de GPU que NVML n'a pas listée : amdgpu avec son `gpu_busy_percent` et la VRAM provenant de sysfs, et i915, xe, nouveau ou nvidia sans utilisation, complétées par le nom et la mémoire de leur backend dès qu'un modèle les utilise ; les adaptateurs d'affichage seul sont exclus, et l'interface ne dessine pas de barre de VRAM pour un GPU sans chiffres de mémoire), ainsi que la mémoire des modèles chargés, répartie par usage. La mémoire ne passe jamais par la file des tâches : chaque tâche publiée réinitialise `vTimeLastTask`, si bien qu'une page qui interroge le serveur toutes les deux secondes maintiendrait le modèle éveillé indéfiniment, et `mCreateResponse` attend qu'un modèle en veille se réveille. À la place, la boucle principale publie un instantané (`mRefreshMonitorSnapshot`) après `mLoadModel`, au plus une fois par seconde pendant que les emplacements travaillent et toujours une fois qu'ils sont inactifs (la fin d'une requête enregistre son invite) ; les threads HTTP se contentent de le copier sous un mutex, et l'entrée en veille publie `{"state": "sleeping"}`. L'instantané combine `mgs_get_memory_breakdown` (modèle, contexte et calcul par type de tampon) avec `mgs_model_get_weight_breakdown` (poids MTP et des experts routés, calculés une seule fois après le chargement parce que la fonction parcourt chaque tenseur) et `mgs_get_expert_memory_breakdown` (tampons du cache des experts et emplacements de préchargement de l'ordonnanceur, que la ventilation normale ne voit pas). Un contexte MTP sur le modèle cible partage ses poids, si bien que seuls son cache KV et ses tampons de calcul comptent ; un GGUF MTP séparé compte comme poids MTP et tout autre modèle brouillon comme poids du modèle brouillon. Les types de tampons de l'hôte (y compris la mémoire de l'hôte épinglée d'un GPU) vont dans la barre de la RAM et ceux des périphériques dans celle de leur GPU, associés à NVML par l'identifiant de bus PCI (en minuscules, sans le suffixe `-vN` des périphériques virtuels CUDA). `fMonitorReport` ajoute « autre » (la mémoire utilisée qu'aucun segment n'explique : autres processus, contextes des pilotes, projecteur) et le reste libre. Le processus parent du routeur n'initialise jamais de backend GPU, ce qui créerait son propre contexte CUDA : il lit les GPU via NVML et demande `/api/monitor/memory` à chaque processus enfant prêt (délai d'expiration de 1 s), tandis que les enfants en cours de chargement ou en veille ne rapportent que leur état. `GET /api/monitor/usage` (uniquement l'utilisation : CPU global, chaque processeur physique sans ses CPU logiques, et chaque GPU) est aussi autorisé pendant le chargement du modèle. Les lectures du CPU et des GPU sont partagées pendant 750 ms entre les clients qui interrogent simultanément ; une référence CPU de plus de 10 s est remplacée par un nouvel intervalle de 250 ms. Dans l'interface, `cMonitorStore` n'interroge le serveur que lorsque quelque chose y est abonné et se met en pause lorsque l'onglet est masqué ; la barre d'état réutilise le rapport tant que la page Supervision est ouverte. La page ne dessine que l'utilisation et la mémoire : les entrées par modèle du rapport (état, mémoire résidente, cache des experts) restent dans l'API pour d'autres clients. Ses cartes ont pour titre l'étiquette du périphérique en gras (`gpu-N` et `cpu-N`, dans l'ordre du rapport, une carte par GPU et par processeur physique) suivie du nom du périphérique ; chaque carte de processeur affiche la charge moyenne du système, et chaque jauge d'utilisation (`MonitorMeter`, les barres par cœur et la barre d'état) est une barre verte (`--monitor-meter-free`) qui se remplit de rouge selon l'utilisation (`--monitor-meter-used`), indépendamment de la palette catégorielle des barres de mémoire. La barre d'état est fixée en bas : `.has-status-bar` définit `--status-bar-height`, que le formulaire du chat, la barre latérale, les pieds de page collants et le remplissage du `body` ajoutent, de sorte que chaque décalage reste comme avant lorsque la barre est masquée (Paramètres → Affichage). Les barres de mémoire utilisent les huit couleurs catégorielles validées plus un « autre » neutre, dans un ordre fixe (`aMonitorSegmentGroups`), si bien que les segments apparentés du serveur partagent une couleur (poids MTP et du modèle brouillon, cache des experts et préchargement). Le menu de raisonnement dimensionne ses entrées selon leur contenu (`w-max`, noms avec `whitespace-nowrap`) : avec le `min-width: 0` et le `overflow-wrap: anywhere` globaux, un nom `flex-1` placé à côté d'une indication était auparavant coupé lettre par lettre.

**Backend Vulkan.** `build/build-local.sh --vulkan` et l'installateur Debian (`--vulkan`, également via `MGS_BUILD_BACKEND=vulkan`) configurent `-DGGML_VULKAN=ON` avec CUDA désactivé ; les shaders sont compilés avec `glslc` lors de la compilation et CMake a besoin des en-têtes Vulkan et SPIR-V (`libvulkan-dev`, `spirv-headers`). L'installateur ajoute ces paquets ainsi que `mesa-vulkan-drivers` ; la compilation locale se contente de vérifier la présence de `glslc` et transforme un échec de configuration en une indication qui nomme les paquets. L'ensemble autonome local copie le chargeur Vulkan `libvulkan.so.1` au moyen de la fermeture `ldd` habituelle, tandis que le pilote (ICD) est ouvert par le chargeur depuis `/usr/share/vulkan/icd.d/` et charge ses propres bibliothèques système (RADV entraîne LLVM, libdrm et les bibliothèques clientes X/Wayland) ; les sonames déjà présents dans `lib/mgs/` sont partagés, c'est pourquoi l'ensemble doit être compilé sur la version de Debian qui l'exécute. Le périphérique Vulkan annonce les capacités `async` et `events`, si bien que le préchargement des experts et le cache des experts fonctionnent sans changement, et son `device_id` est l'identifiant de bus PCI, de sorte que la page Supervision l'associe à NVML ou à la carte sysfs amdgpu (dont le nom générique est alors remplacé par la description du backend). Vulkan n'exporte pas `ggml_backend_register_host_buffer` ; les pages d'experts mappées restent donc paginables : sur une RTX 4060 Ti via Vulkan (Qwen3.6-35B-A3B Q4_K), les transferts d'experts mesurés ont atteint 2,7 Go/s avec mmap et 13,1 Go/s avec `--load-mode none` (tampons de l'hôte épinglés), et la génération 27,5 et 36,6 jetons/s ; le chargeur indique désormais qu'aucun backend ne peut épingler la mémoire mappée, au lieu d'incriminer CUDA. Les nœuds de rendu nécessitent le groupe `render`, que `configure-web.sh` accorde au compte de service (ainsi que `video`, de manière idempotente sur Alpine).

**VRAM réelle avec Vulkan.** Sur un GPU dédié, `ggml-vulkan` ne compte et n'alloue que la mémoire locale au périphérique (VRAM) ; la GTT, la partie de la RAM du système (normalement la moitié) que les GPU AMD et Intel peuvent mapper, n'est jamais comptée comme mémoire du GPU, car le GPU la lit via PCIe. Trois garde-fous maintiennent le modèle dans la VRAM réelle. Sans Resizable BAR, le tas local au périphérique visible par le CPU est une petite fenêtre (256 Mio sur une RX 580) partagée avec le bureau, et `ggml-vulkan` l'essayait auparavant en premier pour chaque tampon de périphérique : les petits tampons (environ 99 Mio, dont le cache KV de MTP) y atterrissaient et le noyau en évinçait 67 Mio vers la GTT. Lorsque ce tas fait moins de la moitié du plus grand tas local au périphérique, `disable_host_visible_vidmem` est désormais activé automatiquement, si bien que les tampons de périphérique vont dans le grand tas (sur la RX 580 : 0 évincé, 872 Kio restant dans la fenêtre). Les pools du cache des experts utilisent un second type de tampon Vulkan avec `VK_EXT_memory_priority` 0,5 (exporté sous le nom `ggml_backend_dev_get_cache_buffer_type` et choisi par `fPoolBufferType`), de sorte que, lorsque la VRAM se fait rare, le pilote évince le cache avant les couches MTP, les poids et le cache KV, qui conservent la priorité 1,0 ; les vérifications de copie asynchrone acceptent tout type de tampon de périphérique du même GPU (`ggml_backend_vk_buffer_is_device_of`). Enfin, chaque processus d'inférence lit `/proc/self/fdinfo` (`fMonitorDrmResidency` : `drm-resident-*`/`drm-memory-*` et `amd-evicted-vram`, publiés par amdgpu, i915 et xe), joint ces données à son instantané de supervision, avertit une fois dans le journal lorsque plus de 64 Mio (ou 2 %) de ses allocations GPU se trouvent hors de la VRAM (`mCheckVramResidency`), et la page Supervision affiche l'emplacement réel ainsi qu'un avertissement. `--load-mode none` n'est pas choisi automatiquement : sur AMD, la mémoire de l'hôte épinglée est décomptée de la GTT, et 18,9 Go d'experts avec 16,8 Go de GTT ont fait échouer RADV avec « Not enough memory for command submission » (`ErrorDeviceLost`).

**Serveur MCP de shell local.** `--local-shell-mcp-server` active `server_shell_mcp` (`backend/tools/server/server-shell-mcp.cpp`), un serveur MCP Streamable HTTP écrit en C++ à l'intérieur de `mgs`, de sorte que l'ensemble autonome n'a besoin ni de Python ni de paquets supplémentaires. Ce n'est pas un écouteur séparé : il est enregistré comme `<api prefix>/mcp/shell` sur le même serveur que l'API, si bien que l'interface web l'atteint par la même origine, le même certificat TLS, la même clé d'API et le même proxy Apache depuis n'importe quelle machine, alors qu'un port `127.0.0.1` ne serait accessible que depuis le serveur lui-même. Au démarrage, `mStart` cherche `bash`, `zsh`, `sh` et `pwsh`/`powershell` dans les entrées absolues du `PATH` et dans les répertoires habituels, et n'expose que les outils dont l'interpréteur existe et est exécutable (`bash.run`, `zsh.run`, `sh.run`, `psh.run`). Le serveur ne conserve aucun état : un message JSON-RPC par POST, des réponses JSON, pas de flux SSE (GET renvoie 405) et pas de session. `fRunCommand` lance l'interpréteur avec `posix_spawn` dans une nouvelle session (son propre groupe de processus, sans le terminal de contrôle du serveur, de sorte que sudo ne demande jamais de mot de passe sur le terminal qui a lancé `mgs`), avec `/dev/null` comme entrée, la gestion des signaux par défaut (le serveur ignore SIGPIPE) et des tubes séparés pour stdout et stderr, lus avec `poll` ; le délai d'expiration (60 s par défaut, 3600 s au maximum) ou la fermeture de la connexion tuent tout le groupe, et après la fin du shell la sortie en attente est lue pendant 250 ms, de sorte que les processus en arrière-plan ne peuvent pas bloquer l'appel. Chaque flux conserve son début et sa fin (8+8 Kio de stdout, 4+4 Kio de stderr). Chaque appel à un outil de shell laisse aussi son propre fichier JSONL, même lorsque ses arguments sont rejetés, (`server_shell_mcp_call_log`) dans `~/.mgs/local-shell-mcp-server/` de l'utilisateur qui exécute `mgs`, nommé d'après l'heure locale de l'appel à la milliseconde près (`y2026m10d12h23m59s59ms731.jsonl`, créé avec `O_EXCL`, de sorte que les appels d'une même milliseconde reçoivent `-2`, `-3`…) : une ligne `command` écrite avant l'exécution (outil, shell, répertoire de travail, délai d'expiration, commande), puis une ligne `stdout` ou `stderr` par lecture, avec toute la sortie dans l'ordre d'arrivée (`fRunCommand` remet chaque fragment à `pOutput`, et `mOutput` retient un caractère UTF-8 coupé entre deux lectures), et enfin une ligne `result` (code de sortie, signal, délai dépassé, annulation, secondes et octets de chaque flux) ou une ligne `error` (un appel rejeté a sa ligne `command`, avec ce qui a été demandé, et la ligne `error`). La sortie n'est jamais conservée en mémoire, si bien que le fichier contient tout ce que le résultat de l'outil tronque et survit à un arrêt de `mgs` pendant l'exécution. Le dossier est créé avec le mode 0700 et les fichiers avec 0600, car les sorties peuvent contenir des secrets ; un fichier qui ne peut pas être écrit ne laisse qu'un avertissement dans le journal. `mToolsCallResult` répond par un objet JSON (`vExitCode`, null lorsqu'un shell tué n'a pas pu être récupéré, `stdout`, `stderr`, `signal`, `vTimedOut`, `cancelled`, `timeout`, `seconds`, `shell`, `cwd`) à la fois comme `structuredContent` et comme bloc de texte, car l'interface ne conserve que le texte d'un résultat d'outil : le modèle lit le même JSON, et le chat le découpe en boîtes sans avoir à deviner où s'arrête un flux. Les requêtes avec un en-tête `Origin` doivent provenir d'une page de ce serveur (`fOriginAllowed`, comparé avec `Host`/`X-Forwarded-Host` ; les pages loopback sont acceptées pour le proxy de développement) et doivent utiliser `Content-Type: application/json`, ce qui bloque les requêtes intersites ; les clients sans `Origin` dépendent de la clé d'API. Comme les autres fonctionnalités d'agent, l'option limite l'origine CORS par défaut à localhost et ajoute un avertissement au démarrage. Les processus enfants du routeur ne la reçoivent jamais, et la route répond aussi pendant le chargement du modèle. `/api/props` publie `shell_mcp_server` ; `cMcpStore.mSyncShellServer` (appelé depuis le layout racine) ajoute l'entrée `mgs-shell` (nommée `local shell mcp server`, comme le `serverInfo.title` du serveur), activée la première fois, conserve son URL sur l'origine actuelle ainsi que son nom, et la supprime lorsque le serveur cesse de la proposer, et `MCPService.mCreateTransport` envoie la clé d'API de l'interface aux serveurs MCP de même origine. Les appels d'outils passent toujours par la demande d'autorisation de l'interface. Dans le chat, `ChatMessageToolCallBlock` envoie les appels `bash.run`, `zsh.run`, `sh.run` et `psh.run` (`fIsLocalShellTool` : noms de `aShellMcpToolNames` qu'aucun autre serveur MCP ne possède) à `ChatMessageToolCallBlockLocalShell`, qui garde le nom de l'outil comme titre et affiche les mêmes boîtes grises à police à chasse fixe que la boîte « Entrée » des autres outils : stdin avec la commande seule, extraite des arguments partiels pendant leur réception en flux, puis stdout et stderr uniquement lorsqu'elles ont du contenu, avec le code de sortie dans le titre (`stdout (code 2):`, ou `stdin (code 0):` sans sortie) ; la boîte stdin a une bordure blanche (gris foncé avec le thème clair), la boîte stdout une bordure verte et la boîte stderr une bordure rouge, de même pour les quatre outils (le `borderColor` de `SyntaxHighlightedCode` avec `--local-shell-stdin-border`, `--local-shell-stdout-border` et `--local-shell-stderr-border`). Un résultat qui n'est pas cet objet JSON (erreur d'arguments, autorisation refusée, requête échouée) s'affiche dans la boîte stderr. Le réglage `expandLocalShellCommands` (Affichage) fait en sorte que `ChatMessageAgenticContent.fGetDefaultExpanded` déploie ces appels, si bien que les boîtes apparaissent à mesure que leur contenu est connu.

**Paramètres de l'interface web.** Tous les paramètres de l'interface résident dans un seul document JSON que le serveur conserve dans `~/.mgs/config/ui-settings.json` de l'utilisateur qui exécute `mgs` (`backend/tools/server/server-ui-settings.cpp` : dossiers 0700, fichier 0600, écrit sous un mutex au moyen d'un fichier temporaire renommé par-dessus l'ancien), si bien que tous les navigateurs le partagent. `GET /api/ui/settings` renvoie `{"settings": DOCUMENT}` (`null` avant le premier enregistrement) et `POST /api/ui/settings` le remplace en entier ; les deux exigent la clé d'API, sont enregistrés dans tous les modes (le processus parent du routeur les sert lui-même) et répondent pendant le chargement du modèle. `/api/config.js` publie la langue enregistrée sous la forme `globalThis.cUiLanguage` (uniquement une étiquette de langue valide), car `i18n.ts` fixe la langue à l'importation du module. Dans l'interface, `cUiSettingsStore` (`frontend/src/lib/stores/ui-settings.svelte.ts`) charge le document lorsque le layout racine est monté et remet chaque section au store qui l'a enregistrée : `config` et `userOverrides` (store des paramètres), `favoriteModels` (modèles), `disabledToolKeys` (outils), `alwaysAllowedTools` (autorisations), `reasoningEffortDefault` (conversations) et `dismissedRecommendedMcpServers` (boîte de dialogue d'ajout de serveur MCP) ; `language` est écrit par `fSetLanguage`, qui attend la fin de l'enregistrement avant de recharger. `mSet` enregistre l'ensemble du document 300 ms après la dernière modification, et une modification encore en attente est envoyée avec `keepalive` lorsque la page se décharge. Rien n'est enregistré avant l'arrivée du document, de sorte qu'un état partiel n'écrase jamais le fichier ; un chargement qui échoue est retenté toutes les 5 s, sauf en cas de 401/403, où l'on attend la clé d'API. La synchronisation des valeurs par défaut du serveur et l'entrée du MCP de shell attendent à la fois `/api/props` et le document ; un document absent correspond à la première visite, où les valeurs par défaut de `--ui-config` s'appliquent une fois. Seule la clé d'API reste dans le navigateur (`MgsUi.apiKey`), car elle authentifie la requête qui charge le reste ; les conversations restent dans IndexedDB, et les clés de reprise des flux et de version de compilation dans `localStorage`.

**File d'attente des requêtes.** Le serveur a un seul emplacement par défaut (`-np 1`, `common_params::vNParallel` ; le mode automatique de l'amont, avec quatre emplacements partageant un cache KV unifié, a été supprimé, si bien que `--kv-unified` est aussi désactivé par défaut) : chaque requête obtient le contexte entier, qu'elle vienne de l'interface web ou directement de l'API, et les autres attendent dans la file différée de `server_queue`, qui les exécute dans l'ordre d'arrivée (un emplacement libéré déplace la première tâche différée en tête de la file des tâches, `mPopDeferredTask`). `-np N` exécute jusqu'à N requêtes en parallèle et répartit le contexte entre elles. L'API ne dépend ni de l'interface ni de son document de paramètres ; le seul lien est que l'interface web marque ses requêtes avec `"mgs_client": "webui"` (un `field_str` du schéma de complétion qui définit `task_params::vFromWebui`), si bien que le serveur connaît l'origine de chaque requête en cours ou en attente. Lorsqu'une tâche ne trouve aucun emplacement libre, `mDeferTask` compte les emplacements occupés (`mCountRunning`) et les tâches différées qui la précèdent (`server_queue::mDeferredTasks`), réparties entre API et interface web, et, lorsque la requête a demandé des notifications (`vQueueNotice` : interface web, mode flux, et tout format sauf Anthropic Messages et OpenAI Responses, dont les flux d'événements ont une grammaire fixe), envoie un `server_task_result_queue`, qui arrive dans le flux sous la forme `data: {"mgs_queue": {"ahead": N, "ahead_api": A, "ahead_webui": W}}`. Les gestionnaires en mode flux attendent le premier résultat avant d'envoyer les en-têtes, si bien que cet événement ouvre aussi la réponse immédiatement. Lorsqu'une tâche en file obtient son emplacement, elle reçoit une dernière notification avec tous les compteurs à 0, et `mNotifyQueuePositions` met à jour les tâches encore en attente. Les clients qui n'envoient pas `mgs_client` ne reçoivent jamais ces événements, si bien que leurs flux compatibles OpenAI restent inchangés. Dans l'interface, `ChatService.mHandleStreamResponse` transmet les événements à `onQueue` et efface l'état au premier fragment normal ; `cChatStore` le conserve par conversation (`mGetQueueStatus`) et `ChatMessageAssistantProcessingInfo` affiche `fQueueStatusText` avant tout autre texte de progression : la variante API lorsqu'une des requêtes qui précèdent est venue directement de l'API, sinon la variante interface web, toutes deux avec le nombre de requêtes qui précèdent. Les requêtes que l'interface envoie d'elle-même (préremplissage du cache KV après une réponse, titres générés) portent la même marque et attendent aussi leur tour.

**Demandes de mot de passe de sudo.** Sous Linux, lorsque sudo existe, `mStart` crée aussi `server_shell_mcp_askpass` : un socket Unix abstrait (aucun fichier à protéger ni à nettoyer) servi par son propre thread, avec un thread par connexion. Un `tools/call` dont le `_meta` contient `mgs/callId` (l'interface en génère un par appel dans `cMcpStore.mExecuteTool`) est enregistré avec un jeton aléatoire, et sa commande reçoit `SUDO_ASKPASS` (l'exécutable `mgs` lui-même : `MGS_EXECUTABLE`, publié par le lanceur, ou `/proc/self/exe`), `MGS_LOCAL_SHELL_ASKPASS` (nom du socket et jeton) et, lorsque le serveur n'en a pas, `DISPLAY=:mgs-askpass`, car sudo ne se rabat sur l'assistant askpass en l'absence de terminal que lorsque `DISPLAY` existe. sudo exécute `mgs <prompt>` ; `fServerShellMcpAskpassMain`, la première chose qu'appelle `mgs_server`, reconnaît ce cas (la variable, un seul argument et un parent sudo) et envoie le jeton et le message de demande par le socket. `mServe` vérifie avec `SO_PEERCRED` que l'assistant appartient au même utilisateur et avec `fParentIsSudo` que son parent est sudo (nom `sudo`, notre uid réel, root comme uid effectif ou sauvegardé : un processus non privilégié ne peut pas lire l'exécutable d'un processus setuid, c'est donc la vérification la plus forte disponible), de sorte qu'une commande ne peut pas lancer elle-même l'assistant avec un faux message pour capturer le mot de passe. La demande attend alors (5 minutes au plus) pendant que `fRunCommand` repousse son échéance du temps passé à attendre (`mPaused`) ; `DialogLocalShellAskpass`, monté une seule fois dans le layout racine pour s'ouvrir sur n'importe quelle page, interroge `GET /api/mcp/shell/askpass?call=` toutes les 500 ms pour chaque appel en cours (`cMcpStore.mActiveShellCalls`, rempli par `mExecuteTool` avec l'outil et la commande) et affiche la première demande dans une boîte de dialogue centrée (`Dialog` de ShadCN sans le bouton de fermeture : le champ du mot de passe prend le focus dès qu'une demande s'affiche (`fFocusPassword`, un attachement du champ, car `onOpenAutoFocus` s'exécute avant que sa référence ne soit liée), Accepter ou Entrée (`fHandlePasswordKeydown`) répond, Annuler ou Échap annule, un clic à l'extérieur ne fait rien) avec le message de sudo, l'outil et la commande, ainsi qu'un avis lorsque sudo redemande après un mot de passe ; `POST /api/mcp/shell/askpass` remet le mot de passe ou une annulation, l'assistant l'écrit dans le tube que lit sudo et les copies sont effacées. Le mot de passe n'atteint jamais le résultat de l'outil, la conversation ni les journaux ; les erreurs (annulation, absence de réponse, commande terminée) arrivent dans le stderr de la commande sous la forme `mgs: ...`. Les autres clients MCP n'envoient pas d'identifiant d'appel, si bien que leurs commandes ne reçoivent pas de variables askpass et que sudo échoue faute de terminal, comme auparavant.
**Durcissement de la sécurité.** La version 0.1.9 corrige les constats d'une revue de sécurité statique externe (21 constats : 20 corrigés ; celui qui concerne les installateurs est laissé tel quel à dessein, voir ci-dessous).
- **HTTP (`server-http.cpp`) :** les chemins publics ne dispensent de la clé d'API que pour GET/HEAD, et `GET /models?reload=...` exige la clé lorsque des clés existent. Avec le mode CORS `localhost` qu'activent les outils et les serveurs MCP, une requête dont la méthode n'est pas GET, HEAD ou OPTIONS reçoit 403 avant le routage lorsque son `Origin` n'est ni loopback ni ce même serveur (`Host` ou `X-Forwarded-Host` ; Apache conserve `Host` avec `ProxyPreserveHost On`) ; les requêtes sans `Origin` (curl, SDK) passent. `POST /tools` exige `Content-Type: application/json` (415), de sorte qu'un formulaire intersite ne peut pas l'atteindre sans une requête préliminaire (preflight) que CORS refuse. Pendant la réception d'une requête, chaque lecture attend 30 s au plus (`cHttpRequestReadTimeoutSec`) ; `--timeout` régit toujours les écritures, si bien que les longues générations ne sont pas coupées. Les deux pools de threads mettent en file d'attente au plus 256 connexions acceptées (`cHttpMaxQueuedConnections`), et `mPost`/`mDel` refusent les corps imbriqués sur plus de 1024 niveaux de tableaux ou d'objets (`fJsonNestingExceeds`, `cHttpMaxRequestJsonDepth`) avant qu'un gestionnaire ne les analyse, car nlohmann copie et sérialise les documents de manière récursive.
- **Routeur (`server-models.cpp`) :** `fRedactArgs` et `fRedactPreset` remplacent les valeurs des options secrètes (`sSecretOptionEnvs` : jeton HF, clé d'API et fichier de clés, clé SSL, configuration des serveurs MCP) par `<redacted>` dans `status.args`, `status.preset` et le journal de lancement ; les processus enfants reçoivent toujours les vraies valeurs. `mProxyRequest` supprime `Origin` lorsqu'il relaie une requête vers un processus enfant, car le routeur l'a déjà vérifié.
- **Proxy CORS (`server-cors-proxy.h`) :** les requêtes de navigation et d'intégration (`Sec-Fetch-Mode` navigate, `Sec-Fetch-Dest` document, frame, object ou worker) reçoivent 403 (`fProxyIsNavigation`), et chaque réponse relayée est rendue inerte (`fProxyMakeInert`) : CSP sandbox, `nosniff`, `Content-Disposition: attachment` et CORP same-origin, sans les en-têtes amont de cookies, CSP, CORS, HSTS, redirection, lien ou service worker. `Content-Type`, `mcp-session-id` et `WWW-Authenticate` sont conservés pour le client MCP de l'interface.
- **Médias distants (`download.{h,cpp}`, `server-common.cpp`) :** `fCommonRemoteGetContent` applique un délai de connexion, une échéance totale (`set_max_timeout` plus une vérification dans le récepteur du corps) et suit les redirections manuellement. Pour `image_url`, `input_audio` et `input_video` (`vPublicHostsOnly`), l'hôte est résolu une seule fois et chaque adresse doit être publique : ni loopback, ni RFC 1918, ni CGNAT, ni lien local (169.254.169.254 compris), ni plages de documentation, de multidiffusion ou réservées, et en IPv6 uniquement 2000::/3, les adresses mappées, NAT64 et 6to4 étant jugées d'après leur IPv4. La connexion est épinglée à l'adresse vérifiée (`set_hostname_addr_map`) et chaque redirection est de nouveau vérifiée ; `--media-allow-private-urls` lève la vérification des adresses. Les téléchargements de médias disposent de 10 s par connexion, lecture ou écriture, de 30 s au total, de 5 redirections, de 10 Mio et de 8 téléchargements simultanés (`media_download_slot`) ; `ffprobe` et `ffmpeg` ne lisent que des tubes lorsque l'entrée est un tampon de requête.
- **Décodage (`mtmd-helper.cpp`, `server-common.cpp`) :** images jusqu'à 32768 px par côté et 100 mégapixels, vérifiées avec `stbi_info_from_memory` avant le décodage ; audio jusqu'à une heure, vérifié avant l'allocation des échantillons ; images vidéo jusqu'à 8192 px par côté et 2 Gio d'images RGB par vidéo ; au plus 2 Gio d'images et d'audio décodés par requête (`fProcessMtmdPrompt`).
- **Analyseurs :** le convertisseur GBNF (`json-schema-to-grammar.cpp`) rejette les motifs vides et les quantificateurs qui n'ont rien à répéter ; il limite l'imbrication des schémas, les visites imbriquées et les chaînes de `$ref` à 256 (`cMaxSchemaDepth`, mesuré de manière itérative par `fJsonExceedsDepth`), les groupes de motifs à 128, les noms de propriétés exclues à 1024 octets et les listes `type` à 7 entrées, et assainit les noms de règles avec une boucle au lieu du `std::regex` récursif. Le moteur d'exécution Jinja (`jinja/value.h`) limite `range()` à un million d'éléments, les chaînes construites à 256 Mio et 1 Mi de fragments, l'indentation de `indent()`/`tojson()` à 256, l'imbrication de l'exécution des instructions à 1024 et l'imbrication de l'analyse à 256. `gguf.cpp` ignore les dimensions nulles dans la vérification de dépassement au lieu de diviser par elles ; les tenseurs vides restent valides.
- **RPC (`ggml-rpc/`) :** le `recv_msg` de taille variable applique un plafond par commande (SET_TENSOR : en-tête plus le plus grand tampon actif de la connexion ; GRAPH_COMPUTE : `INT32_MAX`, le maximum qu'un client peut envoyer) et intercepte `std::length_error`. Les bornes des tenseurs envoyées par le pair sont vérifiées avec des fonctions protégées contre les dépassements (`rpc_checked_nbytes`, `rpc_tensor_region_ok`) et donnent lieu à des réponses d'erreur au lieu de `GGML_ASSERT` ; toute exception ne ferme que cette connexion, et la libération d'un tampon supprime les graphes stockés qui l'utilisent. Les réceptions RDMA ne copient jamais plus que ce qui est demandé et gardent le reste dans `rx_pending` ; la paire de files n'accorde aucun accès distant.
- **Interface web :** un rendu Markdown qui échoue affiche du texte échappé. Les liens dont le schéma n'est pas http, https, mailto ou tel (ou relatif) perdent leur `href`, les pièces jointes d'images doivent être `data:image/...;base64`, et l'avis d'image cassée est construit avec des nœuds DOM (`fCreateImageErrorFallback`). L'importation de conversations vérifie le fichier (512 Mo), les entrées du ZIP (10 000), chaque JSONL (256 Mo) et le total extrait (1 Go) avant la décompression, valide chaque enregistrement, exige que le `convId` de chaque message corresponde à sa conversation et écrit avec `bulkAdd`, en ignorant toute conversation dont les identifiants de messages existent déjà. Une identité unique par nom d'outil (`mResolveEnabledEntry`) sert au modèle, à l'approbation et à l'exécution, qui est envoyée à ce serveur précis (`mExecuteTool(pToolCall, pServerId, pSignal)`) ; un nom proposé par deux serveurs MCP activés est écarté avec un avertissement, et « toujours autoriser ce serveur » s'applique par identifiant de serveur.
- **Dépendances de l'interface web (`frontend/package.json`, 0.1.10) :** les paquets signalés par `npm audit` qui atteignent le bundle du navigateur passent à des versions corrigées : DOMPurify 3.4.17, mermaid 11.17.2 et `@modelcontextprotocol/sdk` 1.32.1. SvelteKit 2.70.3 et `@vite-pwa/assets-generator` 1.0.4 (sharp 0.35.5, Node.js 20.9 ou ultérieur) sont aussi mis à jour, et `npm audit fix` actualise les paquets transitifs utilisés à la compilation dans leurs plages ; les versions directes restent épinglées exactement. Ce que `npm audit` liste encore ne touche que les outils de compilation (`postcss-selector-parser` via `@tailwindcss/typography`, le serveur de développement d'esbuild sous Windows) ou KaTeX, dont le correctif (0.18.2) est hors de la plage `^0.16` qu'acceptent `rehype-katex` et mermaid ; cet avis concernant KaTeX nécessite une pollution de prototype déjà présente pour être exploité.
- **Non traité :** l'épinglage des installateurs `curl | bash` sur une révision ou une signature immuable (les règles du projet exigent l'installation depuis `main`), une échéance absolue pour l'ensemble du bloc d'en-têtes (cpp-httplib applique le délai d'expiration à chaque lecture), les échéances de lecture du RPC et les clients RPC concurrents, un `create_node` itératif dans le serveur RPC, un budget global de CPU et de mémoire pour les modèles Jinja et la récursion de `mgs-grammar.cpp` sur la `grammar` de la requête.

<a id="flows"></a>
## Principaux chemins d'appel

1. **Installation :** entrée Debian par fichier ou stdin → validation → journal et verrou → copie locale des sources ou archive GitHub `main` → validation/synchronisation des sources → Bash enfant avec stdin fermé → `install-common.sh:fMain` → dépendances → préparation stable dans `_/temp/source`, y compris `build/` → CMake avec `-S _/temp/source/build` → installation de `bin/mgs`. Alpine appelle directement le script auxiliaire depuis une copie locale des sources.
2. **Déploiement :** `configure-web.sh` → compte du service → clé API/certificat → modèle de configuration autonome et services → `start-web.sh` → écouteurs occupés → choix de 11080+/11443+ → liaison d'Apache → appartenance des deux écouteurs → `ports.json`. Un vrai conflit de liaison renvoie au choix des ports ; les autres échecs arrêtent le service.
3. **Chat :** composant → `ChatService.mSendMessage` → messages normalisés et JSON personnalisé → `fApplyResponseLanguage` avec l'indicateur `respondInInterfaceLanguage` actuel et la locale de l'interface → `fApiUrl` → enregistrement HTTP → authentification/disponibilité → `server_routes` → file de tâches/emplacement → évaluation mgs/GGML → JSON ou SSE → stockage du navigateur et rendu. `mGenerateTitle` et chaque tour agentique empruntent ce même chemin ; `mPreEncode` applique la même instruction système avant de préparer le cache KV.
4. **Routeur :** gestionnaire externe → chemin interne canonique → choix du modèle → requête `/api` vers l'enfant → réponse ou flux conservé. La recherche, la reprise et l'annulation suivent le même contrat.
5. **MTP :** initialisation commune → `fCommonMaybeEnableEmbeddedMtp` → `fDetectEmbeddedMtp` → en-têtes et tenseurs de tous les fragments du GGUF → vérifications de l'architecture, du tronc et de la tête → choix de `draft-mtp`, sauf surcharge explicite → chargement du modèle : `mgs_model_base::mLoadTensors` place les couches MTP et la couche de sortie sur un GPU → `mgs_model_loader::mCreateTensor` ignore pour elles les surcharges vers la mémoire hôte.
6. **MoE :** poids mappés → enregistrement côté hôte → partitionnement du graphe → `fInitializeExpertPrefetch` → transfert par un backend séparé → événements prêt/libre → calcul. La pression mémoire réduit le nombre d'emplacements ou rétablit les copies ordinaires.
7. **Langue :** `lang` de l'URL (prioritaire) / stockage → l'un des 15 catalogues (par défaut `en-US`) → `fTranslate` → texte échappé par Svelte ; layout racine → `lang`/`dir` du HTML → navigation logique et texte bidirectionnel du chat ; sélecteur → persistance → rechargement.
8. **Inférence mise à jour :** indices d'origine du micro-lot → arène indépendante avec ou sans sorties → noyaux CPU/CUDA/HIP/Vulkan/SYCL → rétablissement de l'ordre des lignes NextN → acceptation jusqu'à l'EOG → métriques spéculatives des emplacements terminés.
9. **Exportation et outils :** identifiants sélectionnés → lecture des conversations et messages persistés → JSONL/ZIP ; HTTP 403 des outils → état désactivé conservé → nouvel essai explicite depuis le panneau.
10. **Compilation locale :** `build/build-local.sh` depuis un fichier ou stdin → options → choix local/distant → espace de travail privé et journal dans `/tmp/moe-gguf-server-build.XXXXXXXX/` → vérifications de la chaîne de compilation, de CUDA et de Node.js → copie locale, ou téléchargement, validation et extraction de l'archive HTTPS dans `source/`, y compris `build/` → CMake avec `-S source/build` dans `cmake/` → `mgs` → lanceur statique → chargeur, fermeture `ldd` et modules NSS dans `bundle/lib/mgs/` → binaire du serveur et `DT_RPATH` `$ORIGIN` → marqueur dans `bundle/lib/mgs/` → `build/licenses/` et le `LICENSE` de la racine dans `bundle/licenses/` → verrou du préfixe → artefacts terminés copiés à côté de leur emplacement final → remplacement atomique de `lib/mgs/`, `bin/mgs` et `share/doc/mgs/licenses/` → vérification avec `<loader> --list` → `--version` via le lanceur → `fCleanup` supprime l'espace de travail privé. À l'exécution : lanceur → `/proc/self/exe` → `MGS_EXECUTABLE` → préfixe à partir de `bin/` → `execv(lib/mgs/<loader>, lib/mgs/mgs, arguments)` → les enfants du routeur repassent par le lanceur.


11. **Démarrage web natif :** `common_params` / CLI → `server_http_context::mInit` → `fCreateHttpsServer` (PEM, ou `fPersistentServerIdentity` : charger ou créer `~/.mgs/certificates/`) → `start` → `fBindServerPort` pour HTTPS → port HTTP distinct → deux threads d'écoute → URL réelles dans le journal → arrêt et jonction des deux threads.
12. **Cache des experts MoE :** première requête après le chargement → `mgs_context::mDecode` → `mgs_expert_cache::mFCreate` → couches et groupes éligibles → budget de chaque GPU → pools et tampons d'identifiants sur chaque GPU → sonde de bande passante par GPU → `mSchedReserve` avec le graphe hybride et le callback d'envoi. Micro-lots de moins de 32 jetons : routeur sur le périphérique → `mPartition` sur le CPU (copie de la sélection, succès LRU, envois équilibrés, identifiants) → branche périphérique sur le pool → branche CPU sur les poids de l'hôte, en même temps → `mMeasureCpu` → fusion sur le périphérique → poids du routeur. Grands micro-lots : préchargement → `mUploadWeights` (copies sur le périphérique pour les experts en cache, envois depuis l'hôte pour les autres) → calcul. `POST /api/expert-cache` → file de tâches → `mgs_set_expert_cache_size` → le décodage suivant reconstruit le cache et les graphes.
13. **Points de contrôle du contexte :** remplissage du lot de l'invite → début de message dans un micro-lot rempli au moins aux 3/4, ou dernier message de l'utilisateur → coupure du lot → point de contrôle au début du lot (début de message, fin de l'invite ou `--checkpoint-min-step` depuis le précédent) → `mCreateCheckpoint` (évince les voisins les plus proches) → une requête ultérieure qui diverge à la position p restaure le point de contrôle le plus récent avant p → seul le suffixe est traité.

<a id="impact"></a>
## Analyse d'impact

- **Langue des réponses :** appliquer l'instruction après le JSON personnalisé, afin que le remplacement de `messages` ne puisse pas contourner le paramètre activé. Lire l'indicateur actuel à chaque nouvelle requête, plutôt que de stocker une instruction de locale dans la conversation. La complétion et le préremplissage doivent utiliser le même utilitaire pour préserver le préfixe KV. La reconnexion d'un flux réutilise la génération déjà en cours et ne peut pas changer son instruction de langue. Garder alignées les 15 entrées de catalogue `responseLanguage.*` ; les consignes régionales sont explicites pour l'espagnol d'Argentine et d'Espagne, l'anglais britannique et américain et le portugais du Brésil et d'Europe. Le respect de la consigne reste dépendant du modèle ; les appelants externes de l'API ne sont pas concernés.

- **Installation à distance :** les changements de l'URL, de la structure de l'archive GitHub et du protocole entre le point d'entrée et le script auxiliaire affectent `curl | bash`. Garder les options d'aide alignées et l'origine du dépôt fixe. Le marqueur et le verrou protègent l'arborescence gérée ; ne pas y stocker de modifications locales qui doivent survivre à la synchronisation.
- **TLS natif :** les clients directs doivent utiliser HTTPS et faire confiance au certificat ou fournir une paire PEM connue. `--http` est explicite pour le backend Apache et pour les enfants du routeur ; les enfants n'héritent pas des variables TLS publiques. Un port principal explicite n'est jamais modifié silencieusement. Les compilations sans OpenSSL exigent un HTTP explicite.
- **Ports web :** ils affectent les redirections, les adresses publiques, les pare-feu et l'origine du stockage du navigateur. `ports.json` n'est publié qu'une fois que les deux écouteurs appartiennent au processus Apache lancé. Un verrou exclusif empêche les lanceurs concurrents. Le port HTTPS est réservé avant la recherche du port HTTP, de sorte que des séquences qui se chevauchent ne partagent jamais un port. L'épuisement des ports produit une erreur explicite.
- **Préfixes et middlewares :** ils affectent tous les clients HTTP, l'authentification, le routeur, les flux, le frontend et Swagger. Modifier ensemble `server-http`, `server-models`, `api-url` et leur documentation.
- **Durcissement des requêtes :** la vérification intersites suppose que `Host` ou `X-Forwarded-Host` désigne l'adresse publique : un proxy inverse qui réécrit `Host` sans envoyer `X-Forwarded-Host` fait échouer avec une erreur 403 les écritures de l'interface lorsque les outils ou les serveurs MCP sont activés (`deploy/apache2.conf.in` conserve `ProxyPreserveHost On`). Augmenter `cHttpRequestReadTimeoutSec` ou supprimer la borne de la file d'attente réintroduit l'épuisement par des clients lents ; abaisser `cHttpMaxRequestJsonDepth` en dessous d'environ deux fois `cMaxSchemaDepth` ferait refuser des schémas JSON que le convertisseur accepte.
- **Options secrètes :** une option qui contient un secret d'authentification doit figurer dans `sSecretOptionEnvs`, sinon sa valeur apparaît dans la liste publique du routeur et dans le journal de lancement des processus.
- **Politique des médias distants :** les valeurs par défaut de `common_remote_params` conservent le comportement précédent pour les manifestes Hugging Face et Docker ; seul le chemin des médias définit `vPublicHostsOnly`. Suivre automatiquement les redirections, ou se connecter par nom après la vérification, rouvre la porte au DNS rebinding et aux SSRF par redirection. Les limites de décodage sont des constantes génériques de `mtmd-helper.cpp` et de `server-common.cpp` ; les abaisser fait refuser des médias volumineux légitimes.
- **Identité des outils de l'interface :** l'approbation, les autorisations et l'exécution doivent utiliser l'entrée renvoyée par `mResolveEnabledEntry` et son identifiant de serveur ; revenir à une résolution par simple nom (première correspondance dans l'interface, dernier écrivain dans `MCPStore`) permettrait à l'approbation donnée à un serveur d'exécuter l'outil d'un autre serveur, y compris le shell local.
- **Schéma de complétion :** il affecte la validation de l'inférence, les valeurs par défaut et la documentation OpenAPI. Les extensions doivent conserver les noms des champs du protocole.
- **Catalogues et sélecteur :** ils affectent toutes les vues et tous les libellés initialisés lors de l'importation des modules. Garder alignés les clés, les noms des langues et les paramètres de données dans les 15 catalogues ; les paramètres de suffixe pluriel de l'anglais peuvent être omis lorsqu'une traduction utilise des libellés avec compteur. Préserver les balises HTML et les jetons du modèle de titre comme `{{USER}}` et `{{ASSISTANT}}`. Enregistrer les nouvelles locales à la fois dans `aLanguages` et dans `dCatalogs`. L'hébreu affecte aussi le sens de la navigation ; le code doit rester LTR. Ne pas traduire les identifiants de protocole ni les données des utilisateurs.
- **Enregistrement et préchargement :** ils affectent l'utilisation de la RAM et de la VRAM, les événements GPU et la durée de vie des mappages et des tampons. Ne jamais libérer une page enregistrée ou un emplacement tant qu'il est encore utilisé.
- **MTP :** il affecte le choix du décodeur avant l'allocation des poids. Préserver la priorité des options explicites et inspecter chaque fragment du GGUF. Les poids MTP ignorent les surcharges vers la mémoire hôte et prennent la mémoire du périphérique avant que `--fit` ne place le tronc et avant le dimensionnement du cache des experts ; modifier l'affectation des couches MTP dans `mLoadTensors` change donc l'utilisation de la VRAM de tous les modèles avec MTP.
- **CMake et installateurs :** ils affectent toutes les plateformes de compilation. Ne pas réutiliser les caches de l'ancienne structure ni masquer les échecs de la compilation locale de l'interface.
- **Version :** `MGS_VERSION` donne leur nom aux fichiers des bibliothèques partagées (`libmgs-engine.so.0.1.0` ; le soname reste `.so.0`) et parvient à `/api/props`, à `system_fingerprint`, au `serverInfo.version` du MCP de shell, au `User-Agent` des téléchargements et au `build.json` de l'interface. Conserver la forme `MAJOR.MINOR.PATCH` : la compilation de l'interface rejette les caractères hors de `[A-Za-z0-9._-]`.
- **Vulkan :** le paquet partage le runtime C/C++ avec le pilote système qu'il charge ; un paquet compilé sur une version de Debian plus ancienne ou plus récente peut donc ne pas réussir à charger l'ICD. Les envois d'experts depuis la mémoire épinglée n'existent qu'avec CUDA ; tout changement des valeurs par défaut de `--load-mode` ou des types de tampon de l'hôte modifie la vitesse de transfert sous Vulkan. Les comptes de service qui n'appartiennent pas au groupe `render` ne peuvent pas ouvrir le GPU. Les tampons de périphérique doivent rester en mémoire device-local ; ne jamais activer `GGML_VK_ALLOW_SYSMEM_FALLBACK` ni `GGML_VK_PREFER_HOST_MEMORY` pour servir des modèles MoE. Une nouvelle allocation de périphérique de type cache doit utiliser le type de tampon de cache, et tout nouveau chemin asynchrone de `ggml-vulkan` doit accepter tous les types de tampon de périphérique du GPU.
- **Paquet local :** les bibliothèques nouvellement liées sont prises en compte automatiquement grâce à `ldd`. Les modifications de `OUTPUT_NAME`, du chemin de réexécution du routeur (`fGetServerExecPath`, `MGS_EXECUTABLE`), du mode d'exécution explicite du chargeur ou de l'ordre de recherche des bibliothèques affectent `build/build-local.sh` et le lanceur. Exécuter directement `lib/mgs/mgs` contourne le chargeur embarqué et n'est pas pris en charge. Les bibliothèques des pilotes doivent rester exclues.
- **Cache des experts MoE :** il affecte la mémoire du périphérique (le pool prend ce qui reste après le contexte ; `--moe-cache-reserve` couvre les autres processus et les tampons alloués à la demande), la synchronisation des partitions dans l'ordonnanceur, les noyaux CPU `mul_mat_id`/`add_id` (identifiants négatifs) et le graphe de chaque architecture MoE (`mBuildMoeFfn`). Les noyaux de périphérique des produits d'experts doivent accepter des identifiants d'emplacement distincts au sein d'un même jeton. Modifier le placement de `--fit` change la RAM nécessaire : lorsque `MemAvailable` est insuffisant, le maintien de tous les experts en RAM se replie sur des couches d'experts entières. Avec plusieurs GPU, chaque GPU possède son propre pool pour ses couches ; la répartition des couches (`--fit`, `--tensor-split`) décide des experts que chaque GPU met en cache.
- **Tailles de lot et threads :** `cBatchShare` dans `fRaiseBatch` échange de la mémoire du périphérique contre de la vitesse de traitement de l'invite ; le micro-lot est choisi avant le contexte, si bien qu'un micro-lot plus grand raccourcit aussi le contexte par défaut (Qwen3.6-35B-A3B Q8_0 sur 16 Go : 122880 jetons avec 512, 89856 avec 4096). Le serveur découpe les invites et place les points de contrôle du contexte selon les `mgs_n_batch`/`mgs_n_ubatch` de la cible, de sorte que leurs positions suivent les tailles choisies. Tout changement qui fait recevoir au contexte brouillon ou MTP un lot plus grand que son propre `n_batch` fait déborder son tampon de lot. `fCommonDefaultThreads` modifie la part du CPU de chaque couche MoE dont les experts sont en RAM ; mesurer la génération avec `--spec-type none` sur une machine virtuelle et sur une machine physique avant de changer le plafond.
- **Taille du contexte dans `--fit` :** `cContextShare` dans `fRaiseContext` échange du contexte contre des experts : chaque octet de cache KV qu'il autorise est pris sur le pool du cache des experts ou sur les couches d'experts entières placées sur les périphériques ; une part plus grande réduit donc la vitesse de génération et une part plus petite raccourcit le contexte par défaut. Le contexte brouillon suit le contexte cible ; modifier la façon dont `mLoadModel` le dimensionne change donc la mémoire du périphérique laissée au cache des experts de chaque modèle avec MTP ou avec un modèle brouillon.
- **Points de contrôle du contexte :** leur espacement et leur placement affectent la mémoire hôte (jusqu'à `--ctx-checkpoints` états par emplacement) et le découpage en lots du préremplissage ; chaque coupure supplémentaire coûte un passage de plus sur les experts déchargés.
- **Compatibilité supprimée :** les clients, les préréglages du routeur, les surcharges de service et les scripts de compilation doivent utiliser les noms actuels ; les alias supprimés échouent désormais comme options inconnues, sont ignorés comme variables d'environnement ou renvoient 404 comme routes. Réintroduire un nom exige de l'ajouter dans `common/arg.cpp`, `server.cpp` ou CMake et de le documenter dans les variantes de CODE et de MANUAL. Ne mettre à jour le README que lorsque sa présentation ou sa commande d'installation change.
- **Supervision :** l'instantané est construit dans la boucle principale, le seul thread autorisé à toucher aux contextes ; un tampon alloué en dehors de `mgs_get_memory_breakdown` (un nouveau cache ou un nouveau pool) apparaît comme « autre » tant qu'un appel de ventilation ne le signale pas. Ne jamais faire passer la supervision par la file de tâches : cela réinitialiserait le minuteur d'inactivité et réveillerait les modèles en veille. L'agrégation du routeur repose sur le contrat des enfants (préfixe `/api`, pas de clé API). Les nouveaux éléments fixes ou ancrés en bas de l'interface doivent ajouter `--status-bar-height`.
- **Serveur MCP de shell :** quiconque peut utiliser l'API (ou ouvrir l'interface) peut exécuter des commandes sous l'utilisateur du service ; il est donc réservé aux environnements de confiance et doit être combiné avec une clé API. Modifier la route, la propriété `shell_mcp_server` ou l'identifiant `mgs-shell` affecte la synchronisation de l'interface et les paramètres enregistrés ; modifier les vérifications d'Origin ou de Content-Type rouvre l'exécution de commandes intersites ; modifier `fRunCommand` affecte le nettoyage des groupes de processus, les délais d'expiration et les limites de sortie ; modifier les champs JSON de `mToolsCallResult` affecte ce que lit le modèle et `fParseLocalShellResult`, qui affiche alors tout le résultat comme texte stderr, ainsi que les lignes `result` des journaux d'appels ; modifier `cCallLogFolder`, le nom des fichiers ou les modes 0700/0600 de `server_shell_mcp_call_log` déplace les journaux d'appels ou expose la sortie des commandes aux autres utilisateurs.
- **Paramètres de l'interface web :** le document est partagé par tous les navigateurs et c'est le dernier enregistrement qui l'emporte ; un enregistrement envoie toujours toutes les sections, si bien qu'un store qui garderait des paramètres en dehors de `cUiSettingsStore` les perdrait sur les autres navigateurs. Enregistrer avant le chargement du document écraserait le fichier avec un état partiel, ce qu'empêche `mSet`. Renommer une section ou une clé de configuration laisse l'ancienne valeur non lue (pas de migration). Le fichier peut contenir des en-têtes MCP, d'où le mode 0600 ; toute personne qui possède la clé API peut le lire via l'API.
- **Demandes de mot de passe sudo :** le mot de passe traverse le navigateur, l'API (HTTPS et clé API) et le socket abstrait ; modifier `fParentIsSudo`, la vérification `SO_PEERCRED` ou la recherche du jeton permet à une commande de lire le mot de passe avec une fausse demande ; modifier `fServerShellMcpAskpassMain` ou sa position au début de `mgs_server` casse le programme auxiliaire ou fait se comporter comme lui les exécutions ordinaires de `mgs` à l'intérieur d'une commande ; modifier `cAskpassDisplay` ou la condition qui définit `DISPLAY` fait que sudo cesse d'utiliser le programme auxiliaire ; lancer les commandes sans session qui leur soit propre (`POSIX_SPAWN_SETSID`) fait que sudo demande plutôt le mot de passe dans le terminal qui a lancé `mgs` ; démonter `DialogLocalShellAskpass` du layout racine laisse les demandes sans réponse jusqu'à leur expiration ; modifier `mgs/callId` affecte `cMcpStore.mExecuteTool` et l'interrogation périodique de l'interface ; journaliser les corps des requêtes de `/mcp/shell/askpass` écrirait des mots de passe dans les journaux.
- **File d'attente des requêtes :** l'emplacement unique par défaut donne à chaque requête la totalité du contexte ; augmenter la valeur par défaut de `-np` (ou rétablir un mode automatique) répartit le contexte entre les emplacements et raccourcit les réponses longues. Les événements `mgs_queue` n'atteignent que les requêtes marquées avec `mgs_client: "webui"` : les envoyer à d'autres clients, ou dans les flux Anthropic Messages ou OpenAI Responses, casserait leurs analyseurs. Chaque gestionnaire de flux doit accepter un `server_task_result_queue` comme premier résultat ou comme résultat ultérieur, et tout nouveau chemin de report doit passer par `mDeferTask` afin que les requêtes en attente conservent leur position. Une tâche remise en file va à la fin de la file des tâches différées, comme dans le projet amont.
- **Architectures supprimées :** Gemma 4 et toutes les architectures DeepSeek antérieures à V4.1 ont disparu ; en réintroduire une suppose de restaurer ses entrées d'architecture, ses tables, son graphe, son vocabulaire et ses éléments de chat, et de la rajouter dans `RulesForThisProjectOnly.md`. Les GGUF d'autres modèles convertis en `deepseek2` (Kimi-K2.x, GLM-4.7-Flash et d'autres) ne se chargent plus.
- **Éléments DSV4 partagés :** `ggml_dsv4_hc_pre`, `ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_comb`, `ggml_dsv4_hc_post`, `ggml_lightning_indexer`, `vDsv4HcMult`, `aDsv4CompressRatios` et les cparams hc fusionnés servent à Kimi-K3, GLM-5.3-Flash, Qwen3.8 et DeepSeek-V4.1 ; une modification à cet endroit affecte les quatre. Ils n'ont pas de noyaux Vulkan ni Metal ; avec ces backends, ils s'exécutent donc sur le CPU.
- **Mémoire d'index hybride :** partagée par qwen4exp et glm5-next ; les cellules KV stockent des identifiants de jetons et `seq_pos` contient des paires (position, cellule), sur lesquelles reposent les plongements à n-grammes et la restauration de l'état.
- **Tenseurs externes :** les tenseurs `cTensorExternal` ne sont jamais alloués et le préchargement s'arrête au premier d'entre eux ; le code qui parcourt les données des tenseurs (quantification, enregistrement, rapports de mémoire) doit les ignorer. Les lignes Engram nécessitent un `pread` POSIX sur le fichier du modèle pendant toute l'exécution.

Les règles propres au projet interdisent d'écrire ou d'exécuter des tests. La revue est statique et ne garantit ni le bon fonctionnement à l'exécution ou sur GPU, ni celui de l'installation à distance, ni l'absence de débordement sur mobile. `tests/` est réservé et ne contient aucun test exécutable.
