## アーキテクチャと設計判断

**MoE モデルの読み込みと MTP の優先。** エンジンは `backend/src/CMakeLists.txt` にある明示的なソースリストをコンパイルします。dense 専用のデコーダー実装は削除されています。共有グラフは、それを使う MoE 実装（Phi-MoE、Granite、Nemotron、Ernie、Nomic を含む）に属し、MoE モデル内部の dense ブロックは引き続き必要です。`mgs_model_create` は重みを読み込む前にエキスパート数を確認し、dense なメインモデルを拒否します。例外は MTP として明示的に読み込まれるヘッドのみの GGUF で、dense な予測ヘッドを MoE のターゲットに使うことができます。Qwen35 に残っているのは MTP グラフだけです。

MTP の配置は、選択されたすべての GPU を対象とし、バックエンドの割り当てサイズとアラインメントを考慮し、出力ヘッド（またはそれと重みを共有するトークン埋め込み）も含めます。まず、すべてのヘッドを収容できる GPU を探し、見つからなければ最も大きいグループから順に複数の GPU に分けて配置します。グループが RAM にフォールバックするのは、選択されたどの GPU にも収まらない場合だけです。独立した `dMtpContexts` は、本体のコンテキストより先に割り当てられてアップロードされます。テンソルのオーバーライドでこの配置を置き換えることはできません。外部 MTP の重みは、`--fit off` の場合も含めてターゲットより先に事前読み込みされ、2 つ目のコピーを読み込むことなく投機的デコーディングの初期化に引き渡されます。fit の見積もりでは、それらのコンテキスト／計算用メモリを確保しますが、すでに割り当て済みの重みを二重に数えることはありません。

**ソースの規約と CLI の検証。** プロジェクトの識別子は CamelCase を使い、プロジェクトのルールで定められた関数・メソッド・パラメーター・値の接頭辞を付けます。公開 C API、GGUF の名前、プロトコルのフィールド、サードパーティの名前、フレームワークが要求するコールバック／コンポーネントの名前は、それぞれの契約どおりの名前を保持します。C++ の整形には 2 スペースのインデントを使います。この命名規則は、どの Linux ビルドでもコンパイルされないプリプロセッサの分岐（Windows、macOS、デバッグ用マクロ、`MGS_LLGUIDANCE`、`#if 0`）にも適用されます。そこではコンパイラが古い名前を検出できないため、名前を変更したときはそれらの分岐を手作業で確認する必要があります。`--chat-template-kwargs` は `vEnableThinking` を拒否するので、`--reasoning on` または `--reasoning off` を使ってください。アンダースコアを含むオプションの表記は書き換えられず、同じオプションを繰り返すと、明示的に繰り返し可能な `--spec-type` を除いて拒否されます。`Github-Repo-Push.sh` は `set -euo pipefail`、`fCleanup`、その EXIT トラップ、明示的に結果を確認する `fMain` を使っており、公開手順のいずれかが失敗するとスクリプトは停止します。

`frontend/` には UI、`backend/` にはエンジン、サーバー、依存関係、`deploy/` にはインストーラー、サービス、アセット用スクリプト、`build/` にはローカルの自己完結型ビルドスクリプトとその再配置可能なランチャー、`doc/` にはドキュメント、`_/` にはローカルの作業用資料が置かれています。取り込んだ依存関係はそのまま保持されています。

Svelte のインターフェースは `frontend/`、C++ のエンジン／サーバーは `backend/`、インストールは `deploy/` にあります。エンジンは `src/`、`common/`、`include/`、`ggml/`、`vendor/`、`tools/` の相対的な位置関係を保っています。`build/CMakeLists.txt` にある CMake のエントリポイントは処理をバックエンドに委ね、UI ライブラリは `frontend/` からビルドされて実行ファイルに埋め込まれます。CMake のターゲットは `mgs-engine`（エンジンライブラリ、`backend/src/`）、`mgs-common-base` と `mgs-common`（`backend/common/`）、`mtmd`、`server-context`、`mgs-server-impl`（`backend/tools/`）、`mgs-ui`（埋め込みインターフェース）、そして実行ファイルのターゲット `mgs` です。ビルド出力とインストールのどちらでも `mgs` という名前が使われます。

**命名。** llama.cpp から引き継いだコードは、プロジェクト独自の名前を使います。`backend/include/mgs.h` と `mgs-cpp.h` の公開 C API は `mgs_` と `MGS_` の接頭辞を使い、エンジンのソースは `backend/src/mgs*.{h,cpp}`、サーバーのエントリ関数は `mgs_server`、環境変数は `MGS_*`（`MGS_ARG_*`、`MGS_API_KEY`、`MGS_CACHE`、`MGS_MOE_CACHE*`、`MGS_SERVER_*`）、CMake のオプションは `MGS_*`、Prometheus のメトリクスは `mgs:*`、CORS プロキシのヘッダー接頭辞は `x-mgs-proxy-header-`、ブラウザのストレージは `MgsUi`、ダウンロードキャッシュは `~/.cache/mgs/`、tinyBLAS の CPU カーネルは `ggml-cpu/tinyblas/` 内の `GGML_TINYBLAS` です。残っている `llama` という表記は意図的なものです。具体的には、llama.cpp のライセンス表示（`LICENSE`、`build/licenses/LICENSE-llama.cpp`）と README のキャッチフレーズ、上流プロジェクトそのものへの言及（由来や比較。そのリポジトリへのリンクは含めません）、GGUF ファイル内に格納される値（SentencePiece のトークナイザーモデル `llama`、プリトークナイザー `llama-bpe` と `llama4`、およびそれらの識別子 `cMgsVocabPreTypeLlama3`/`LLAMA4` と `fUnicodeRegexSplitCustomLlama3`）、コメント内のサードパーティのモデルやコードの名前（CodeLlama、Llama-3_1-Nemotron、LLaDA、Ultravox モデル、YaRN の参照実装 `LlamaYaRNScaledRotaryEmbedding.py`）、tinyBLAS のソース内の参考文献、virtgpu バックエンドが使う virglrenderer の API リモーティングの `APIR_LLAMA_CPP_*` 変数、そして「llamada」のようなスペイン語の単語です。Meta の Llama アーキテクチャ（`llama`、`llama4`、`llama-embed`）、その組み込みチャットテンプレート、Llama 4 のビジョンプロジェクターは削除されました。

HTTP の登録処理は、公開する各ルートに API プレフィックスを付けます。ハンドラーはプレフィックスを除いた正規のパスを受け取り、ルーターはモデルの子プロセスに転送するときに `/api` を付け加えます。公開認証の許可リストには外部から見た完全なパスを使います。UI は `/` に置かれたままで、`/api/config.js` がアプリケーションのモジュールが読み込まれる前にプレフィックスを公開します。Swagger と OpenAPI は、モデルの読み込み中も含めて `/api/doc/` の下にあります。ルート／メソッドのレジストリが現在のルート一覧を提供し、completion のパラメーターは `server-schema` から取得されます。

JSON カタログには、`de-DE`、`en-GB`、`en-US`、`es-AR`、`es-ES`、`fr-FR`、`he-IL`、`hi-IN`、`it-IT`、`ja-JP`、`ko-KR`、`pt-BR`、`pt-PT`、`ru-RU`、`zh-CN` の 15 ロケール分のインターフェースの翻訳が収められています。`aLanguages` と `dCatalogs` はそれらをロケールコードのアルファベット順に登録し、`en-US` は既定の言語であると同時にメッセージのフォールバックでもあります。各カタログには、15 言語すべての名前のローカライズ版が含まれます。`fTranslate` は、会話データを変更することなく名前付きの値を補間します。新しい翻訳では、削除／インポートのメッセージで英語の複数形の接尾辞を補間する代わりに、件数ラベルを使います。言語を変更すると、その言語がサーバーの設定ドキュメントに保存され、モジュールのインポート時に計算されるラベルも切り替わるようにインターフェースが再読み込みされます。`/api/config.js` はモジュールが読み込まれる前に保存済みの言語を公開し、URL の `?lang=` はそれより優先されます。ルートレイアウトは HTML の言語と方向を設定し（`rtl` はヘブライ語のみ）、ナビゲーションは論理的な位置指定を使い、チャットの入力欄とユーザーのプレーンテキストには `dir="auto"` を使い、コード／ターミナルのテキストは左から右のままです。フレームワークの契約、プロトコルのフィールド、インポートしたシンボルは元の名前を保持し、プロジェクト独自の関数は所定の命名接頭辞に従います。

**ドキュメントの言語。** README、MANUAL、CODE の各ドキュメントは、インターフェースと同じ 15 ロケールで用意されています。`README.md`（en-US）はルートにあり、その翻訳は `doc/README.<locale>.md` です。マニュアルとこのガイドは `doc/MANUAL.md` と `doc/CODE.md`（en-US）、および `doc/MANUAL.<locale>.md` と `doc/CODE.<locale>.md` です。どの版も冒頭に、ほかのすべての版へロケールコードのアルファベット順でリンクする言語バーを置いています。見出しにはどの言語でも同じ `<a id>` アンカーが付いているため、ドキュメント間のリンク（`MANUAL.<locale>.md#local-build` など）はすべての言語で機能します。コードブロック、コマンド、パス、オプション、識別子はすべての翻訳で同一で、変わるのは本文だけです。ヘブライ語版はプレーンな Markdown です。GitHub と Gitea は段落ごとに方向を検出するため、本文は右から左に読まれ、コードブロックは左から右のままになります。

インストールには root が必要で、コマンドの失敗を明示的に処理し、ステージングは `_/temp/` の下でのみ行います。プロジェクトの変更を含まない上流のインターフェースをダウンロードする代わりに、UI はローカルでビルドされます。デプロイでは、特権を持たない推論サービスと Web サービスが作成されます。その専用の Apache インスタンスは、起動のたびに HTTP のポートを 11080 から、HTTPS のポートを 11443 から探します。推論はループバックの 8080 番ポートのままです。HAProxy は設定されません。プログラムの設定は `/opt/moe-gguf-server/.mgs/config/`（サービスアカウントの `~/.mgs/config/`）にあり、所有者はそのアカウントで、モードは 0600 です。中身は、`configure-web.sh` が書き込む `api.key`、`web-domain`、`apache2.conf.in`（Apache の `ServerRoot`）と、`mgs` が書き込む `ui-settings.json` です。`/etc` の下に残るのは、システムとの統合部分（systemd または OpenRC のユニット）だけです。会話はブラウザに保存され、バックエンドにユーザーデータベースはありません。

サーバー自体は既定で HTTPS を有効にします。`common_params` は 11443 から始まり、`server_http_context` は最初の空きポートにバインドし、続いて HTTP を 11080 から探します。2 つ目のリスナーは、ホスト、パス、クエリを保ったまま `Cache-Control: no-store` を付けて、選択された HTTPS ポートへの 308 を返します。`--port` はメインのポートを固定し（0 にすると OS に任せます）、`--http-port` は HTTP の探索開始ポートを変更します。探索が次のポートに進むのはアドレス使用中の競合の場合だけで、それ以外のエラーでは起動が停止します。`server-tls.cpp` は指定された PEM のペアを読み込み、指定がなければ `~/.mgs/certificates/` にある自己署名の ID（`fPersistentServerIdentity`）を使います。`fullchain.pem` と `privkey.pem` が対応していて証明書の有効期限が切れていない間はそれらを再利用し、そうでなければ ECDSA P-256 の証明書（有効期間 365 日、localhost、ループバック、設定されたホスト、マシン名、各インターフェースのアドレスを SAN に含む）を生成して、一時ファイルと名前の変更を通じて保存します（フォルダーは 0700、鍵は 0600）。そのため、どの実行でもどのビルドでも同じ証明書が提供され、ブラウザは信頼の例外を保持し続けます。外部コマンドは一切呼び出されません。フォルダーに書き込めない場合、その実行ではメモリ上の ID を使います。OpenSSL のサポートがない場合、HTTPS は明示的に失敗します。`--http` は意図的なプレーン HTTP を選択するもので、ルーターの子プロセスと 8080 番ポートの Apache バックエンドで使われます。Unix ソケットと Vertex AI は HTTP のままです。デストラクターは両方のリスナーを停止して join します。これらの判断は、インストーラーやランチャーとは独立して C++ 側に実装されています。

`build/build-local.sh` はワークステーションでの手動利用を想定しています。root を必要とせず、パッケージやサービスをインストールせず、実行中のものを何も残しません。完全なローカルのソースツリーをコピーするか、`curl | bash` 経由やスタンドアロンのスクリプトとして呼び出された場合は Git を使わずに GitHub の `main` アーカイブをダウンロードし、`/tmp/moe-gguf-server-build.XXXXXXXX/` で `mgs` ターゲットをビルドして、再配置可能な自己完結型のコピーをプレフィックスの下にインストールします（既定は `~/.local` で、現在のユーザー専用です。`--prefix` で変更できます）。インストールされるのは `bin/mgs`、`lib/mgs/`、`share/doc/mgs/licenses/` です。`lib/mgs/` には、サーバーのバイナリ、`ldd` で得られるその推移的な依存関係一式、glibc の動的ローダー、glibc が `dlopen` で開く NSS モジュールが入っています。カーネルは絶対パスの `PT_INTERP` しか受け付けないため、`bin/mgs` は静的なランチャー（`build/mgs-launcher.c`）になっています。このランチャーは `/proc/self/exe` を読み取り、`bin/` からプレフィックスへとさかのぼって、残りの引数を付けて `lib/mgs/<loader> lib/mgs/mgs` を実行します。プレフィックス内のものはどれも、その絶対的な位置に依存しません。サーバーのバイナリと同梱のライブラリには `DT_RPATH` `$ORIGIN` が設定されています。これは `LD_LIBRARY_PATH` より優先されるため、意図的に選んだものです。この方式ではサーバーのプロセスイメージがローダーになるため、ランチャーは `MGS_EXECUTABLE` をエクスポートし、`fGetServerExecPath` がそれを返すことで、ルーターの子プロセスはランチャーを通じて起動し直されます。NVIDIA ドライバーのライブラリ（`libcuda`、`libnvidia-*`）はカーネルモジュールと一致している必要があるため、決して同梱されません。`lib/mgs/` 内のマーカーファイルによって、このスクリプトが作成したものではないインストールを置き換えてしまうことを防ぎます。

ローカルでの各実行では、`mktemp -d /tmp/moe-gguf-server-build.XXXXXXXX` で作成した新しいプライベートディレクトリを使います。ダウンロードしたアーカイブ、そのメンバー一覧、コピーまたは展開したソース、CMake の出力、npm/Node/CUDA のキャッシュ、作業用ファイル、ログ、組み立てた `bundle/` はすべてそこに置かれます。コンパイラの自動キャッシュは無効になっている（`GGML_CCACHE=OFF`、`CCACHE_DISABLE=1`）ため、ビルド後にキャッシュサーバーが残ることはありません。成果物がそろうと、スクリプトは `flock` でプレフィックスのディレクトリ自体をロックし、完成したファイルを最終的な配置先の隣にある一時エントリにコピーしてから、同じファイルシステム上で名前を変更して所定の位置に置きます。`fCleanup` はログの書き込み処理を待ってから、成功時、失敗時、処理対象の INT/TERM/HUP シグナルを受けたときに、プライベートな作業領域を削除します。ソースツリーや `/opt/` にビルドファイルが書き込まれることはなく、ローカルのビルダーには `--build-dir` オプションはありません。

エントリスクリプトのパスは `fMain` を呼び出す前に `${BASH_SOURCE[0]:-}` で取得されるため、`set -u` のもとでも標準入力からの実行が機能します。オプションはソースの探索より前に解析されるので、`--help` にはソースツリーもソースのダウンロードも必要ありません。`fHasProjectSources` は、ビルドのエントリポイント、ランチャー、フロントエンドのマニフェスト、ライセンスのディレクトリを確認します。完全なローカルコピーがある場合は、既存の除外設定を適用してステージングされます。そうでない場合、`fDownloadSources` は curl/gzip がすでに存在することを要求し、リトライ付きで HTTPS 経由でダウンロードし、アーカイブ内のパスを検証してからプライベートな `source/` ディレクトリに展開し、そのうえで必要なファイルを確認します。`fMain` は標準入力を `/dev/null` からリダイレクトして実行されるため、ビルドツールがパイプで渡されたスクリプトを読み込んでしまうことはありません。リモート実行時のオプション指定には `bash -s --` を使います。パッケージがインストールされることは決してありません。


Debian のエントリポイントは単独で動作します。完全なローカルチェックアウトを検出するか、GitHub から `main` をダウンロードします。リモートモードでは `/opt/moe-gguf-server-source`（`MGS_INSTALL_SOURCE_DIR` で上書き可能）を使い、ソースの出所を示すマーカーを確認し、同期とコンパイルの間はロックを保持します。`rsync --checksum --no-times --delete` は不要になったソースを削除し、`_/` を保持し、変更されたファイルに新しいタイムスタンプを付けます。ヘルパーは、標準入力を閉じた別の Bash で、親のログストリームを複製せずに実行されます。

後方互換性のためのレイヤーは一切保持していません。非推奨の CLI エイリアスと削除済みオプションの墓標（tombstone）、重複した長いオプション名（各オプションは短い名前と長い名前を 1 つずつ持ちます）、`MGS_ARG_NO_*` 環境変数によるフォールバックと旧オプションにちなんだ名前の環境変数、旧来の HTTP ルートのエイリアス（`/completion`、`/embedding`、`/reranking`）と重複したリクエストフィールド（`thinking_budget_tokens`、embedding ルートの `content`）、思考出力形式 `deepseek-legacy`、Jinja 以外のテンプレートエンジン（`--jinja`/`--no-jinja`、`mgs-chat.cpp` の組み込み C++ テンプレート、`mgs_chat_apply_template`。すべてのチャットテンプレートは Jinja を通り、`chatml` は組み込みの ChatML ソースを指します）、古い CMake 変数名、ブラウザデータの移行処理、インストーラーの互換用シムは削除されました。そのため、各オプション、ルート、変数、保存される値には、現在の名前が 1 つだけあります。このプロジェクトは一度もデプロイされたことがないため、公開されている mgs/GGML/mtmd の C API にも非推奨のシンボルは一切残っておらず、現行の関数だけが残っています（削除されたものは [MANUAL.ja-JP.md](MANUAL.ja-JP.md#removed-compatibility) に一覧があります）。例外は意図的なものです。現行の変換や、サポート対象ファミリーで最もダウンロードされている公開 GGUF が依然として依存しているフォールバックによる GGUF ファイルの読み込み（Hugging Face 上のヘッダーで確認済みです。`full_attention_interval` から導出される Qwen3.6 のリカレント層の配置と、`attention.indexer.types` を持たない GLM-5.2/5.3 ファイル向けの組み込みの GLM-5.2 インデクサー配置）、ツールチェーンとオペレーティングシステムのバージョンによるガード、そして外部プロトコル（OpenAI、Anthropic、TEI/Jina、GCP Vertex、MCP）や ggml-virtgpu の virglrenderer ゲストのような外部の相手との相互運用性です。古いファイル向けのシムは削除されました。対象は、Grok-1、MiniCPM、Kimi-Linear の分割されていない `attn_kv_b`（非 MLA）の経路、Qwen3-Next の `ssm_in` の経路、`expert_gating_func`・`rope.scaling.finetuned`・`full_attention_interval` キーの欠落、Cohere2-MoE のスカラー値の SWA 周期、プリトークナイザーと Kimi-K2 のマージの欠落、`llama3`・`llama-v3`・`jina-es`・`jina-de`・`llada-moe` というプリトークナイザー名、`rope.scale_linear`、初期の Gemma 2、GGUF バージョン 1 と 2、古い `tokenizer.ggml.prefix/suffix/middle_token_id` キー、そして `mtmd` では、古い単発スクリプトによるプロジェクター（`mlp`、`mlp_norm`、`ldp`、`ldpv2`、`resampler`、`adapter`、プロジェクタータイプのないファイル）、古い改造（surgery）変換で入れ替わっていた FFN、欠落した Kimi-K2.5 と Step3-VL のキーの既定値です。ユーザーの判断により、アーキテクチャ全体の削除も行われました。Gemma 4 と、V4.1 より古いすべての DeepSeek アーキテクチャです（後述のサポート対象ファミリーを参照してください）。

手動で構成するには、プロジェクトのルートから `cmake -S build -B _/temp/cmake` を実行します。ビルドスクリプトは `build/` をソースと一緒にステージングし、CMake のソースディレクトリとして `source/build` を選択します。デプロイスクリプトは生成ファイルを `_/temp/` の下に置き、キャッシュされた構成が別のソースディレクトリを指している場合は `CMakeCache.txt` と `CMakeFiles/` をリセットします。ローカルビルドは常に `/tmp/` の下に新しい使い捨ての作業領域を作って使います。cpp-httplib の TLS ライブラリは、`backend/CMakeLists.txt` で宣言されたオプションに基づいて `backend/vendor/cpp-httplib/CMakeLists.txt` で選択されます。`MGS_BUILD_BORINGSSL` と `MGS_BUILD_LIBRESSL`（どちらも既定でオフ）はそのライブラリをダウンロードしてビルドするもので、この順に `MGS_OPENSSL`（既定でオン、システムの OpenSSL）より優先されます。どれも有効でない場合、サーバーは HTTPS に対応しません。

**バージョン。** プロジェクトのバージョンは、`backend/cmake/build-info.cmake` の `MGS_VERSION` として 1 か所だけで定義され（`0.1.0` から開始）、プロジェクトに変更を加えるたびにパッチ番号が上がります（0.1.1、0.1.2、…）。ローカルビルドと Debian インストーラーは同じ CMake ツリーを構成するため、どちらも同じバージョンになります。CMake は `mgs version: …` を出力し、`build-info.cpp` は `mgs_version()` でそれを返します。このバージョンは、共有ライブラリのファイルバージョン（soname は `.so.0` のまま）、`mgs.pc`、`mgs-config.cmake`、インターフェースの `build.json` にも設定されます。このプロジェクトは Git を使わないため、ビルド番号やコミットはありません。`--version`、`/api/props` の `build_info` プロパティ、OpenAI の `system_fingerprint`、シェル MCP の `serverInfo.version`、ダウンロード時の `User-Agent`（`mgs/0.1.0`）は、すべてこのバージョンを報告します。`deploy/scripts/ui-assets.cmake` は `build.json` に別のバージョンが入っているとインターフェースを再ビルドするため、インターフェースのソースに手を触れなくても、バージョンの変更は再利用される `_/temp/` のビルドツリーに反映されます。

整形の設定はフォルダー単位で適用されます。`.clang-format` は `backend/`、`frontend/`、`build/` にあり、`.editorconfig` はそれらのフォルダーに加えて `deploy/` と `tests/` にあります。`build/licenses/` 内のライセンス表示は `build/.editorconfig` を継承します。同等の設定は互いに同期させておいてください。プロジェクトのルートと `doc/` にあるファイルには、UTF-8、LF、2 スペースのインデントというエディターの設定が必要です。

`doc/` フォルダーには閲覧用のドキュメントが入っています。Swagger のページは `frontend/api.html` にあり、CMake がそれをサーバーに埋め込みます。バックエンドは、リクエストのたびに登録済みのルートから `/api/doc/openapi.json` を生成します。静的な `openapi.json` のソースファイルはありません。

このフォークは llama.cpp のサーバー、マルチモーダル対応、GGML バックエンドを受け継ぎ、重みが GPU メモリとシステム RAM に分かれている場合向けの MoE 最適化を加えています。ホストメモリの登録とエキスパートのプリフェッチは、thecodacus のフォークの `fable5/host-register` ブランチと `fable5/prefetch-experts` ブランチに由来します。プリフェッチスロットは gate/up/down のエキスパートテンソルを保持し、その転送を計算と重ね合わせます。自動 MTP は、`draft-mtp` を選択する前に `nextn_predict_layers`、モデル本体、統合されたすべてのヘッドを確認します。この確認はすべての GGUF シャードを対象にします。チューニングと制限事項については[マニュアル](MANUAL.ja-JP.md#performance)を参照してください。

**MoE エキスパートキャッシュ。** `backend/src/mgs-expert-cache.{h,cpp}` は、エキスパートがシステムメモリに置かれたままになっているすべての層について、最近使われたエキスパートを GPU ごとに 1 つのデバイスプールに保持します。このプールは、その GPU に割り当てられた層の間で共有されます（同じ GPU 上で、エキスパートごとのテンソルの型と形状が同一である層のグループごとに、1 つの LRU リストを持ちます）。1 つのスロットには、1 つのエキスパートのエキスパート単位のテンソルがすべて入ります。つまり、重み、バイアス、エキスパートごとのスケールで、gate/up の射影は分かれていても結合されていてもかまいません。op オフロードの下限（32 トークン、`GGML_OP_OFFLOAD_MIN_BATCH`）未満のマイクロバッチでは、`mBuildMoeFfn` はエキスパートの処理チェーンを 2 回構築します。スロット識別子を通じてプールを読むデバイス側の分岐と、ホスト上の重みを読む CPU 側の分岐です。最初に CPU のパーティション演算（`mPartition`）が実行されます。この演算はヒット数を数え、ミスのうち帯域幅に応じて配分した分（およそ m·B_upload/(B_upload+B_cpu)、最低 1 つ）をアップロードし、デバイス側の分岐より前に、スロット識別子とアップロードをデバイスのストリームにキューイングします。その間に、CPU 側の分岐が残りのミスを同時に計算します。もう一方の分岐が担当するエキスパートには、CPU 側では識別子 -1 が与えられ（CPU の `mul_mat_id`/`add_id` カーネルはそれらをスキップしてゼロを書き込みます）、デバイス側では空のスロットが与えられます（位置 k は空のスロット k を使うため、CUDA の MMQ ヘルパーが要求するとおり、1 つのトークン内でスロットが重複することはありません）。そのため、両方の分岐の和は、丸め誤差の範囲で通常の実行結果と一致します。スケジューラーが入力を持たない分割を直前の分割と同期させるのは、直前の分割が入力をコピーしていた場合か、そのバックエンドが現在のバッファータイプにアクセスできる場合だけです。これにより、上流の #26040 の修正を維持しつつ、両方の分岐を重ねて実行できます。アップロードの帯域幅は作成時に実際のエキスパートを使って測定され、CPU の帯域幅は CPU 側の分岐の所要時間からオンラインで推定されます。大きなマイクロバッチでは、エキスパートのプリフェッチが維持されます。`ggml_backend_sched_set_weight_upload` によって、キャッシュは自分が持つエキスパートをデバイス間コピーでプリフェッチスロットに移し、それ以外のものだけをホストメモリからアップロードします。キャッシュは、コンテキストの後に残ったデバイスメモリから `--moe-cache-reserve` とプリフェッチスロットを差し引いた分を使います。キャッシュは、すべてのコンテキストとプロジェクターが読み込まれた後の最初のリクエストで作成され（共通のウォームアップ処理はその作成を後回しにします）、実行時にサイズを変更でき（`mgs_set_expert_cache_size`、`POST /api/expert-cache`）、そのカウンターを `mgs_get_expert_cache_info`、`/api/expert-cache`、`/api/metrics` で報告します。設定は、`--moe-cache*` オプションで設定される `MGS_MOE_CACHE*` 環境変数を通じて渡されるため、公開 API は変わりません。キャッシュが有効で RAM が十分にある場合、`--fit` はすべてのエキスパートをシステムメモリに置き、空いているデバイスメモリをキャッシュに回します。デコーディングには、エキスパート層を丸ごと静的に置くよりも LRU キャッシュのほうが適しているためです。複数の GPU がある場合は、dense 部分のみとなった層をメモリ目標に応じてそれらに分散させるので、各 GPU は自分の層のエキスパートをキャッシュします。アップロードの帯域幅は GPU ごとに測定され、要求されたサイズは、各 GPU がキャッシュするホスト上のエキスパートに応じて GPU 間で分割されます。また、複数のマイクロバッチを同時に処理中の状態に保つパイプライン並列処理では、キャッシュは無効のままです。`--fit` は nextn（MTP）層も数に入れます。ローダーはこの層を、オフロードする層の番号の中に含めるためです。そうしないと、MTP がオフのときに最初の層が CPU に残っていました。

**`--fit` でのコンテキストサイズ。** `fCommonParamsFitImpl` のステップ 2 は、ユーザーが指定していないコンテキストを、すべての重みがデバイスメモリに収まらなければならないかのように縮小していました。そのため、デバイスより大きいモデルは、エキスパートが結局システムメモリに置かれるにもかかわらず、常に `--fit-ctx`（4096 トークン）まで落ちてしまい、思考を伴う回答が途中で切れていました。dense な重みが収まると、`fRaiseContext` は縮小後のコンテキストと学習時のコンテキストで dense のみの配置を測定して線形補間し、KV キャッシュとそれに伴って増えるバッファーが、dense な重みの後に残ったデバイスメモリの最大 4 分の 1（`cContextShare`）を占めるところまでコンテキストを引き上げます（256 の倍数に切り捨て、もう 1 回の測定で確認します）。この処理は、すべてのエキスパートを RAM に置く配置（エキスパートキャッシュ）が選ばれた後、エキスパート層が丸ごとデバイスを埋める前に実行されるため、エキスパートは常にそのメモリの少なくとも 4 分の 3 を確保できます。明示的に指定された `--ctx-size` は決して変更されず、`--fit-ctx` は最小値のままで、KV キャッシュがシステムメモリにある場合は何も変わりません。ドラフトのコンテキストは、ターゲットのコンテキストサイズを引き継ぎます（`mLoadModel` 内の `vParamsDft.n_ctx = n_ctx`）。以前はコンテキストサイズが 0 のとき、モデルの学習時のコンテキスト分の KV キャッシュを割り当てていたため、エキスパートキャッシュからデバイスメモリを奪っていました。

**自動構成。** `mgs --model FILE` は、そのマシンで最も速い設定を自分で選ばなければなりません。明示的に指定されたオプションは常に優先されます。エキスパートがシステムメモリにある場合、プロンプトの各マイクロバッチは、デバイス上にないエキスパートを PCIe 経由でストリーミングします（RTX 4060 Ti 上の Qwen3.6-35B-A3B Q8_0 では、マイクロバッチ 1 つあたり約 2 秒）。そのため、プロンプトの処理速度はマイクロバッチの大きさにほぼ比例して伸びる一方、生成速度はそれに左右されません。2514 トークンのプロンプトでは、マイクロバッチ 512 で 215 トークン/秒だった速度が、2048 で 408、4096 で 737～755 になり、生成速度は変わりませんでした。コンテキストを引き上げる前に、`fRaiseBatch` は選択された配置で 4096、2048、1024 トークンのマイクロバッチを試し、追加で必要なメモリが dense な重みの後に残ったデバイスメモリの 8 分の 1（`cBatchShare`）以内に収まる最大のものを採用します。論理バッチもそれに合わせて大きくなります。この処理が実行されるのは、`-b`/`-ub`（またはそれらの変数）が指定されていない場合だけです（`common_params::vBatchExplicit`。`pAutoBatch` として渡されます）。`common_init_result` は、得られた `n_batch` をパラメーターに書き戻します。ドラフトと MTP のコンテキストはパラメーターをコピーし、ターゲットの各バッチを自身の `n_batch` のバッファーに取り込むためです。それらのマイクロバッチは既定値のままです。CPU スレッド数の既定値（`fCommonDefaultThreads`。`-t` がないときに `fPostprocessCpuParams` が適用します）は演算に役立つコアの数で、プロセスのアフィニティマスクに含まれる論理 CPU の半分が上限です。MoE 推論のうち CPU が担う部分はメモリ帯域幅に律速されるうえ、SMT が見えない仮想マシンですべての論理 CPU を使うと、ワーカーが GPU を駆動するスレッドと競合していたためです（16 vCPU の場合、4～12 スレッドでは互いに誤差の範囲で、16 スレッドでは 13% 遅くなりました）。SMT が見える場合は上限が物理コア数と等しくなるため、ベアメタルのマシンでは従来の既定値が維持されます。`common_init_result` はスレッド数をログに記録し、`--fit` は自身が選択したマイクロバッチとコンテキストをログに記録します。

**MTP の配置。** MTP の重みは、ほかのどの配置ルールよりも優先してデバイスメモリに置かれます。対象は、モデルに組み込まれた nextn 層と、`--spec-draft-model` で渡された MTP 専用 GGUF のすべての層です。`mgs_model_base::mLoadTensors` は、`n_gpu_layers` がそれらを CPU に残すような場合でも、それらの層と出力層を GPU に割り当てます。また、`mgs_model_loader::mCreateTensor` は、それらをホストメモリに送るオーバーライド（`--fit` による部分的な層、`--cpu-moe`、`--n-cpu-moe`、`--override-tensor`、およびそれらに相当する `--spec-draft-*`）を無視します。トークン埋め込みは本体のものと同様に CPU に残ります。行の参照は GPU で行っても得るものがないためです。MTP 層が、512 MiB の余裕を見込んだデバイスの空きメモリに収まらない場合は、通常の配置が適用されます。`--fit` はモデルを割り当てずに読み込んで測定するため、MTP の重みがデバイス上にあることを把握したうえで、残りをその周りに収めます。エキスパートキャッシュは残った分を使います。MTP の GGUF が別にある場合、`fCommonModelParamsToMgs` は、使われないコピーを保持する代わりに、ターゲットに組み込まれた MTP 層を読み込まないままにします。

**サポート対象のファミリー。** 動作しなければならない MoE ファミリーは、Qwen3.6（`qwen35moe`）、Qwen3.8-Flash-Next（`qwen4exp`）、GLM-5.3（`glm-dsa`）、GLM-5.3-Flash（`glm5-next`）、Kimi-K3（`kimi-k3`）、DeepSeek-V4.1-Flash（`deepseek41`）、MiniMax-M3（`minimax-m3`）、Nemotron-3（`nemotron_h_moe`）、MiMo-V2.6（`mimo2`）です。ユーザーの判断により、Gemma 4（`gemma4`、`gemma4-assistant`、`gemma4v`・`gemma4uv`・`gemma4a`・`gemma4ua` の各プロジェクター、`peg-gemma4` チャット形式）と、V4.1 より古いすべての DeepSeek アーキテクチャが削除されました。削除されたのは、`deepseek`、`deepseek2`（Kimi-K2.x、GLM-4.7-Flash、Moonlight、GigaChat3、Kanana-2、Mistral-Large-3、Youtu も使っていたもの）、`deepseekocr` プロジェクターを含む `deepseek2-ocr`、`deepseek32`、`mistral4`、`deepseek4` です。それらの GGUF は未知のアーキテクチャとして拒否されます。

**Kimi-K3（`models/kimi-k3.cpp`）。** KDA の線形アテンション層（有界シグモイドによる減衰を伴うフルランクのゲート `ssm_g`、共有の `fBuildGdnL2Norm`、`mBuildRecurrentAttn` のチャネルごとのゲート）が、シグモイドの出力ゲートを備えた吸収形式 `k_b`/`v_b` の MLA 層と交互に並びます。`ggml_dsv4_hc_pre` で構築される層をまたぐ残差ミックスは、`attn_res_score`、`ffn_res_score`、`output_res_score` を読み取ります。MoE は潜在空間型です。ルーターはフル幅で動作し、896 個のエキスパートは潜在幅で動作します（`ffn_routed_down` → エキスパート → `ffn_routed_norm` → `ffn_routed_up`）。`situ` 活性化（`cLlmFfnSitu`）は `mBuildMoeFfn` で処理され、このモデルでは `MGS_MAX_EXPERTS` は 1024 になります。リカレント状態はロールバック（`n_rs_seq`）に対応しています。公開されている GGUF には MTP は含まれていません。チャットテンプレートは `<|open|>`/`<|sep|>`/`<|close|>` を使い、`fCommonChatParamsInitKimiK3` で解析されます。トークナイザーは `kimi-k2` プリトークナイザーをそのまま使います。

**GLM-5.3-Flash（`models/glm5-next.cpp`）と `glm5v`。** KDA 層と、k-pool DSA インデクサー（`indexer_kpool_gate`、`indexer_kpool_ape`）を備えた nope のみの MLA 層、融合された hc 演算によるハイパーコネクションのストリーム、そして `ggml_swiglu_clamp` を使う DeepSeek 方式の MoE で構成されます。この新しい演算（CPU、CUDA、Vulkan）で、デコーディング中も CUDA の mat-vec + GLU の融合を維持します。NextN ブロックは DSA 層です。MTP は `--model` だけで有効になり、その重みは VRAM 優先の配置を受けます。メモリは `mgs_memory_hybrid_idx` です。`glm5v` プロジェクターは glm4v のグラフを再利用し、オプションの畳み込み後の正規化、クランプ付きの SwiGLU、独自のプリプロセッサー、`<|begin_of_image|>`/`<|end_of_image|>` マーカーを加えています。`glm4` と `glm5` のプリトークナイザーは、`ignore_merges` 付きで ChatGLM4 を使います。

**Qwen3.8-Flash-Next（`models/qwen4exp.cpp`）。** 低ランクのハイパーコネクションのミキサーと結合（`ggml_dsv4_hc_pre_gated`、恒等ミキシングの `ggml_dsv4_hc_post`）、n-gram ハッシュによる層ごとの埋め込み（テーブル `per_layer_token_embd` は約 29 GB で、マップされたまま、行のプリフェッチを使って必要に応じて読み込まれます）、リカレントキャッシュ内の拡張（dilated）畳み込みの履歴（`cache_ple_r_l`）、ロールバック対応のゲート付き delta-net 層、QSA のブロックスパースアテンション層（k-pool インデクサーキャッシュ、`ggml_lightning_indexer` によるスコアリング、KQ マスクの上に重ねる top-k 選択マスク。上流のスパースカーネルは移植されていないため、dense な flash attention で計算します）、ゲート付き共有エキスパートを持つ MoE、IMROPE、そして独自のハイパーコネクションミキサーとドラフトメモリを持つ MTP ブロックで構成されます。`mgs_memory_hybrid_idx`（`mgs-memory-hybrid-idx.{h,cpp}`）は、qwen4exp と glm5-next 向けに、KV キャッシュ、リカレントキャッシュ、k-pool インデクサーキャッシュを組み合わせます。KV セルは n-gram の参照のためにトークン ID（`vTok`）を記録し、`seq_pos` は（位置、セル）の組の集合です。

**DeepSeek-V4.1-Flash（`models/deepseek41.cpp`、`mgs-kv-cache-dsv41.{h,cpp}`）。** このアーキテクチャ名を宣言している公開レイアウトは 2 種類あります。antirez の DwarfStar のファイル（`deepseek41.hidden_size` のように Hugging Face の設定から取ったキー、`deepseek41.config` という JSON 文字列、E8M0 スケール付きの E4M3 値からなる I8 の Engram テーブル。1 行あたり 264 バイト）と、llama.cpp エコシステムのファイル（標準のキー、ggml の型による Engram テーブル）です。`fMgsDeepseek41AdaptMetadata` は、モデルが作成される前に 1 つ目のレイアウトを標準のキーに変換し（スコアリング関数 → ゲーティングの列挙値、スカラーの `swiglu_limit` → 層ごとの配列、40 個または 43 個の圧縮率、素数の累積和としての Engram のオフセット）、ローダーは Engram の射影の両方の名前を受け付けます。層の役割（KV のソース、インデックスキーの所有者、top-k のソース）は、存在するテンソルから決まります。Engram テーブル（約 188 GiB）は `cTensorExternal` で作成されます。サイズとしては数えられますが割り当てられることはなく、プリフェッチはその手前で止まり、各トークンの行はプライベートなディスクリプター上で `pread` によって読み込まれます（`mEngramReadRows`。E4M3+E8M0 をデコードするか、`to_float` で逆量子化します）。キャッシュは圧縮率ごとに 1 つのグループを持ち（圧縮率 2 ではゲート付きプーリング、圧縮率 1 では層 20 以降の全長のストリーム）、インデックスキーのキャッシュはキーの所有者にだけ置かれ、読み取り側の層はソース層のストレージを参照します。Engram は直前のトークンを生のキャッシュセルから取得します。グラフでは、遅延したハイパーコネクションのミックス（ワンホットの最初のコピー、最後の FFN ミックスによる最終的な折りたたみ、HC ヘッドなし）、q ヘッドの正規化なし、RoPE 適用前の潜在表現から得るインデックスキー、top-k の再利用と 2 段階の候補ブロックプール、層 1 と層 14 の前に置く Engram、ルーティングされるエキスパートと共有エキスパートでの `ggml_swiglu_clamp` を使います。GGUF にチャットテンプレートがない場合は、`DEEPSEEK41_TEMPLATE_SRC`（Jinja のソース）が使われます。DSML タグには先頭に空白が付き、サーバーは `reasoning_effort`（1～100）をテンプレートに渡します。MTP/DSpark やビジョンには対応していません。ggml の `dsv4_*` と `lightning_indexer` の演算、および hparams の `vDsv4HcMult`/`aDsv4CompressRatios` は、Kimi-K3、GLM-5.3-Flash、Qwen3.8 が使っているため残されています。Vulkan と Metal では、それらの演算は CPU で実行されます。

**コンテキストのチェックポイント。** メモリをロールバックできないモデル（リカレント層や SWA 層を持つもの）は、チェックポイントから復元します。チェックポイントは、ユーザー、アシスタント、またはツールのメッセージが始まるバッチの開始時（エージェントがコンテキストを編集する境界）、プロンプトの終わり付近、そして直前のチェックポイントから `--checkpoint-min-step` トークン（既定値 1024）以上離れた後は任意のバッチで作成されます。メッセージの境界でバッチを区切るのは、そのバッチの最後のマイクロバッチが 4 分の 3 以上埋まっている場合だけです。マイクロバッチが 1 つ増えるたびに、オフロードされたエキスパートが再びストリーミングされるためです。`--ctx-checkpoints` に達すると、隣との間隔が最も狭いチェックポイントが削除されるため、残りのチェックポイントはコンテキスト全体に分散した状態を保ちます。

**Vulkan バックエンド。** `build/build-local.sh --vulkan` と Debian インストーラー（`--vulkan`、または `MGS_BUILD_BACKEND=vulkan`）は、CUDA をオフにして `-DGGML_VULKAN=ON` を構成します。シェーダーはビルド時に `glslc` でコンパイルされ、CMake には Vulkan と SPIR-V のヘッダー（`libvulkan-dev`、`spirv-headers`）が必要です。インストーラーはそれらのパッケージに加えて `mesa-vulkan-drivers` をインストールします。ローカルビルドは `glslc` の有無を確認するだけで、構成に失敗した場合は必要なパッケージ名を示すヒントに置き換えて表示します。ローカルのバンドルは通常の `ldd` による依存関係一式を通じて Vulkan ローダー `libvulkan.so.1` をコピーしますが、ドライバー（ICD）はローダーが `/usr/share/vulkan/icd.d/` から開き、ドライバー自身がシステムのライブラリを読み込みます（RADV は LLVM、libdrm、X/Wayland のクライアントライブラリを読み込みます）。`lib/mgs/` にすでにある soname は共有されるため、バンドルはそれを実行するのと同じ Debian のリリースでビルドしなければなりません。Vulkan デバイスは `async` と `events` の機能を報告するため、エキスパートのプリフェッチとエキスパートキャッシュはそのまま動作します。また、その `device_id` は PCI バス ID なので、モニターはそれを NVML または amdgpu の sysfs カードと対応付けます（その場合、カードの汎用名はバックエンドの説明に置き換えられます）。Vulkan は `ggml_backend_register_host_buffer` をエクスポートしないため、マップされたエキスパートのページはページング可能なままです。RTX 4060 Ti で Vulkan 経由で測定したところ（Qwen3.6-35B-A3B Q4_K）、エキスパートのアップロードは mmap で 2.7 GB/s、`--load-mode none`（ピン留めされたホストバッファー）で 13.1 GB/s に達し、生成速度はそれぞれ 27.5 トークン/秒と 36.6 トークン/秒でした。ローダーは現在、CUDA が原因だとする代わりに、マップされたメモリをピン留めできるバックエンドがないことを伝えます。レンダーノードには `render` グループが必要で、`configure-web.sh` がサービスアカウントにそのグループを付与します（`video` も付与し、Alpine では冪等に処理します）。

**Vulkan での実際の VRAM。** ディスクリート GPU では、`ggml-vulkan` はデバイスローカルのメモリ（VRAM）だけを数えて割り当てます。GTT は AMD と Intel の GPU がマップできるシステム RAM の一部（通常は半分）ですが、GPU は PCIe 経由でそれを読むため、GPU メモリとして数えられることはありません。3 つの安全策によって、モデルは実際の VRAM に保たれます。Resizable BAR がない場合、CPU から見えるデバイスローカルのヒープはデスクトップと共有される小さなウィンドウ（RX 580 では 256 MiB）で、`ggml-vulkan` は以前、すべてのデバイスバッファーについてまずそこを試していました。その結果、小さなバッファー（MTP の KV キャッシュを含む約 99 MiB）がそこに置かれ、カーネルがそのうち 67 MiB を GTT に追い出していました。現在は、そのヒープが最大のデバイスローカルヒープの半分未満であれば `disable_host_visible_vidmem` が自動的に設定されるため、デバイスバッファーは大きなヒープに置かれます（RX 580 では追い出しは 0 で、ウィンドウに残るのは 872 KiB）。エキスパートキャッシュのプールは、`VK_EXT_memory_priority` が 0.5 の 2 つ目の Vulkan バッファータイプを使います（`ggml_backend_dev_get_cache_buffer_type` としてエクスポートされ、`fPoolBufferType` が選択します）。そのため VRAM が逼迫すると、ドライバーは優先度 1.0 を保つ MTP 層、重み、KV キャッシュよりも先にキャッシュを追い出します。非同期コピーのチェックは、同じ GPU のあらゆるデバイスバッファータイプを受け付けます（`ggml_backend_vk_buffer_is_device_of`）。最後に、各推論プロセスは `/proc/self/fdinfo` を読み取り（`fMonitorDrmResidency`。amdgpu、i915、xe が公開する `drm-resident-*`/`drm-memory-*` と `amd-evicted-vram`）、それをモニターのスナップショットに添付し、GPU 割り当てのうち 64 MiB（または 2%）を超える分が VRAM の外にあるときはログで 1 回警告します（`mCheckVramResidency`）。モニターには実際の配置場所と警告が表示されます。`--load-mode none` は自動的には選ばれません。AMD ではピン留めされたホストメモリが GTT の枠を消費するため、16.8 GB の GTT に対して 18.9 GB のエキスパートを置いたところ、RADV が「Not enough memory for command submission」（`ErrorDeviceLost`）で失敗しました。

**ローカルシェル MCP サーバー。** `--local-shell-mcp-server` は `server_shell_mcp`（`backend/tools/server/server-shell-mcp.cpp`）を有効にします。これは `mgs` の内部に C++ で書かれた MCP Streamable HTTP サーバーなので、自己完結型のバンドルに Python **Web UI の設定。** インターフェースのすべての設定は 1 つの JSON ドキュメントにまとめられ、サーバーがそれを `mgs` を実行するユーザーの `~/.mgs/config/ui-settings.json` に保存します（`backend/tools/server/server-ui-settings.cpp`。フォルダーは 0700、ファイルは 0600 で、ミューテックスの保護下で一時ファイルに書き込み、古いファイルを上書きする形でその名前を変更します）。そのため、すべてのブラウザがこの設定を共有します。`GET /api/ui/settings` は `{"settings": DOCUMENT}` を返し（最初の保存前は `null`）、`POST /api/ui/settings` はそれを丸ごと置き換えます。どちらも API キーが必要で、すべてのモードで登録され（ルーターの親プロセスは自身でそれらを提供します）、モデルの読み込み中も応答します。`i18n.ts` はモジュールのインポート時に言語を確定するため、`/api/config.js` は保存済みの言語を `globalThis.cUiLanguage` として公開します（有効な言語タグの場合のみ）。インターフェースでは、`cUiSettingsStore`（`frontend/src/lib/stores/ui-settings.svelte.ts`）がルートレイアウトのマウント時にドキュメントを読み込み、各セクションをそれを登録したストアに渡します。`config` と `userOverrides`（設定ストア）、`favoriteModels`（モデル）、`disabledToolKeys`（ツール）、`alwaysAllowedTools`（許可）、`reasoningEffortDefault`（会話）、`dismissedRecommendedMcpServers`（MCP サーバー追加ダイアログ）です。`language` は `fSetLanguage` が書き込み、保存が終わるのを待ってから再読み込みします。`mSet` は最後の変更から 300 ms 後にドキュメント全体を保存し、ページのアンロード時にまだ保存待ちの変更があれば `keepalive` 付きで送信します。ドキュメントが届くまでは何も保存されないため、不完全な状態でファイルが上書きされることはありません。読み込みに失敗した場合は 5 秒ごとに再試行しますが、401/403 の場合は API キーを待ちます。サーバーの既定値の同期とシェル MCP のエントリは、`/api/props` とドキュメントの両方を待ちます。ドキュメントがない場合は初回の訪問であり、そのときに `--ui-config` の既定値が 1 回だけ適用されます。ブラウザに残るのは API キー（`MgsUi.apiKey`）だけです。残りを読み込むリクエストを認証するのがこのキーだからです。会話は IndexedDB に残り、ストリーム再開用とビルドバージョン用のキーは `localStorage` に残ります。

**リクエストキュー。** サーバーは既定でスロットを 1 つ持ちます（`-np 1`、`common_params::vNParallel`。統合 KV キャッシュを共有する 4 つのスロットを使う上流の自動モードは削除されたため、`--kv-unified` も既定でオフです）。各リクエストは、Web UI から来たものでも API に直接送られたものでも、コンテキスト全体を使えます。ほかのリクエストは `server_queue` の遅延キューで待機し、到着順に実行されます（スロットが解放されると、最初の遅延タスクがタスクキューの先頭に移されます。`mPopDeferredTask`）。`-np N` を指定すると最大 N 件のリクエストを並列に実行し、コンテキストをそれらの間で分割します。API はインターフェースにもその設定ドキュメントにも依存しません。唯一のつながりは、Web UI が自身のリクエストに `"mgs_client": "webui"` という印を付けることです（completion スキーマの `field_str` で、`task_params::vFromWebui` を設定します）。これによってサーバーは、実行中および待機中のすべてのリクエストの出所を把握します。タスクが空きスロットを見つけられないとき、`mDeferTask` は使用中のスロット（`mCountRunning`）と、自分より前にある遅延タスク（`server_queue::mDeferredTasks`）を、API と Web UI に分けて数えます。そして、リクエストが通知を求めている場合（`vQueueNotice`。Web UI からのリクエストで、ストリーミングであり、イベントストリームの文法が固定されている Anthropic Messages と OpenAI Responses 以外の形式であること）は、`server_task_result_queue` を送ります。これはストリームに `data: {"mgs_queue": {"ahead": N, "ahead_api": A, "ahead_webui": W}}` として届きます。ストリーミングのハンドラーは最初の結果を待ってからヘッダーを送るため、このイベントによってレスポンスもすぐに開始されます。キューに入っていたタスクがスロットを得ると、すべての件数が 0 の最後の通知を受け取り、`mNotifyQueuePositions` がまだ待機中のタスクを更新します。`mgs_client` を送らないクライアントはこれらのイベントを決して受け取らないため、その OpenAI 互換のストリームは変わりません。UI では、`ChatService.mHandleStreamResponse` がイベントを `onQueue` に渡し、最初の通常のチャンクを受け取ると状態をクリアします。`cChatStore` はその状態を会話ごとに保持し（`mGetQueueStatus`）、`ChatMessageAssistantProcessingInfo` はほかのどの進捗テキストよりも先に `fQueueStatusText` を表示します。前にあるリクエストのいずれかが API に直接送られたものであれば API 用の文言を、そうでなければ Web UI 用の文言を表示し、どちらも前にあるリクエストの数を示します。UI が自分で送るリクエスト（応答後の KV キャッシュの事前入力、自動生成されるタイトル）にも同じ印が付き、それらも順番を待ちます。

**sudo のパスワード入力要求。** Linux で sudo が存在する場合、`mStart` は `server_shell_mcp_askpass` も作成します。これは専用のスレッドが提供する抽象 Unix ソケット（保護や後始末が必要なファイルはありません）で、接続ごとに 1 つのスレッドを使います。`_meta` に `mgs/callId` を含む `tools/call`（UI が `cMcpStore.mExecuteTool` で呼び出しごとに 1 つ生成します）はランダムなトークンとともに登録され、そのコマンドには `SUDO_ASKPASS`（`mgs` の実行ファイル自体。ランチャーが公開する `MGS_EXECUTABLE`、または `/proc/self/exe`）、`MGS_LOCAL_SHELL_ASKPASS`（ソケット名とトークン）、そしてサーバー側で未設定の場合は `DISPLAY=:mgs-askpass` が設定されます。端末がないとき、sudo が askpass ヘルパーにフォールバックするのは `DISPLAY` が存在する場合だけだからです。sudo は `mgs <prompt>` を実行します。`mgs_server` が最初に呼び出す `fServerShellMcpAskpassMain` がこのケース（変数があり、引数が 1 つで、親が sudo であること）を認識し、ソケットを通じてトークンとプロンプトを送ります。`mServe` は、ヘルパーが同じユーザーのものであることを `SO_PEERCRED` で、その親が sudo であることを `fParentIsSudo` で確認します（名前が `sudo` で、実 uid がサーバーと同じで、実効 uid または保存 uid が root であること。特権のないプロセスは setuid プロセスの実行ファイルを読めないため、これが利用できる最も強力な確認です）。そのため、コマンドが偽のプロンプトを付けてヘルパー自体を起動し、パスワードを盗み取ることはできません。その後プロンプトは待機し（最大 5 分）、その間 `fRunCommand` は待機に費やした時間だけ期限を延ばします（`mPaused`）。ルートレイアウトに 1 度だけマウントされ、どのページでも開く `DialogLocalShellAskpass` は、実行中のすべての呼び出し（`mExecuteTool` がツールとコマンドを書き込む `cMcpStore.mActiveShellCalls`）について 500 ms ごとに `GET /api/mcp/shell/askpass?call=` をポーリングし、最初のプロンプトを画面中央のダイアログに表示します（閉じるボタンのない ShadCN の `Dialog` です。プロンプトが表示されるとすぐにパスワード欄にフォーカスが移ります。これは欄のアタッチメントである `fFocusPassword` が行います。`onOpenAutoFocus` は欄の ref がバインドされる前に実行されるためです。「承認」または Enter（`fHandlePasswordKeydown`）で応答し、「キャンセル」または Escape でキャンセルし、外側をクリックしても何も起きません）。ダイアログには sudo のプロンプト、ツール、コマンドが表示され、パスワードの入力後に sudo が再度要求したときはその旨の通知も表示されます。`POST /api/mcp/shell/askpass` がパスワードまたはキャンセルを届け、ヘルパーはそれを sudo が読み取るパイプに書き込み、コピーは消去されます。パスワードがツールの結果、会話、ログに届くことはありません。エラー（キャンセル、応答なし、コマンドの終了）は、`mgs: ...` としてコマンドの stderr に出力されます。ほかの MCP クライアントは呼び出し ID を送らないため、そのコマンドには askpass の変数が設定されず、sudo は従来どおり端末がないために失敗します。
**セキュリティの強化。** バージョン 0.1.9 では、外部の静的セキュリティレビューによる指摘事項に対処しています（指摘は 21 件で、うち 20 件を修正済みです。インストーラーに関する 1 件は設計上そのままにしています。後述を参照してください）。
- **HTTP（`server-http.cpp`）：** 公開パスで API キーが不要になるのは GET/HEAD の場合だけで、キーが存在する場合は `GET /models?reload=...` にもキーが必要です。ツールや MCP サーバーが有効にする `localhost` の CORS モードでは、メソッドが GET、HEAD、OPTIONS のいずれでもないリクエストは、その `Origin` がループバックでもこのサーバー自身（`Host` または `X-Forwarded-Host`。Apache は `ProxyPreserveHost On` で `Host` を保持します）でもない場合、ルーティングの前に 403 を受け取ります。`Origin` のないリクエスト（curl、SDK）は通過します。`POST /tools` には `Content-Type: application/json` が必要なため（415）、クロスサイトのフォームは、CORS が拒否するプリフライトなしにはそこに到達できません。リクエストの受信中、各読み取りの待機は最大 30 秒です（`cHttpRequestReadTimeoutSec`）。書き込みは引き続き `--timeout` で制御されるため、長い生成が途中で切られることはありません。どちらのスレッドプールも、受け付けた接続を最大 256 件までしかキューに入れず（`cHttpMaxQueuedConnections`）、`mPost`/`mDel` は、配列またはオブジェクトの入れ子が 1024 段より深い本文を、どのハンドラーが解析するよりも前に拒否します（`fJsonNestingExceeds`、`cHttpMaxRequestJsonDepth`）。nlohmann はドキュメントを再帰的にコピーしてダンプするためです。
- **ルーター（`server-models.cpp`）：** `fRedactArgs` と `fRedactPreset` は、秘密のオプション（`sSecretOptionEnvs`。HF トークン、API キーとキーファイル、SSL の鍵、MCP サーバーの構成）の値を、`status.args`、`status.preset`、起動ログの中で `<redacted>` に置き換えます。子プロセスには引き続き実際の値が渡されます。`mProxyRequest` は子プロセスに転送するときに `Origin` を取り除きます。ルーターがすでにそれを確認しているためです。
- **CORS プロキシ（`server-cors-proxy.h`）：** ナビゲーションと埋め込みのリクエスト（`Sec-Fetch-Mode` が navigate、`Sec-Fetch-Dest` が document、frame、object、worker のいずれか）は 403 を受け取り（`fProxyIsNavigation`）、プロキシされたすべての応答は無害化されます（`fProxyMakeInert`）。サンドボックスの CSP、`nosniff`、`Content-Disposition: attachment`、同一オリジンの CORP が付けられ、上流のクッキー、CSP、CORS、HSTS、リダイレクト、リンク、Service Worker のヘッダーは除去されます。`Content-Type`、`mcp-session-id`、`WWW-Authenticate` は、UI の MCP クライアントのために残されます。
- **リモートメディア（`download.{h,cpp}`、`server-common.cpp`）：** `fCommonRemoteGetContent` は接続タイムアウトと全体の期限（`set_max_timeout` に加え、本文の受信処理での確認）を適用し、リダイレクトは手動でたどります。`image_url`、`input_audio`、`input_video`（`vPublicHostsOnly`）では、ホストの名前解決は 1 回だけ行われ、すべてのアドレスが公開アドレスでなければなりません。ループバック、RFC 1918、CGNAT、リンクローカル（169.254.169.254 を含む）、ドキュメント用、マルチキャスト、予約済みの範囲は認められず、IPv6 では 2000::/3 だけが認められます。マップされたアドレス、NAT64、6to4 のアドレスは、その IPv4 アドレスで判定されます。接続は確認済みのアドレスに固定され（`set_hostname_addr_map`）、リダイレクトのたびに改めて確認されます。`--media-allow-private-urls` はアドレスの確認を解除します。メディアのダウンロードは、接続・読み取り・書き込みごとに 10 秒、全体で 30 秒、リダイレクト 5 回、10 MiB、同時に 8 件までです（`media_download_slot`）。入力がリクエストのバッファーの場合、`ffprobe` と `ffmpeg` はパイプだけを読み取ります。
- **デコード（`mtmd-helper.cpp`、`server-common.cpp`）：** 画像は 1 辺 32768 px、100 メガピクセルまでで、デコード前に `stbi_info_from_memory` で確認します。音声は 1 時間までで、サンプルを割り当てる前に確認します。動画のフレームは 1 辺 8192 px まで、RGB フレームは動画 1 本あたり 2 GiB までです。デコードされた画像と音声は、リクエストあたり最大 2 GiB です（`fProcessMtmdPrompt`）。
- **パーサー：** GBNF コンバーター（`json-schema-to-grammar.cpp`）は、空のパターンと、繰り返す対象のない量指定子を拒否します。また、スキーマの入れ子、入れ子になった訪問、`$ref` の連鎖を 256 まで（`cMaxSchemaDepth`。`fJsonExceedsDepth` が反復処理で測定します）、パターンのグループを 128 まで、除外するプロパティ名を 1024 バイトまで、`type` のリストを 7 項目までに制限し、ルール名のサニタイズには再帰的な `std::regex` の代わりにループを使います。Jinja ランタイム（`jinja/value.h`）は、`range()` を 100 万要素まで、構築される文字列を 256 MiB かつ 1 Mi 個の部分まで、`indent()`/`tojson()` のインデントを 256 まで、文の実行の入れ子を 1024 まで、解析の入れ子を 256 までに制限します。`gguf.cpp` は、オーバーフローの確認でゼロの次元で割る代わりにそれをスキップします。空のテンソルは引き続き有効です。
- **RPC（`ggml-rpc/`）：** 可変長版の `recv_msg` はコマンドごとの上限を受け取り（SET_TENSOR ではヘッダーにその接続で現存する最大のバッファーを加えた値、GRAPH_COMPUTE ではクライアントが送れる最大値である `INT32_MAX`）、`std::length_error` を捕捉します。相手から送られたテンソルの境界は、オーバーフローに対して安全なヘルパー（`rpc_checked_nbytes`、`rpc_tensor_region_ok`）で確認され、`GGML_ASSERT` の代わりにエラーを返します。例外が起きても閉じられるのはその接続だけで、バッファーを解放すると、それを使う保存済みのグラフも破棄されます。RDMA の受信では要求された量を超えてコピーすることはなく、残りは `rx_pending` に保持されます。キューペアはリモートアクセスを一切許可しません。
- **Web UI：** Markdown のレンダリングに失敗した場合は、エスケープしたテキストを表示します。スキームが http、https、mailto、tel のいずれでもない（相対リンクでもない）リンクは `href` を失い、画像の添付は `data:image/...;base64` でなければならず、壊れた画像の通知は DOM ノードで構築されます（`fCreateImageErrorFallback`）。会話のインポートでは、展開前にファイル（512 MB）、ZIP のエントリー（10,000 件）、各 JSONL（256 MB）、展開後の合計（1 GB）を確認し、すべてのレコードを検証し、各メッセージの `convId` がその会話と一致することを要求し、`bulkAdd` で書き込みます。メッセージ ID がすでに存在する会話はスキップされます。ツール名ごとに 1 つの識別情報（`mResolveEnabledEntry`）が、モデル、承認、実行のすべてに使われ、実行はまさにそのサーバーに送られます（`mExecuteTool(pToolCall, pServerId, pSignal)`）。有効な 2 つの MCP サーバーが同じ名前を提供している場合、その名前は警告とともに保留され、「次のサーバーのすべてのツールを常に許可」はサーバー ID 単位で適用されます。
- **Web UI の依存関係（`frontend/package.json`、0.1.10）：** `npm audit` で指摘され、ブラウザのバンドルに含まれるパッケージは、修正済みのリリースに移行しました。DOMPurify 3.4.17、mermaid 11.17.2、`@modelcontextprotocol/sdk` 1.32.1 です。SvelteKit 2.70.3 と `@vite-pwa/assets-generator` 1.0.4（sharp 0.35.5、Node.js 20.9 以降）も更新され、`npm audit fix` はビルド時の推移的なパッケージをそれぞれの範囲内で更新します。直接の依存関係のバージョンは引き続き厳密に固定されています。`npm audit` がまだ挙げているのは、ビルドツール（`@tailwindcss/typography` 経由の `postcss-selector-parser`、Windows 上の esbuild 開発サーバー）か KaTeX に関するものだけです。KaTeX の修正（0.18.2）は、`rehype-katex` と mermaid が受け入れる `^0.16` の範囲外にあります。この KaTeX の勧告を悪用するには、既存のプロトタイプ汚染が必要です。
- **対処しないもの：** `curl | bash` インストーラーを不変のリビジョンや署名に固定すること（プロジェクトのルールで `main` からのインストールが求められています）、ヘッダーブロック全体に対する絶対的な期限（cpp-httplib はタイムアウトを読み取りごとに適用します）、RPC の読み取り期限と同時接続のクライアント、RPC サーバーにおける `create_node` の反復処理化、Jinja テンプレートに対する CPU とメモリの全体的な予算、そしてリクエストの `grammar` に対する `mgs-grammar.cpp` の再帰です。

<a id="flows"></a>
## 主な呼び出し経路

1. **インストール：** Debian のファイルまたは stdin からの起動 → 検証 → ログとロック → ローカルのチェックアウトまたは GitHub の `main` アーカイブ → ソースの検証と同期 → stdin を閉じた子の Bash → `install-common.sh:fMain` → 依存関係 → `build/` を含む安定した `_/temp/source` への配置 → `-S _/temp/source/build` を指定した CMake → `bin/mgs` のインストール。Alpine はローカルのチェックアウトからヘルパーを直接呼び出します。
2. **デプロイ：** `configure-web.sh` → サービスアカウント → API キーと証明書 → 単独で動作するテンプレートとサービス → `start-web.sh` → 使用中のリスナー → 11080+/11443+ からの選択 → Apache の bind → 両方のリスナーの所有者の確認 → `ports.json`。実際に bind が競合した場合は選択に戻り、それ以外の失敗ではサービスを停止します。
3. **チャット：** コンポーネント → `ChatService.mSendMessage` → 正規化されたメッセージとカスタム JSON → 現在の `respondInInterfaceLanguage` フラグと UI のロケールを使う `fApplyResponseLanguage` → `fApiUrl` → HTTP の登録 → 認証と準備状態の確認 → `server_routes` → タスクキューとスロット → mgs/GGML による評価 → JSON または SSE → ブラウザーのストレージと描画。`mGenerateTitle` とエージェントの各ターンも同じ経路を使います。`mPreEncode` は、KV キャッシュを準備する前に同じシステム指示を適用します。
4. **ルーター：** 外部のハンドラー → 正規形の内部パス → モデルの選択 → 子プロセスへの `/api` リクエスト → レスポンスまたは保持されたストリーム。検索、再開、キャンセルも同じ取り決めに従います。
5. **MTP：** 共通の初期化 → `fCommonMaybeEnableEmbeddedMtp` → `fDetectEmbeddedMtp` → GGUF の全シャードのヘッダーとテンソル → アーキテクチャ、トランク、ヘッドの検査 → 明示的に上書きされない限り `draft-mtp` を選択 → モデルのロード：`mgs_model_base::mLoadTensors` が MTP 層と出力層を GPU に配置 → `mgs_model_loader::mCreateTensor` がそれらについてはホストメモリへのオーバーライドを無視。
6. **MoE：** マップされた重み → ホストへの登録 → グラフの分割 → `fInitializeExpertPrefetch` → 別のバックエンドによる転送 → ready/free イベント → 計算。メモリが逼迫すると、スロット数を減らすか通常のコピーに戻します。
7. **言語：** URL の `lang`（優先）またはストレージ → 15 のカタログのいずれか（既定は `en-US`）→ `fTranslate` → Svelte でエスケープされたテキスト。ルートレイアウト → HTML の `lang`/`dir` → 論理プロパティによるナビゲーションと双方向のチャットテキスト。セレクター → 保存 → 再読み込み。
8. **更新された推論：** マイクロバッチの元のインデックス → 出力ありと出力なしの独立したアリーナ → CPU/CUDA/HIP/Vulkan/SYCL のカーネル → NextN の行の順序を復元 → EOG まで受理 → 完了したスロットの投機的デコードのメトリクス。
9. **エクスポートとツール：** 選択された ID → 永続化された会話とメッセージの読み込み → JSONL/ZIP。ツールで HTTP 403 → 無効の状態を保持 → パネルからの明示的な再試行。
10. **ローカルビルド：** ファイルまたは stdin からの `build/build-local.sh` → オプション → ローカルかリモートかの選択 → `/tmp/moe-gguf-server-build.XXXXXXXX/` 内の非公開の作業領域とログ → ツールチェーン、CUDA、Node.js の確認 → ローカルのコピー、または HTTPS によるアーカイブのダウンロード、検証、`build/` を含めた `source/` への展開 → `cmake/` 内で `-S source/build` を指定した CMake → `mgs` → 静的ランチャー → `bundle/lib/mgs/` にローダー、`ldd` の閉包、NSS モジュール → サーバーバイナリと `DT_RPATH` の `$ORIGIN` → `bundle/lib/mgs/` にマーカー → `bundle/licenses/` に `build/licenses/` とルートの `LICENSE` → プレフィックスのロック → 完成した成果物をそれぞれの配置先の隣にコピー → `lib/mgs/`、`bin/mgs`、`share/doc/mgs/licenses/` をアトミックに置き換え → `<loader> --list` による検証 → ランチャー経由の `--version` → `fCleanup` が非公開の作業領域を削除。実行時：ランチャー → `/proc/self/exe` → `MGS_EXECUTABLE` → `bin/` からプレフィックスを求める → `execv(lib/mgs/<loader>, lib/mgs/mgs, arguments)` → ルーターの子プロセスもランチャーを経由して起動されます。


11. **ネイティブの Web 起動：** `common_params` / CLI → `server_http_context::mInit` → `fCreateHttpsServer`（PEM、または `fPersistentServerIdentity`：`~/.mgs/certificates/` をロードまたは作成）→ `start` → HTTPS 用の `fBindServerPort` → 別の HTTP ポート → 2 つのリスナースレッド → ログに実際の URL → 停止して両方のスレッドを join。

<a id="impact"></a>
## 影響分析

- **返答の言語：** 指示はカスタム JSON の後に適用するため、`messages` を置き換えても、有効になっている設定を回避することはできません。ロケールの指示を会話に保存するのではなく、新しいリクエストのたびに現在のフラグを読み取ります。KV のプレフィックスを維持するため、completion とプリフィルの両方で同じヘルパーを使う必要があります。ストリームの再接続はすでに実行中の生成を再利用するので、その言語の指示を変えることはできません。15 個の `responseLanguage.*` のカタログエントリーはすべてそろえておきます。地域ごとの指示は、アルゼンチンとスペインのスペイン語、英国と米国の英語、ブラジルとヨーロッパのポルトガル語について明示的に区別しています。プロンプトに従うかどうかは引き続きモデル次第で、外部の API 呼び出し元には影響しません。

- **リモートインストール：** URL、GitHub のアーカイブの構成、エントリーとヘルパーの間の取り決めを変更すると、`curl | bash` に影響します。ヘルプのオプションをそろえ、リポジトリの取得元は固定しておきます。マーカーとロックが管理対象のツリーを保護します。同期の後も残す必要があるローカルの編集をそこに置かないでください。
- **ネイティブ TLS：** 直接接続するクライアントは HTTPS を使い、証明書を信頼するか、既知の PEM の組を渡す必要があります。Apache のバックエンドとルーターの子プロセスでは `--http` を明示的に指定します。子プロセスは公開用の TLS の変数を継承しません。明示的に指定したメインのポートが、知らないうちに変更されることはありません。OpenSSL なしのビルドでは、HTTP を明示的に指定する必要があります。
- **Web のポート：** リダイレクト、公開アドレス、ファイアウォール、ブラウザーのストレージのオリジンに影響します。`ports.json` は、両方のリスナーが起動した Apache のプロセスのものになって初めて公開されます。排他ロックにより、ランチャーの同時実行を防ぎます。HTTP を探す前に HTTPS を予約するので、番号の並びが重なっても同じポートを共有することはありません。ポートが尽きた場合は明示的なエラーになります。
- **プレフィックスとミドルウェア：** すべての HTTP クライアント、認証、ルーター、ストリーム、フロントエンド、Swagger に影響します。`server-http`、`server-models`、`api-url` とそれらのドキュメントは一緒に変更します。
- **リクエストの堅牢化：** クロスサイトの検査は、`Host` または `X-Forwarded-Host` が公開アドレスを示していることを前提にしています。`X-Forwarded-Host` を送らずに `Host` を書き換えるリバースプロキシでは、ツールや MCP サーバーが有効な間、UI の書き込みが 403 で失敗します（`deploy/apache2.conf.in` は `ProxyPreserveHost On` を維持しています）。`cHttpRequestReadTimeoutSec` を引き上げたりキューの上限を外したりすると、低速なクライアントによるリソースの枯渇が再び起こりえます。`cHttpMaxRequestJsonDepth` を `cMaxSchemaDepth` のおよそ 2 倍より小さくすると、変換器が受け入れる JSON スキーマを拒否してしまいます。
- **秘密のオプション：** 認証情報を保持するオプションは `sSecretOptionEnvs` に登録しなければなりません。登録しないと、その値が公開のルーター一覧と起動のログに現れます。
- **リモートメディアのポリシー：** `common_remote_params` の既定値は、Hugging Face と Docker のマニフェストに対する従来の動作を維持します。`vPublicHostsOnly` を設定するのはメディアの経路だけです。リダイレクトを自動で追従したり、検査の後に名前で接続したりすると、DNS リバインディングやリダイレクトを悪用した SSRF の余地が再び生まれます。デコードの制限は `mtmd-helper.cpp` と `server-common.cpp` にある汎用の定数で、下げると正当な大きいメディアを拒否するようになります。
- **UI のツールの識別：** 承認、権限、実行には、`mResolveEnabledEntry` が返すエントリーとそのサーバー ID を使う必要があります。名前だけで解決し直すと（UI では最初に一致したもの、`MCPStore` では最後に書き込んだもの）、あるサーバーに対する承認で別のサーバーのツールが実行されてしまいます。ローカルシェルも例外ではありません。
- **completion スキーマ：** 推論の検証、既定値、OpenAPI のドキュメントに影響します。拡張する場合も、プロトコルのフィールド名は維持しなければなりません。
- **カタログとセレクター：** すべての画面と、モジュールのインポート時に初期化されるラベルに影響します。15 のカタログすべてで、キー、言語名、データのパラメーターをそろえます。翻訳が件数のラベルを使う場合は、英語の複数形の接尾辞のパラメーターを省略してもかまいません。HTML タグと、`{{USER}}` や `{{ASSISTANT}}` などのタイトルテンプレートのトークンは維持します。新しいロケールは `aLanguages` と `dCatalogs` の両方に登録します。ヘブライ語はナビゲーションの方向にも影響しますが、コードは LTR のままでなければなりません。プロトコルの識別子やユーザーのデータは翻訳しません。
- **登録とプリフェッチ：** RAM と VRAM の使用量、GPU のイベント、マッピングとバッファーの寿命に影響します。登録したページやスロットは、使用中の間は決して解放しないでください。
- **MTP：** 重みを確保する前のデコーダーの選択に影響します。明示的なオプションの優先を維持し、GGUF のすべてのシャードを検査します。MTP の重みはホストメモリへのオーバーライドを無視し、`--fit` がトランクを配置する前、そしてエキスパートキャッシュのサイズが決まる前にデバイスメモリを確保します。そのため、`mLoadTensors` での MTP 層の割り当てを変えると、MTP を持つすべてのモデルの VRAM 使用量が変わります。
- **CMake とインストーラー：** すべてのビルドプラットフォームに影響します。古いレイアウトのキャッシュを再利用したり、ローカル UI のビルドの失敗を隠したりしないでください。
- **バージョン：** `MGS_VERSION` は共有ライブラリのファイル名（`libmgs-engine.so.0.1.0`。soname は `.so.0` のまま）に使われ、`/api/props`、`system_fingerprint`、シェル MCP の `serverInfo.version`、ダウンロードの `User-Agent`、UI の `build.json` にも反映されます。`MAJOR.MINOR.PATCH` の形式を守ってください。UI のビルドは `[A-Za-z0-9._-]` 以外の文字を拒否します。
- **Vulkan：** バンドルは、ロードするシステムのドライバーと C/C++ ランタイムを共有するため、それより古い、または新しい Debian のリリースでビルドしたバンドルでは ICD をロードできないことがあります。エキスパートのピン留めアップロードは CUDA にしかありません。`--load-mode` の既定値やホストのバッファータイプを変えると、Vulkan の転送速度が変わります。`render` グループに属さないサービスアカウントは GPU を開けません。デバイスバッファーはデバイスローカルのメモリに留まる必要があります。MoE の推論を提供する際に `GGML_VK_ALLOW_SYSMEM_FALLBACK` や `GGML_VK_PREFER_HOST_MEMORY` を有効にしてはいけません。キャッシュに類する新しいデバイスメモリの確保にはキャッシュのバッファータイプを使い、`ggml-vulkan` に新しく加える非同期の経路はすべて、その GPU のあらゆるデバイスバッファータイプを受け入れなければなりません。
- **ローカルのバンドル：** 新たにリンクされたライブラリは `ldd` を通じて自動的に取り込まれます。`OUTPUT_NAME`、ルーターの再実行の経路（`fGetServerExecPath`、`MGS_EXECUTABLE`）、ローダーの明示実行モード、ライブラリの検索順序を変更すると、`build/build-local.sh` とランチャーに影響します。`lib/mgs/mgs` を直接実行すると同梱のローダーを迂回するため、サポートされません。ドライバーのライブラリは引き続き除外しなければなりません。
- **MoE エキスパートキャッシュ：** デバイスメモリ（プールはコンテキストの後に残った分を使い、`--moe-cache-reserve` は他のプロセスと遅延確保されるバッファーの分を確保します）、スケジューラーでの split の同期、CPU の `mul_mat_id`/`add_id` カーネル（負の識別子）、すべての MoE アーキテクチャのグラフ（`mBuildMoeFfn`）に影響します。エキスパートの積を計算するデバイスのカーネルは、1 つのトークン内で互いに異なるスロットの識別子を受け入れなければなりません。`--fit` の配置を変えると、必要な RAM が変わります。すべてのエキスパートを RAM に置く方式は、`MemAvailable` が足りないとエキスパート層を丸ごと配置する方式に戻ります。GPU が複数ある場合は各 GPU が自分の層のためのプールを持ち、層の分割（`--fit`、`--tensor-split`）によって、各 GPU がどのエキスパートをキャッシュするかが決まります。
- **バッチサイズとスレッド：** `fRaiseBatch` の `cBatchShare` は、デバイスメモリとプロンプトの処理速度とのトレードオフを決めます。マイクロバッチはコンテキストより先に決まるので、マイクロバッチを大きくすると既定のコンテキストも短くなります（16 GB での Qwen3.6-35B-A3B Q8_0：512 では 122880 トークン、4096 では 89856 トークン）。サーバーはターゲットの `mgs_n_batch`/`mgs_n_ubatch` に従ってプロンプトを区切り、コンテキストのチェックポイントを置くため、それらの位置は選ばれたサイズに従います。ドラフトや MTP のコンテキストに、自身の `n_batch` より大きいバッチを渡すような変更は、そのバッチバッファーをあふれさせます。`fCommonDefaultThreads` は、エキスパートを RAM に置くすべての MoE 層で CPU が受け持つ割合を変えます。上限を変える前に、仮想マシンとベアメタルの両方で `--spec-type none` を指定して生成速度を測定してください。
- **`--fit` でのコンテキストサイズ：** `fRaiseContext` の `cContextShare` は、コンテキストとエキスパートとのトレードオフを決めます。許可した KV キャッシュの 1 バイトごとに、その分がエキスパートキャッシュのプール、またはデバイスに配置されるエキスパート層全体から差し引かれるため、割合を大きくすると生成速度が下がり、小さくすると既定のコンテキストが短くなります。ドラフトのコンテキストはターゲットのコンテキストに従うため、`mLoadModel` でのそのサイズの決め方を変えると、MTP やドラフトモデルを使うすべてのモデルで、エキスパートキャッシュに残るデバイスメモリが変わります。
- **コンテキストのチェックポイント：** 間隔と配置は、ホストメモリ（スロットごとに最大 `--ctx-checkpoints` 個の状態）とプリフィルのバッチ分割に影響します。区切りが 1 つ増えるごとに、オフロードされたエキスパートをもう 1 回走査するコストがかかります。
- **削除された互換性：** クライアント、ルーターのプリセット、サービスのオーバーライド、ビルドスクリプトは、現在の名前を使わなければなりません。削除された別名は、オプションとしては不明なオプションとして失敗し、環境変数としては無視され、ルートとしては 404 を返します。名前を復活させるには、`common/arg.cpp`、`server.cpp`、または CMake に追加し、CODE と MANUAL の各言語版に記載する必要があります。README は、その概要やインストールのコマンドが変わった場合にだけ更新します。
- **モニター：** スナップショットはメインループ上で組み立てられます。メインループは、コンテキストに触れてよい唯一のスレッドです。`mgs_get_memory_breakdown` の外で確保されたバッファー（新しいキャッシュやプール）は、内訳の呼び出しがそれを報告するようになるまで「その他」として表示されます。モニターをタスクキュー経由にしてはいけません。アイドルタイマーがリセットされ、スリープ中のモデルを起こしてしまいます。ルーターでの集計は、子プロセスとの取り決め（`/api` プレフィックス、API キーなし）に依存しています。画面に固定する UI 要素や下端に固定する UI 要素を新しく加える場合は、`--status-bar-height` を考慮に入れなければなりません。
- **シェル MCP サーバー：** API を使える人（または UI を開ける人）は誰でもサービスユーザーとしてコマンドを実行できるため、信頼できる環境専用であり、API キーと組み合わせて使うべきです。ルート、`shell_mcp_server` プロパティ、`mgs-shell` 識別子を変更すると、UI の同期と保存された設定に影響します。Origin や Content-Type の検査を変えると、クロスサイトでのコマンド実行の余地が再び生まれます。`fRunCommand` を変えると、プロセスグループの後始末、タイムアウト、出力の上限に影響します。`mToolsCallResult` の JSON フィールドを変えると、モデルが読む内容、`fParseLocalShellResult`（解析できないと結果全体を stderr のテキストとして表示します）、呼び出しログの `result` 行に影響します。`cCallLogFolder`、ファイル名、`server_shell_mcp_call_log` の 0700/0600 のモードを変えると、呼び出しログの場所が変わるか、コマンドの出力が他のユーザーに見えてしまいます。
- **Web UI の設定：** ドキュメントはすべてのブラウザーで共有され、最後の保存が優先されます。保存では常にすべてのセクションを送るため、設定を `cUiSettingsStore` の外に保持するストアがあると、他のブラウザーではその設定が失われます。ドキュメントのロード前に保存するとファイルが不完全な状態で上書きされてしまいますが、`mSet` がそれを防いでいます。セクションや設定キーの名前を変えると、古い値は読まれなくなります（移行はありません）。ファイルには MCP のヘッダーが含まれることがあるため、モードは 0600 です。API キーを持つ人は誰でも、API を通じてそれを読めます。
- **sudo のパスワード要求：** パスワードはブラウザー、API（HTTPS と API キー）、抽象ソケットを通ります。`fParentIsSudo`、`SO_PEERCRED` の検査、トークンの照合を変えると、コマンドが偽の要求でパスワードを読み取れるようになります。`fServerShellMcpAskpassMain` や、`mgs_server` の先頭にあるその呼び出し位置を変えると、ヘルパーが動かなくなるか、コマンド内での通常の `mgs` の実行がヘルパーとして振る舞うようになります。`cAskpassDisplay` や `DISPLAY` を設定する条件を変えると、sudo がヘルパーを使わなくなります。コマンドを専用のセッション（`POSIX_SPAWN_SETSID`）なしで起動すると、sudo は代わりに `mgs` を起動した端末でパスワードを求めます。ルートレイアウトから `DialogLocalShellAskpass` を外すと、要求は期限切れになるまで応答されないままになります。`mgs/callId` を変えると、`cMcpStore.mExecuteTool` と UI のポーリングに影響します。`/mcp/shell/askpass` のリクエストボディをログに記録すると、パスワードがログに書き込まれてしまいます。
- **リクエストキュー：** 既定のスロット 1 つでは、各リクエストがコンテキスト全体を使えます。`-np` の既定値を上げる（または自動モードを復活させる）と、コンテキストがスロット間で分割され、長い回答が短くなります。`mgs_queue` イベントは、`mgs_client: "webui"` が付いたリクエストにしか届きません。他のクライアントや、Anthropic Messages、OpenAI Responses のストリームに送ると、それらのパーサーが壊れます。ストリーミングのハンドラーはすべて、最初の結果としても後続の結果としても `server_task_result_queue` を受け入れなければなりません。また、新しく追加する保留の経路はすべて `mDeferTask` を通し、待機中のリクエストが自分の位置を保てるようにします。再びキューに入れられたタスクは、upstream と同様に保留キューの末尾に回ります。
- **削除されたアーキテクチャ：** Gemma 4 と、V4.1 より古いすべての DeepSeek アーキテクチャは削除されています。いずれかを復活させるには、その arch のエントリー、テーブル、グラフ、語彙、チャットの各部品を戻し、`RulesForThisProjectOnly.md` に再び追加する必要があります。`deepseek2` として変換された他のモデルの GGUF（Kimi-K2.x、GLM-4.7-Flash など）は、もうロードできません。
- **共有の DSV4 部品：** `ggml_dsv4_hc_pre`、`ggml_dsv4_hc_pre_gated`、`ggml_dsv4_hc_comb`、`ggml_dsv4_hc_post`、`ggml_lightning_indexer`、`vDsv4HcMult`、`aDsv4CompressRatios`、融合された hc の cparams は、Kimi-K3、GLM-5.3-Flash、Qwen3.8、DeepSeek-V4.1 で使われます。ここを変更すると 4 つすべてに影響します。これらには Vulkan と Metal のカーネルがないため、それらのバックエンドでは CPU で実行されます。
- **ハイブリッドインデックスメモリ：** qwen4exp と glm5-next が共有します。KV のセルにはトークン ID が格納され、`seq_pos` は（位置、セル）の組を保持します。n-gram の埋め込みと状態の復元はこれに依存しています。
- **外部テンソル：** `cTensorExternal` のテンソルは決して確保されず、プリフェッチは最初のそのテンソルの手前で止まります。テンソルのデータを走査するコード（量子化、保存、メモリのレポート）は、それらをスキップしなければなりません。Engram の行を読むには、実行中ずっとモデルファイルに対して POSIX の `pread` を使える必要があります。

プロジェクト固有のルールにより、テストの作成と実行は禁止されています。レビューは静的なものであり、実行時の動作、GPU、リモートインストール、モバイル表示でのはみ出しについての正しさを保証するものではありません。`tests/` は予約されていますが、実行可能なテストは置かれていません。

## 拡張ポイント

- **エンドポイント：** ハンドラーを実装し、`server.cpp` で `get`、`post`、`del` を使って登録します。登録によってプレフィックスが付き、一覧にも含まれます。`fRouteDescription` と `fOperation` に、パラメーター、レスポンス、例を追加します。ルーターの操作については、認証と転送を確認します。
- **UI のテキスト：** 15 の JSON カタログすべてに安定したキーを追加し、値には `{p0}`、`{p1}` などを使って `fTranslate` で解決します。ヘルプの HTML は信頼できるものでなければなりません。ユーザーのコンテンツを、サニタイズしていない HTML として挿入しないでください。ロケールを追加するには、その完全な JSON を `i18n.ts` でインポートして登録し、`aLanguages` をアルファベット順に保ち、すべてのカタログにその `language.<locale>` のラベルを追加し、`README`、`MANUAL`、`CODE` の翻訳を加えて、すべての言語版の言語バーにそのリンクを追加します。
- **CLI オプション：** `common/arg.cpp` とそのパラメーター構造体を拡張し、公開の取り決めを維持し、動作を記載し、影響を受けるシンボル、モジュール、フローの行を更新します。認証情報を保持するオプションは、`sSecretOptionEnvs`（`server-models.cpp`）にも追加します。
- **インストール：** `fMain` と `fShowHelp` を拡張し、システムを変更する前に検証し、すべての失敗を伝播させ、CODE と MANUAL の各言語版を更新します。インストールのコマンドが変わる場合は、README の各言語版も更新します。
- **ローカルのバンドル：** 別のシステムライブラリを `lib/mgs/` から除外するには、`fIsDriverLibrary` を拡張します。これは `fVerifyBundle` の判定にも使われます。新しい補助ファイルは一時的な `bundle/` ディレクトリの下で組み立て、完成した成果物をプレフィックス内のそれぞれの配置先の隣にコピーしてから、ディレクトリの置き換えに `fReplaceDirectory` を使います。新しくインストールするエントリーは、`fMain` の所有者の確認に追加します。
- **エキスパートごとのテンソル：** `mgs_expert_role` に役割を追加し、`fLayerExpertTensors` と `mBuildMoeFfn` の `vTensors` のまとまりでそれを対応付け、プールのテンソルをデバイス側の分岐に渡します。そうすれば、プール、アップロード、プリフェッチの再利用がそのテンソルにも適用されます。
- **ビルドのバックエンド：** 両方のスクリプト（`build-local.sh` と `install-common.sh`、さらに Debian のエントリースクリプトの引き渡しリスト）にオプションを、`fInstallSystemDependencies` にそのパッケージを、configure の引数にその `-DGGML_*` フラグを、サマリーにそのメッセージを追加します。バイナリが直接リンクするドライバーのライブラリは `fIsDriverLibrary` に追加します。
- **新しいバージョン：** プロジェクトに変更を加えるたびに、`backend/cmake/build-info.cmake` の `MGS_VERSION` のパッチ番号を上げます（0.1.1、0.1.2 など）。バイナリ、ライブラリ、インターフェースはそこからバージョンを取得するので、他に編集する箇所はありません。
- **メモリセグメント：** `mBuildMonitorSnapshot`（`fAdd`）、`aMonitorSegments`、`MonitorSegmentKey` にキーを追加し、`aMonitorSegmentGroups` のいずれかのグループに配置して（8 つのカテゴリ色はすべて使用中なので、9 色目を追加せずに既存のグループにまとめます）、MANUAL のセグメントの表と `fRouteDescription` に記載します。
- **シェルツール：** `server_shell_mcp::mStart` の `lCandidates` に候補（ツール名、タイトル、実行ファイル名、コマンドの前に置く引数）を追加します。検出、`tools/list`、`tools/call`、ログは、それ以上の変更なしにその候補を扱います。チャットが stdin、stdout、stderr のボックスで表示するように `aShellMcpToolNames` にツール名を追加し、`fRouteDescription` のルートの説明、`--local-shell-mcp-server` のヘルプ、`expandLocalShellCommands` のヘルプテキスト、MANUAL を更新します。
- **インターフェースが保持する設定：** 単純な設定は `settings-registry.ts` に追加すれば、`config` セクションとともに保存されます。新しいセクションには、`UiSettingsDocument` のフィールド、それを所有するストアで `cUiSettingsStore.mRegister` により登録するローダー、そして変更のたびに呼ぶ `cUiSettingsStore.mSet` が必要です。`server-api-doc.cpp` の `/ui/settings` の説明にも記載してください。設定を `localStorage` に保持してはいけません。
- **別のクライアント向けのキュー通知：** `mgs_queue` イベントを受け取りたいクライアントは、`"stream": true` とともに `"mgs_client": "webui"` を送ります。別の発信元の値を加えるには、`task_params` のフィールド、`fMakeMgsCmplSchema` の `mgs_client` フィールドでのその処理、`mCountRunning`、`mDeferTask`、`mNotifyQueuePositions`、`server_task_result_queue` における専用のカウンター、そして `fQueueStatusText` と 15 のカタログでの翻訳済みのテキストが必要です。
