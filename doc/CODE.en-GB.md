## Architecture and decisions

**MoE model loading and MTP priority.** The engine compiles an explicit source list in `backend/src/CMakeLists.txt`. Dense-only decoder implementations are removed. Shared graphs belong to the MoE implementations that use them (including Nemotron-3, Qwen3.6, Qwen3.8, GLM-5.3-Flash and Kimi-K3); dense blocks inside a MoE model remain necessary. `mgs` stops at startup when it is given a dense model: before `--fit`, the HTTP listeners or any weight, `mgs_server` asks `mgs_model_file_is_moe` (which reads only the GGUF header, with the DeepSeek-V4.1 key translation and the KV overrides of the loader) about `--model` and `--spec-draft-model`, logs that mgs only loads MoE models and exits with status 1. In router mode the check runs in the child of that model, so the child exits and the router marks the model as failed. `mgs_model_create` applies the same rule (`fMgsModelIsMoe`) to every load through the API and rejects dense models before their weights; it reads the counts under the architecture name of the file, so a dense model of an architecture that mgs no longer has is reported as dense rather than as unknown. A head-only GGUF explicitly loaded as MTP is the exception: a dense prediction head can serve a MoE target, but never as `--model`. Qwen35 retains only its MTP graph. Version 0.1.19 also removed what no MoE architecture reaches: 85 `llm_arch` entries that could no longer load, with their tensors, KV keys and `llm_type` size labels, the dense branches (without experts) of the MoE graphs that had them (Mistral 3, MiniCPM, Granite MoE and Granite hybrid), the T5 infrastructure (cross-attention and relative positions), RWKV, the Qwen3 reranker, ModernBert, the DFlash, DSpark and Eagle3 draft architectures (with their `--spec-type` values and the layer-input extraction they needed) and the Gemma 3 projectors of `mtmd`.

MTP placement considers every selected GPU, accounts for backend allocation sizes and alignment, and includes the output head (or its tied token embedding). It first looks for a GPU that can hold all heads; otherwise it places the largest groups across GPUs. A group falls back to RAM only when no selected GPU can hold it. The separate `dMtpContexts` are allocated and uploaded before trunk contexts; tensor overrides cannot replace that placement. External MTP weights are preloaded before the target, including with `--fit off`, and transferred into speculative initialisation without loading a second copy. The fit estimate reserves their context/compute memory without counting their already allocated weights twice.

**Source conventions and CLI validation.** Project identifiers use CamelCase with the function, method, parameter and value prefixes specified by the project rules. Public C APIs, GGUF names, protocol fields, third-party names and framework-required callback/component names retain their contracts. C++ formatting uses two spaces. `backend/ggml` is project code too (C, C++, CUDA and the Vulkan GLSL shaders of the remaining backends): it uses two spaces and the same prefixes (static functions such as `fGgml…`, methods `m…`, fields and locals `v…`, `c…`, `l…`, `a…`, `d…` or `s…`, parameters `p…`), except the names of its public C API in `backend/ggml/include/` (`ggml.h`, `ggml-backend.h`, `gguf.h`…), which are a contract like `mgs.h`. The naming also covers the preprocessor branches that no Linux build compiles (Windows, macOS, debug macros, `MGS_LLGUIDANCE`, `#if 0`): the compiler cannot catch an old name there, so any rename must be checked in those branches by hand. `--chat-template-kwargs` rejects `vEnableThinking`; use `--reasoning on` or `--reasoning off`. Option spellings with underscores are not rewritten, and repeated options are rejected except for the explicitly repeatable `--spec-type`. `Github-Repo-Push.sh` uses `set -euo pipefail`, `fCleanup`, its EXIT trap and an explicitly checked `fMain`; every failed publication step stops the script.

`frontend/` contains the UI; `backend/` the engine, server and dependencies;
`deploy/` installers, services and asset scripts; `build/` the local
self-contained build script and its relocatable launcher; `doc/` documentation; `_/` local working material. Imported dependencies are preserved.

The Svelte interface lives in `frontend/`, the C++ engine/server in `backend/`, and installation in `deploy/`. The engine retains the relative relationships between `src/`, `common/`, `include/`, `ggml/`, `vendor/` and `tools/`. The CMake entry point in `build/CMakeLists.txt` delegates to the backend; the UI library is built from `frontend/` and embedded in the executable. The CMake targets are `mgs-engine` (the engine library, `backend/src/`), `mgs-common-base` and `mgs-common` (`backend/common/`), `mtmd`, `server-context` and `mgs-server-impl` (`backend/tools/`), `mgs-ui` (the embedded interface) and the executable target `mgs`; both build output and installation use `mgs`.

**Naming.** The code inherited from llama.cpp uses the project's own names: the public C API of `backend/include/mgs.h` and `mgs-cpp.h` uses the `mgs_` and `MGS_` prefixes, the engine sources are `backend/src/mgs*.{h,cpp}`, the server entry function is `mgs_server`, environment variables are `MGS_*` (`MGS_ARG_*`, each named after the long name of its option, `MGS_MODEL_ENDPOINT`, the `MGS_MOE_CACHE_*` diagnostics, `MGS_MTMD_*`, `MGS_SERVER_*`), CMake options are `MGS_*` (`MGS_MTMD_VIDEO` among them), the Prometheus metrics are `mgs:*`, the CORS proxy header prefix is `x-mgs-proxy-header-`, the browser storage uses `MgsUi`, the download cache is `~/.cache/mgs/` and the tinyBLAS CPU kernels are `GGML_TINYBLAS` in `ggml-cpu/tinyblas/`. The remaining `llama` spellings are deliberate: the llama.cpp licence notices (`LICENSE`, `build/licenses/LICENSE-llama.cpp`) and the README tagline; mentions of the upstream project as such (provenance, comparisons), without links to its repository; values stored inside GGUF files (the SentencePiece tokeniser model `llama` and the `llama-bpe` and `llama4` pre-tokenisers, with their `cMgsVocabPreTypeLlama3`/`LLAMA4` identifiers and `fUnicodeRegexSplitCustomLlama3`); names of third-party models and code in comments (CodeLlama, the Ultravox model and the `LlamaYaRNScaledRotaryEmbedding.py` YaRN reference implementation); a bibliographic reference in the tinyBLAS sources; and Spanish words such as «llamada». The `APIR_LLAMA_CPP_*` variables left with the virtgpu backend. Meta's Llama architectures (`llama`, `llama4`, `llama-embed`), their built-in chat templates and the Llama 4 vision projector were removed.

HTTP registration applies the API prefix to each published route. Handlers receive canonical paths without the prefix; the router adds `/api` when forwarding to model children. Public authentication allowlists use complete external paths. The UI stays at `/`; `/api/config.js` publishes the prefix before application modules load. Swagger and OpenAPI live under `/api/doc/`, including during model loading. The route/method registry supplies the live inventory; completion parameters come from `server-schema`. The OpenAI-compatible routes are registered only under `/v1` and the health check only as `/health`: the aliases without `/v1` (`GET /models`, `/chat/completions`, `/responses`, `/audio/transcriptions` and their `input_tokens` routes) and `/v1/health` were removed, while `/rerank` and `/v1/rerank` (TEI/Jina) and the native handlers (`/completions`, `/embeddings`…) stay. The public allowlist (`sGetPublicEndpoints`) holds `<prefix>/health`, `<prefix>/v1/models`, `/api/config.js`, the documentation and the UI assets.

JSON catalogues hold interface translations for 15 locales: `de-DE`, `en-GB`, `en-US`, `es-AR`, `es-ES`, `fr-FR`, `he-IL`, `hi-IN`, `it-IT`, `ja-JP`, `ko-KR`, `pt-BR`, `pt-PT`, `ru-RU` and `zh-CN`. `aLanguages` and `dCatalogs` register them in locale-code alphabetical order; `en-US` remains the default and message fallback. Each catalogue includes the localised names of all 15 languages. `fTranslate` interpolates named values without modifying conversation data. The new translations use count labels in deletion/import messages instead of interpolating English plural suffixes. Changing language saves it in the server's settings document and reloads the interface so labels calculated at module import also change; `/api/config.js` publishes the saved language before the modules load, and `?lang=` in the URL overrides it. The root layout sets the HTML language and direction (`rtl` only for Hebrew); navigation uses logical positioning, chat input and plain user text use `dir="auto"`, and code/terminal text stays left to right. Framework contracts, protocol fields and imported symbols retain their original names; project-owned functions follow the required naming prefixes.

**Documentation languages.** The README, MANUAL and CODE documents exist in the same 15 locales as the interface: `README.md` (en-US) is in the root and its translations are `doc/README.<locale>.md`; the manual and this guide are `doc/MANUAL.md` and `doc/CODE.md` (en-US) and `doc/MANUAL.<locale>.md` and `doc/CODE.<locale>.md`. Every variant opens with a language bar that links all the others in locale-code alphabetical order. Headings carry the same `<a id>` anchors in every language, so links between documents (such as `MANUAL.<locale>.md#local-build`) work in all of them. Code blocks, commands, paths, options and identifiers are identical in every translation; only the prose changes. The Hebrew variants are plain Markdown: GitHub and Gitea detect the direction of each paragraph, so the text reads right to left while code blocks stay left to right.

Installation requires root, handles command failures explicitly and stages only under `_/temp/`. The UI is built locally instead of downloading an upstream interface lacking project changes. Deployment is a single step: the installers (`install-common.sh:fMain`) validate the web options with `configure-web.sh --check` before compiling, build with the chosen backend (`--cuda`, the Debian default; `--rocm`; `--vulkan`; `--cpu`, the Alpine default), install `PREFIX/bin/mgs` and then run `configure-web.sh --binary PREFIX/bin/mgs` with the web options (`--domain`, by default `hostname -f`, then `hostname`, then `uname -n`; `--certificate` and `--private-key`; `--proxy-ip`). `configure-web.sh` stays as the internal piece that reconfigures without rebuilding, and every run rewrites the whole web configuration from its options. It creates unprivileged inference and web services. The dedicated Apache instance searches HTTP ports from 11080 and HTTPS from 11443 on every startup; inference listens on no TCP port: the units start `mgs --http --host /opt/moe-gguf-server/_/temp/web/mgs.sock` and Apache forwards through that Unix socket (`ProxyPass / unix:…|http://localhost/`). With `--proxy-ip`, the template lines marked `@PROXY@` are kept: `mod_remoteip`, `RemoteIPHeader X-Forwarded-For` and `RemoteIPTrustedProxy` on HTTP, and `RemoteIPProxyProtocol On` on HTTPS with every other address in `RemoteIPProxyProtocolExceptions` (`fProxyExceptions` writes the complement of the proxy address as networks, both families, with no `/0`), so only the proxy must send the PROXY header and the logs record the real client (`%a`). No HAProxy is configured. The certificate that Apache serves lives in `/opt/moe-gguf-server/certificates/` (`fullchain.pem` and `privkey.pem`, owned by `moe-gguf-server`, key mode 600): supplied files are copied there, an existing pair is kept across reinstalls and a self-signed one is created only when there is none. `/root/webapp-credentials.txt` (mode 600) holds the service account and the API key, rewritten in place on every run. The program's configuration lives in `/opt/moe-gguf-server/.mgs/config/`, the `~/.mgs/config/` of the service account, owned by it with mode 0600: `api.key`, `web-domain`, `web-proxy-ip` (only with `--proxy-ip`) and `apache2.conf.in` (the Apache `ServerRoot`), written by `configure-web.sh`, and `ui-settings.json`, written by `mgs`; only the system integration (systemd or OpenRC units) stays under `/etc`. Conversations live in the browser; there is no backend user database.

The server itself enables HTTPS by default: `common_params` starts at 11443 and `server_http_context` binds the first free port, followed by HTTP from 11080. The second listener returns 308 to the selected HTTPS port, preserving host, path and query, with `Cache-Control: no-store`. `--port` fixes the main port (0 delegates to the OS); `--http-port` changes the HTTP search start. Only address-in-use conflicts advance the search; other errors stop startup. `server-tls.cpp` loads the supplied PEM pair or, without one, the self-signed identity of `~/.mgs/certificates/` (`fPersistentServerIdentity`): it reuses `fullchain.pem` and `privkey.pem` while they match and the certificate has not expired, and otherwise generates an ECDSA P-256 certificate (365 days, SANs for localhost, loopback, the configured host, the machine name and the addresses of its interfaces) and saves it through temporary files and renames (folder 0700, key 0600), so every run and every build serves the same certificate and browsers keep their trust exception. No external command is invoked; if the folder cannot be written, the run uses its identity from memory. Without OpenSSL support, HTTPS fails explicitly. `--http` selects deliberate plain HTTP, used by router children and by the deployed inference service on its Unix socket; Unix sockets and Vertex AI retain HTTP. A `--host` that ends in `.sock` listens on that Unix socket, and `fRemoveStaleUnixSocket` first deletes a socket file that no server answers (an orphan of a stopped run), never one that still accepts connections (startup then fails with `another server already listens on the Unix socket`). The destructor stops and joins both listeners. `mgs_server` logs a warning when it runs as root (`geteuid() == 0`) and keeps starting. These decisions live in C++, independently of installers and launchers.

`build/build-local.sh` covers manual use on a workstation: it needs no root, installs no packages or services and leaves nothing running. It copies a complete local source tree or downloads the GitHub `main` archive without Git when invoked through `curl | bash` or as a standalone script, builds the `mgs` target in `/tmp/moe-gguf-server-build.XXXXXXXX/` and installs a relocatable, self-contained copy under a prefix (default `~/.local`, only for the current user; `--prefix` changes it): `bin/mgs`, `lib/mgs/` and `share/doc/mgs/licenses/`. `lib/mgs/` holds the server binary, its transitive `ldd` closure, the glibc dynamic loader and the NSS modules that glibc opens with `dlopen`. The kernel only honours an absolute `PT_INTERP`, so `bin/mgs` is a static launcher (`build/mgs-launcher.c`) that reads `/proc/self/exe`, goes up from `bin/` to the prefix and executes `lib/mgs/<loader> lib/mgs/mgs` with the remaining arguments; nothing in the prefix depends on its absolute location. The server binary and bundled libraries carry `DT_RPATH` `$ORIGIN`, deliberately chosen because it outranks `LD_LIBRARY_PATH`. Since the server's process image is then the loader, the launcher exports `MGS_EXECUTABLE` and `fGetServerExecPath` returns it, so router children re-enter through the launcher. NVIDIA driver libraries (`libcuda`, `libnvidia-*`) are never bundled because they must match the kernel module. The backend is chosen with `--cuda` (default), `--rocm`, `--vulkan` or `--cpu`. With `--rocm`, `fDetectRocmTargets` reads the GPU targets with `amdgpu-arch` or `rocminfo` unless `--rocm-targets` gives them (`fWarnUnsupportedRocmTargets` warns about GCN targets up to Polaris, `gfx6xx`–`gfx8xx`), CMake gets `-DGGML_HIP=ON`, `CMAKE_HIP_COMPILER` (from `hipconfig -l` or `HIPCXX`) and `GPU_TARGETS`, the ROCm user-space libraries enter `lib/mgs/` through the same `ldd` closure as the CUDA ones, and `fBundleRocmKernels` copies the GPU kernel folders that rocBLAS and hipBLASLt load at run time (`rocblas/library`, `hipblaslt/library`, found beside those libraries) straight into the new `lib/mgs/` of the prefix, because they take gigabytes; the launcher (`fExportKernelFolders`) exports `ROCBLAS_TENSILE_LIBPATH` and `HIPBLASLT_TENSILE_LIBPATH` pointing to them when they exist, so only the amdgpu kernel driver comes from the system. A marker file inside `lib/mgs/` prevents replacing an installation that the script did not create.

Each local run uses a fresh private directory from `mktemp -d /tmp/moe-gguf-server-build.XXXXXXXX`. The downloaded archive, its member list, copied or extracted sources, CMake output, npm/Node/CUDA caches, scratch files, the log and the assembled `bundle/` stay there. Automatic compiler caching is disabled (`GGML_CCACHE=OFF`, `CCACHE_DISABLE=1`), so no cache server survives the build. Once the artefacts are ready, the script locks the prefix directory itself with `flock`, copies the finished files to temporary entries next to their final places, then renames them into place on the same filesystem. `fCleanup` waits for the log writer and removes the private workspace on success, failure and handled INT/TERM/HUP signals. No build files are written into the source tree or `/opt/`; the local builder has no `--build-dir` option.

The entry script path is captured with `${BASH_SOURCE[0]:-}` before calling `fMain`, so stdin execution also works with `set -u`. Options are parsed before source discovery; `--help` needs neither a source tree nor a source download. `fHasProjectSources` checks the build entry points, launcher, frontend manifests and licence directory. A complete local copy is staged with the existing exclusions. Otherwise, `fDownloadSources` requires existing curl/gzip, downloads over HTTPS with retries, validates the archive paths and extracts into the private `source/` directory before checking the required files. `fMain` runs with stdin redirected from `/dev/null`, so build tools cannot consume the piped script. Remote options use `bash -s --`; packages are never installed.


The Debian entry point is standalone: it detects a complete local checkout or downloads `main` from GitHub. Remote mode always uses `/opt/moe-gguf-server-source` (`cManagedSourceDirectory`, owned by root, mode 700), checks the source-origin marker and holds a lock across synchronisation and compilation. `rsync --checksum --no-times --delete` removes obsolete sources, preserves `_/` and gives changed files fresh timestamps. The helper runs in a separate Bash with stdin closed and without duplicating its parent log stream. The installers read no `MGS_*` build variables: directories, prefix, jobs and backend come only from their options, and `CUDACXX` and `HIPCXX` select the compilers. For CUDA, `fInstallNccl` installs the `libnccl2`/`libnccl-dev` pair built for the detected CUDA release, adding NVIDIA's repository with `cuda-keyring` (`cKeyringVersion`) only when it is missing; for ROCm, the installer checks with `ldd` that the installed binary finds every ROCm library.

No backward-compatibility layer is kept. Deprecated CLI aliases and removed-option tombstones, duplicate long option names (each option keeps one short and one long name), `MGS_ARG_NO_*` environment fallbacks and environment variables named after former options, legacy HTTP route aliases (`/completion`, `/embedding`, `/reranking`) and duplicate request fields (`thinking_budget_tokens`, `content` in the embedding routes), the `deepseek-legacy` reasoning format, the non-Jinja template engine (`--jinja`/`--no-jinja`, the built-in C++ templates of `mgs-chat.cpp` and `mgs_chat_apply_template`: every chat template goes through Jinja, and `chatml` names the built-in ChatML source), old CMake variable names, browser-data migrations and installer shims were removed, so each option, route, variable and stored value has a single current name. Because the project has never been deployed, the public mgs/GGML/mtmd C APIs keep no deprecated symbols either: only their current functions remain, and 0.1.19 also dropped those that only served encoder-decoder, embedding-only or dense models, the removed draft architectures or the KV cache shared between contexts (`mgs_get_logits`, `mgs_get_embeddings`, `mgs_encode`, `mgs_set_causal_attn`, `mgs_model_has_encoder`, `mgs_model_is_recurrent`, `mgs_get_ctx_other` and the `ctx_other` field, `mgs_set_embeddings_layer_inp`, `mtmd_image_tokens_get_n_tokens`…; the removed ones are listed in [MANUAL.en-GB.md](MANUAL.en-GB.md#removed-compatibility)). The exceptions are deliberate: loading GGUF files through fallbacks that current conversions or the most downloaded published GGUFs of the supported families still depend on, checked against their headers on Hugging Face (the Qwen3.6 recurrent layout derived from `full_attention_interval` and the built-in GLM-5.2 indexer layout for GLM-5.2/5.3 files without `attention.indexer.types`), toolchain and operating-system version guards, and interoperability with external protocols (OpenAI, Anthropic, TEI/Jina, GCP Vertex, MCP), kernels, drivers and browsers. Old-file shims were removed: Grok-1, MiniCPM, the unsplit `attn_kv_b` (non-MLA) path of Kimi-Linear, the `ssm_in` path of Qwen3-Next, missing `expert_gating_func`, `rope.scaling.finetuned` and `full_attention_interval` keys, the scalar SWA period of Cohere2-MoE, missing pre-tokenisers and Kimi-K2 merges, the `llama3`, `llama-v3`, `jina-es`, `jina-de` and `llada-moe` pre-tokeniser names, `rope.scale_linear`, early Gemma 2, GGUF versions 1 and 2, the old `tokenizer.ggml.prefix/suffix/middle_token_id` keys, and in `mtmd` the projectors of the old one-off scripts (`mlp`, `mlp_norm`, `ldp`, `ldpv2`, `resampler`, `adapter`, files without a projector type), the swapped FFN of old surgery conversions and the defaults for missing Kimi-K2.5 and Step3-VL keys. Whole architectures were also removed by decision of the user: Gemma 4 and every DeepSeek architecture older than V4.1 (see the supported families below). Version 0.1.38 also removed, by decision of the user, every other MoE architecture inherited from llama.cpp (see the supported families below).

Configure manually with `cmake -S build -B _/temp/cmake` from the project root. Build scripts stage `build/` alongside the sources and select `source/build` as the CMake source directory. Deploy scripts keep generated files under `_/temp/` and reset `CMakeCache.txt` and `CMakeFiles/` if a cached configuration points to another source directory. The local build always uses a fresh disposable workspace under `/tmp/`. The TLS library of cpp-httplib is chosen in `backend/vendor/cpp-httplib/CMakeLists.txt` from the options declared in `backend/CMakeLists.txt`: `MGS_BUILD_BORINGSSL` and `MGS_BUILD_LIBRESSL` (both off) download and build that library, and take precedence in that order over `MGS_OPENSSL` (on, the system OpenSSL); with none of them the server has no HTTPS.

**Version.** The project version is defined once, as `MGS_VERSION` in `backend/cmake/build-info.cmake` (starting at `0.1.0`), and every change to the project raises its patch number (0.1.1, 0.1.2, ...). The local build and the Debian installer configure the same CMake tree, so both produce the same version: CMake prints `mgs version: …`, `build-info.cpp` returns it from `mgs_version()`, and it also sets the file versions of the shared libraries (the soname stays `.so.0`), `mgs.pc`, `mgs-config.cmake` and the interface's `build.json`. The project does not use Git, so there is no build number or commit: `--version`, the `build_info` property of `/api/props`, the OpenAI `system_fingerprint`, the shell MCP `serverInfo.version`, the `info.version` of the generated OpenAPI document, the `clientInfo.version` that the server's MCP client sends and the download `User-Agent` (`mgs/0.1.57`) all report this version. The interface takes it only from `build.json` (no `UI_VERSION` and no `version` in `frontend/package.json`). `deploy/scripts/ui-assets.cmake` reads the version with `fResolveVersion`, and `fNpmBuildShouldSkip` rebuilds the interface (`fStageSources`, `fNpmBuild`, then `fEmitFiles`) when `build.json` holds another version, so a version change reaches a reused `_/temp/` build tree without touching the interface sources; a failed npm build stops the build instead of embedding outdated assets.

Formatting configuration is scoped to folders: `.clang-format` is present in `backend/`, `frontend/` and `build/`; `.editorconfig` is present in those folders plus `deploy/` and `tests/`. Licence notices in `build/licenses/` inherit `build/.editorconfig`. Keep equivalent settings in sync. Files in the project root and `doc/` require editor settings for UTF-8, LF and two-space indentation.

The `doc/` folder contains reading documentation. The Swagger page lives in `frontend/api.html` and CMake embeds it in the server. The backend generates `/api/doc/openapi.json` from registered routes on each request; there is no static `openapi.json` source file.

The fork retains llama.cpp's server, multimodal support and GGML backends, with
MoE optimisations for weights split between GPU memory and system RAM. Host
registration and expert prefetch derive from
the `fable5/host-register` and `fable5/prefetch-experts` branches of
thecodacus's fork.
The prefetch slots hold gate/up/down expert tensors and overlap their transfers
with computation. Automatic MTP (`fCommonMaybeEnableMtp`, `fDetectMtp`) checks
`nextn_predict_layers`, a supported MTP graph, the model trunk and all integrated
heads before selecting `draft-mtp`; the checks include every GGUF shard. A separate
MTP GGUF passed with `--spec-draft-model` is checked instead of `--model`, without
requiring a trunk, so it also turns `draft-mtp` on when no `--spec-type` was given;
`mgs_server` runs this before the MoE-only check, so that the draft is checked as an
MTP head. See the [manual](MANUAL.en-GB.md#performance) for tuning and limitations.

The integrated MTP does not pay off on every machine: each step verifies the drafted tokens with the whole model, which reads the experts of every token, so where most experts come from RAM or disk it generates more slowly than without drafting. When `fCommonMaybeEnableMtp` enables it automatically, the number of draft tokens is therefore measured on the machine (`backend/common/spec-tuning.cpp`). Without a saved result the draft limit becomes `cSpecTuningMaxDraft` (3) and `vTuneDraft` is set; the server creates a `common_spec_tuner`, which `mUpdateSlots` asks for the draft limit of every step (`mStep`): after 32 generated tokens of warm-up, 0 to 3 draft tokens take turns step by step, in an order that is reversed every other round, until each has generated 64 tokens, and only the time between two steps of the same task while no other slot works counts; a step that repeats a partly accepted draft keeps the turn. `mSaveSpecTuning` keeps the fastest, or 0 when drafting is not more than 5% faster than no draft (`cKeepMargin`), and writes it with the speeds to `~/.mgs/tuning/mtp.json` (`fSpecTuningSave`), under a key made of the version of mgs, the model file and its size, the GPUs with their memory and the system memory (`fSpecTuningKey`). At the next start `fCommonMaybeEnableMtp` reads it (`fSpecTuningLoad`): 0 leaves MTP out, so its weights take no device memory, and any other number becomes the draft limit. Without draft tokens the MTP context still processes every batch, and its weights and buffers keep device memory that the experts, the context and the micro-batch get when MTP is not loaded; the measurement sees neither, hence the margin. An explicit `--spec-draft-n-max` or an MTP GGUF passed with `--spec-draft-model` leaves the measurement out. In blocks of generated tokens the candidates did not share the same text and page cache: with 32-token blocks the first answer on a cold page cache gave 2 draft tokens 4.6 tokens/s on a Radeon 860M, which generates 7.2 with them, and with 8-token blocks Qwen3.8-Flash-Next on the RTX 4060 Ti gave them 1.85, where it generates 1.4 with them; hence the warm-up and the turns step by step. On the Radeon 860M, Qwen3.8-Flash-Next generated 5.12 / 7.09 / 7.34 / 6.97 tokens/s with 0 / 1 / 2 / 3 draft tokens and keeps 2; on the RTX 4060 Ti it generated 1.81 / 1.79 / 1.30 / 1.59, so it runs without MTP from the next start, with 23-24 tokens/s of prompt and 1.69-1.70 of generation instead of 12 and 1.4, while Qwen3.6-35B-A3B generated 26.38 / 33.92 / 36.21 / 35.41 there and keeps 2.

A prefetch slot takes the size that the buffer type of its device allocates for the largest host expert tensor (`ggml_backend_buft_get_alloc_size`), not its bytes: CUDA pads quantized tensors whose rows are not a multiple of 512 elements, because its products read past the last row, and zeroes that padding in weight buffers. Up to 0.1.31 the slots took only the bytes, so with Qwen3.8-Flash-Next, whose Q8_0 `ffn_down_exps` have 640-element rows and filled an 850 MiB slot exactly, the product read past the end of the slot and the server stopped with `an illegal memory access was encountered` (or `an internal operation failed` in the next cuBLAS call) whenever the GPU had room for at least two slots, such as with MTP on an RTX 4060 Ti; whether the read failed depended on what was mapped after the slot. After every transfer, `fClearPrefetchPadding` writes zeros over the padding on the prefetch stream, because a slot holds a different tensor every time and a smaller one leaves part of the previous one there, whose bytes can read as NaN scales. The slots also leave `--moe-cache-reserve` free on their device for the memory that the computation allocates on demand: a slot that would leave less is handled like an allocation the device refused (`ggml_backend_sched_set_prefetch_reserve`, which `mgs_context::mSchedReserve` sets every time it creates the scheduler), unless the MoE expert cache took its automatic size on that GPU, which already left room for the slots (`mgs_expert_cache::mPrefetchSetAside`). With Qwen3.8-Flash-Next on the RTX 4060 Ti, MTP of 2 tokens now processes the prompt at 12 tokens/s and generates at 1.31 tokens/s.

**MoE expert cache.** `backend/src/mgs-expert-cache.{h,cpp}` keeps the most recently used experts of
every layer whose experts stay in system memory in one device pool per GPU shared by the layers assigned to it (one SLRU per layer within each group of layers of the same GPU with identical per-expert tensor types and shapes). A slot holds every per-expert tensor of one
expert: weights, biases and per-expert scales, with separate or merged gate/up projections. For micro-batches
below the op-offload limit (32 tokens, `GGML_OP_OFFLOAD_MIN_BATCH`), `mBuildMoeFfn` builds the expert chain
twice: a device branch that reads the pool through slot identifiers and a CPU branch that reads the host
weights. A CPU partition operation (`mPartition`) runs first: it counts the hits, uploads a bandwidth-balanced
share of the misses (about m·B_upload/(B_upload+B_cpu), at least one) and queues the slot identifiers and the
uploads on the device stream before the device branch; the CPU branch then computes the remaining misses at the
same time. Experts handled by the other branch get identifier -1 on the CPU (the CPU `mul_mat_id`/`add_id`
kernels skip them and write zeros) and an empty slot on the device (position k uses empty slot k, so no slot
repeats within a token, as the CUDA MMQ helper requires), so the sum of both branches equals the regular
execution up to rounding. The scheduler only synchronises an input-free split with the previous split when that
split had copied inputs or its backend can access the current buffer type; this keeps the fix of upstream
#26040 and lets both branches overlap. The upload bandwidth is measured at creation with real experts and the
CPU bandwidth is estimated online from the CPU branch duration. Large micro-batches keep the expert prefetch:
`ggml_backend_sched_set_weight_upload` lets the cache copy its experts device-to-device into the prefetch slot
and upload only the others from host memory. The cache takes the device memory left after the context minus
`--moe-cache-reserve` and the prefetch slots. It is created by the first request after every context and
projector is loaded (the common warmup defers it), can be resized at run time (`mgs_set_expert_cache_size`,
`POST /api/expert-cache`) and reports its counters through `mgs_get_expert_cache_info` (with `pending` while the next
decode of a context that creates it, `mgs_context::mUsesExpertCache`, still has to create it or apply a requested
size), `/api/expert-cache`
and `/api/metrics`. Settings travel as parameters: `fCommonContextParamsToMgs` fills the `expert_cache_mib`
(-1 automatic, 0 off, N MiB, from `fCommonMoeCacheSize`) and `expert_cache_reserve_mib` (default 1024) fields of
`mgs_context_params` from `--moe-cache`, `--moe-cache-size` and `--moe-cache-reserve` (`common_params::vMoeCache`,
`vMoeCacheMib`, `vMoeCacheReserveMib`), and `mgs_expert_cache::mFCreate` receives them; only the diagnostic
variables (`MGS_MOE_CACHE_PROTECTED`, `MGS_MOE_CACHE_FILL_RATIO`, `MGS_MOE_CACHE_STATS`) remain. With the cache enabled and enough
RAM, `--fit` keeps every expert in system memory and leaves the free device memory to the cache, because an LRU
cache serves decoding better than whole static expert layers; with several GPUs it spreads the dense-only layers
over them by memory target, so every GPU caches the experts of its own layers. The upload bandwidth is measured
per GPU, a requested size is split among the GPUs by the host experts they cache, and the cache stays off with
pipeline parallelism, which keeps several micro-batches in flight. `--fit` also counts the nextn (MTP) layers, which
the loader numbers among the layers it offloads; otherwise the first layer stayed on the CPU when MTP was off.

**Per-layer segmented LRU (SLRU).** Every cached layer owns an equal share of the real slots of its group (`vSlotShare`) and keeps them in two least-recently-used lists linked through `lPrev` and `lNext`: an expert placed in a slot enters the head of the probation list of its layer (`mInsert`), a hit moves its slot to the head of the protected list (`mTouch`), and the protected list holds at most half of the slots of the layer and returns its oldest slot to the head of the probation list. `mFindVictim` takes the oldest slot of the layer that the partition does not use, from the probation list first and from the protected list only when the probation list has none, so an expert used once no longer evicts one in regular use and a burst of misses in some layers no longer empties the cache of the others. `MGS_MOE_CACHE_PROTECTED` sets the protected share (`0` gives a plain LRU per layer). Routing traces of Qwen3.6-35B-A3B Q8_0 recorded on the RTX 4060 Ti through CUDA and replayed with the real pool and upload quota (the simulated global LRU of earlier versions matched the real one in every partition) raised the hit rate from 72.2 to 74.1% with topic switches, from 70.2 to 71.3% on one long topic and from 61.3 to 65.1% with MTP. The global LRU collapsed when a step uploaded more experts than the pool could keep: with MTP, a quarter of the pool (a GPU with less VRAM) and every miss uploaded it kept 0.03% of hits, against 30.7% per layer; a global SLRU with 70% protected fell from 64.5 to 54.3% with MTP and every miss uploaded, and the frequency admission of colibri (`c/tier.h`, a 25% + 4 margin) lowered the hit rate to 68.6, 64.3 and 59.5%. Most of the gain of the per-layer SLRU comes from the order of the uploads: when the quota covers only part of the misses, `mPartition` uploads first the experts selected by more tokens and then those used most recently and often (`lHeat`, halved every 1024 tokens); with the router order, the per-layer SLRU alone reached only 72.7, 70.4 and 61.9%. Measured with 8 interleaved pairs on that machine (2625-token prompt, 256 generated tokens): the hit rate went from 72.3 to 74.1% and generation from 37.4 to 38.1 tokens/s (+2.0 ± 0.1%) with `--spec-type none`, and from 61.9 to 66.1% and from 45.2 to 47.1 tokens/s (+4.2 ± 1.2%) with MTP. With topic switches generation went from 37.3 to 37.9 tokens/s, and from 46.0 to 48.1 with MTP. With every miss uploaded (`MGS_MOE_CACHE_FILL_RATIO=1`) the output is byte-identical to the global LRU, also with `MGS_MOE_CACHE_PROTECTED=0`.

**Host memory budget.** `mgs_host_memory_available` (`backend/src/mgs.cpp`) returns the smaller of `MemAvailable` and what every level of the cgroup v2 of the process still allows (the lower of `memory.max` and `memory.high`, minus `memory.current` without the inactive file cache), and `mgs_host_memory_total` the smaller of `MemTotal` and the lowest of those limits. `--fit` takes the system memory from the first one, so a systemd service with `MemoryMax` or a container keeps the MoE experts in RAM only when they fit in its limit, and when they do, `common_init_result` lowers the prompt cache (`--cache-ram`, 8 GiB by default) to the memory left after the experts and the margin unless `--cache-ram` was given (`vCacheRamExplicit`). The loader pins only the tensors that stay in system memory (`lMmapsHostRanges`, merged across gaps of up to 16 MiB, one `mgs_mmap::mRegisterHost` call per range), and only while what stays available (`mgs_host_memory_available` minus the pinned bytes) keeps a margin of max(4 GiB, 10%); the ranges beyond that budget stay pageable and the log shows `pinning X of Y GiB of mapped weights`. With Qwen3.6-35B-A3B Q8_0 (33.85 GiB of mapped CPU weights) on the 46 GB machine with the RTX 4060 Ti, inside a 30 GB cgroup and with the GGUF out of the page cache, 0.1.17 kept the experts in RAM, hit the limit thousands of times while loading and was killed after 15 minutes; 0.1.18 placed whole expert layers on the GPU, skipped the pinning, loaded in 2.3 minutes and generated 27 tokens/s. Without a limit only the prompt cache changes (limited to 3.2 GiB there), and generation stayed at 36.5 and 36.6 tokens/s in four interleaved pairs. Up to 0.1.22 it pinned the whole span from the first to the last mapped CPU tensor and compared it with `mgs_host_memory_total`: with whole expert layers on the GPU, that span starts at the token embeddings (near the start of the file, kept on the CPU) and also covers every expert copied to the GPU, 33.85 GiB of that model whatever the number of GPU layers. On the RTX 4060 Ti machine, with 62 GiB of RAM, no swap and 26 GiB used by the desktop, it pinned that span with 35.6 GiB available, and the system stopped responding while loading until it had to be powered off. Before mapping, `mgs_model_loader::mInitMappings` compares the size of the model files with `mgs_host_memory_available`: when they are larger, it neither populates the mapping (`MAP_POPULATE`) nor advises `POSIX_MADV_WILLNEED`, because reading files that do not fit makes the pages read last evict the ones read first, so the load ends with only their tail cached after reading every byte from the disk and evicting the page cache of the other processes. The load then reads only what it copies to the devices or pins, and the rest is read when first used. With Qwen3.8-Flash-Next (113 GB) on the RTX 4060 Ti machine, inside a 40 GiB cgroup and with a SATA disk, the load went from 5 min 15 s to 1 min 31 s and the pinned weights from 16.45 to 23.81 GiB (the populated pages no longer fill the cgroup); on the Radeon 860M laptop (46 GB of RAM, NVMe) it went from about 60 s to 23 s, with the same or higher prompt and generation speed.

**Integrated GPUs (unified memory).** An integrated GPU (`GGML_BACKEND_DEVICE_TYPE_IGPU`: Vulkan `eIntegratedGpu`,
CUDA `prop.integrated`, as on Jetson or DGX Spark) has no memory of its own. With Vulkan,
`ggml_backend_vk_get_device_memory` adds up every heap of such a device, and CUDA reports `MemAvailable` from
`/proc/meminfo`, so what it calls device memory is part of the system RAM that the CPU buffers use too. Counting
both as separate pools let a model that did not fit in the device keep its experts in RAM and then fill the rest of
the device with an expert cache: a copy, in the same RAM, of experts that were already there, uploaded RAM to RAM
on every miss and able to push the mapped experts out of the page cache. `fDeviceIsUma` marks such a device, and
`fCommonParamsFitImpl` gives it and the CPU one budget: its usable free memory (`lDeviceFree`) is the smaller of
what the device reports and `MemAvailable` minus the CPU buffers of the initial measurement (every layer on the
device, the fewest any placement keeps in RAM). Moving a tensor between the device and the CPU does not change the
total, so the same budget serves step 1 (everything on the device with the training context), step 2 (reduced
context), the dense-only check and the per-device targets. When the model still does not fit, the placement with
every expert in RAM is skipped and whole expert layers fill the device (step 4, only whole expert layers on an integrated GPU), the CPU computing the rest. The MTP placement of `mgs_model_base::mLoadTensors` limits the free memory of an integrated GPU the same way, to what `mgs_host_memory_available` still allows.
`mgs_expert_cache::mFCreate` creates no pool on an integrated GPU either, also with explicit placement options
(`--cpu-moe`, `--n-cpu-moe`, `--override-tensor`), and counts those layers apart in its log. The loader uses at
most one integrated GPU and only without a discrete one, so the budget is not split further. A zero-copy path, in
which the integrated GPU reads the experts where they already are, is not implemented: the Vulkan device declares
`buffer_from_host_ptr = false` and accepts only its own buffer types. When the model is mapped (`--load-mode mmap`, the default), the CPU buffers of that budget leave out the mapped weights: with every layer on the device they are only the input tables that the graph gathers row by row (token and per-layer embeddings, 28 GB in Qwen3.8-Flash-Next), of which only the rows read stay in the page cache, which the kernel can reclaim. Counting them left that model 15-17 GB of a Radeon 860M with 46 GB of RAM and 3 expert layers; it now gets the 39.7 GB the device reports, whole expert layers fill it and generation goes from 4.4 to 4.9 tokens/s with 4096-token micro-batches. The scheduler does not prefetch whole expert tensors into slots on an integrated GPU either (`fInitializeExpertPrefetch`): filling a slot is a copy from RAM to RAM by the CPU, with no bus transfer to overlap, and the slots pin RAM that the page cache of the experts left in system memory needs; with the selective copy of the used experts, Qwen3.8-Flash-Next with 42 expert layers in RAM processes a 2625-token prompt at 33 instead of 15 tokens/s and then generates at 5.0 instead of 4.3 tokens/s. On an integrated GPU the CPU and the GPU also share the power budget of the package, and the OpenMP threads of the CPU backend, which spin while the GPU computes its part of every token, took that power from it: the Radeon 860M ran at 918 MHz with spinning threads and at 1720 MHz with sleeping ones, both at 14.6 W. libgomp reads `OMP_WAIT_POLICY` only when it is loaded, so `fWaitPassivelyOnIntegratedGpu` (at server start, not in router mode) restarts the process once with `OMP_WAIT_POLICY=passive` when the only GPU is integrated and the variable is not set; with Qwen3.8-Flash-Next generation goes from 5.25 to 5.5 tokens/s. When the launcher of the local bundle sets `MGS_EXECUTABLE`, the restart executes it, as the router does for its children: there the process image is the bundled loader, and executing `/proc/self/exe` would make the loader read the arguments of `mgs` as its own options (`unrecognized option '--model'`).

**Context size with `--fit`.** Step 2 of `fCommonParamsFitImpl` reduces a context that the user did not set as
if every weight had to fit in device memory, so a model larger than the devices always fell to `--fit-ctx`
(4096 tokens) even though its experts then stay in system memory, and reasoning answers were cut off. Once the dense weights fit, `fRaiseContext` measures the dense-only placement at
the reduced and at the training context, interpolates linearly and raises the context (rounded down to 256 and
checked with one more measurement) until the KV cache and the buffers that grow with it take at most a quarter
(`pContextShare`) of the device memory left after the dense weights. It runs after the placement with every
expert in RAM (expert cache) is chosen and before whole expert layers fill the devices, so the experts always
keep at least three quarters of that memory. An explicit `--ctx-size` is never changed, `--fit-ctx` stays the
minimum, and nothing changes when the KV cache lives in system memory. The draft context takes the context size of
the target (`vParamsDft.n_ctx = n_ctx` in `mLoadModel`): with a context size of 0 it used to allocate its KV
cache for the training context of the model, which took device memory from the expert cache. A placement given
explicitly (`-ngl`, `--tensor-split`, `-ot`, `--cpu-moe` or `--n-cpu-moe`) used to make `--fit` abort; now
`fCommonParamsFitImpl` keeps it as given: step 2 has already fitted an unset context to the first measurement,
which used that placement, and `fRaiseMicroBatch` fits the micro-batch around it unless `-b`/`-ub` were given. When whole expert layers fill the devices because the experts do not stay in RAM for an expert cache (always on an integrated GPU), the share is a sixteenth (`fRaiseContext(..., 16)`): every expert layer left out of the devices is then read from system memory, or from the disk when the model is larger than the RAM, on every token. Qwen3.8-Flash-Next (113 GB) on a Radeon 860M with 46 GB of RAM got 137216 tokens, whose KV cache and QSA masks took 10 GB of the 39.7 GB, and generated 4.9 tokens/s; with a sixteenth it gets 37376 tokens and generates 5.3 tokens/s.

The draft or MTP context is created after the target with the context size of the target, so when that size is left to `--fit`, `mLoadModel` measures the draft context twice before the fit, with `--fit-ctx` tokens and with the training context: what does not grow with the context goes into the device margins (`lFitParamsTarget`) and the growth per token into `common_params::lFitParamsTargetPerCtx`, which `fCommonParamsFitImpl` adds to every measurement for the context size that it measures (`fGetDeviceMemoryData`), so that reducing or raising the context accounts for it. Up to 0.1.32 it was measured only with the training context: on an RTX 4060 Ti the MTP context of Qwen3.8-Flash-Next counted as 1300 MiB (262144 tokens), where the 6912-token context that the fit chose used 158 MiB. With Qwen3.8-Flash-Next and MTP of 2 tokens on the RTX 4060 Ti, the fit now counts 130 MiB plus 4.57 KiB per context token for the MTP context and gives the model a context of 7936 tokens instead of 6912.

**Automatic configuration.** `mgs --model FILE` has to pick the fastest settings for the machine by itself;
explicit options always prevail. With experts in system memory, every micro-batch of a prompt streams the experts
that are not on the device over PCIe (about 2 s per micro-batch for Qwen3.6-35B-A3B Q8_0 on an RTX 4060 Ti), so
prompt speed grows almost linearly with the micro-batch while generation does not depend on it: a 2514-token prompt
went from 215 tokens/s with 512 to 408 with 2048 and 737–755 with 4096, with the same generation speed. Before the
context is raised, `fRaiseBatch` (through `fRaiseMicroBatch`) tries micro-batches of 4096, 2048 and 1024 tokens at the chosen placement and keeps
the largest whose extra memory stays within an eighth (`cBatchShare`) of the device memory left after the dense
weights; the logical batch grows with it. It only runs when `-b`/`-ub` (or their variables) were not given
(`common_params::vBatchExplicit`, passed as `pAutoBatch`). `common_init_result` copies the resulting `n_batch` back
into the parameters, because the draft and MTP contexts copy them and take every target batch into a buffer of
their own `n_batch`; their micro-batch keeps its default. The default CPU thread count (`fCommonDefaultThreads`,
applied by `fPostprocessCpuParams` when `-t` is absent) is the number of cores useful for maths, capped at half of
the logical CPUs of the process affinity mask: the CPU share of MoE inference is bound by memory bandwidth, and
using every logical CPU of a virtual machine without visible SMT made the workers compete with the thread that
drives the GPU (16 vCPUs: 4 to 12 threads within noise of each other, 16 threads 13% slower). A CPU of up to
`cFewCpus` (8) logical CPUs without SMT uses all its cores instead, because with so few cores the CPU limits
generation (4 cores of an i7-7700K computing 40 of the 41 expert layers next to an RX 580: 4 threads 17% faster
than 2). With visible SMT the
cap equals the physical cores, so bare-metal machines keep the previous default. `common_init_result` logs the
thread counts; `--fit` logs the micro-batch and context it chose.

Whole expert layers fill the devices one tensor at a time (step 4 of `fCommonParamsFitImpl`), so what they leave below the target is less than the next expert tensor and nothing else uses it: on its own it is too small for the expert cache next to the prefetch slots. After step 4, `fRaiseMicroBatch` therefore runs once more with `pUnusedMemory`, whose budget is all the memory left below the target instead of an eighth, so a larger micro-batch takes that memory without moving any expert off the devices. With Qwen3.8-Flash-Next and MTP on an RTX 4060 Ti the eighth keeps 2048 tokens, and the micro-batch of 4096 tokens needs 551 MiB more at the final placement: with the default margin of 1 GiB only 378 MiB were left below the target and nothing changed, while with `--fit-target 800` 665 MiB were left and the fit took 4096 tokens with the same experts on the GPU. In that run the prompt was processed at 21-22 tokens/s instead of 12, with generation at 1.41-1.46 tokens/s (1.39 before).

**MTP placement.** MTP weights live in device memory ahead of every other placement rule: the nextn layers
grafted onto a model, every layer of an MTP-only GGUF passed with `--spec-draft-model`.
`mgs_model_base::mLoadTensors` assigns their layers and the output layer to a GPU even when `n_gpu_layers`
leaves them on the CPU, and `mgs_model_loader::mCreateTensor` ignores the overrides that send them to host
memory (`--fit` partial layers, `--cpu-moe`, `--n-cpu-moe`, `--override-tensor` and their `--spec-draft-*`
equivalents). The token embeddings stay on the CPU like those of the trunk, because a row lookup gains nothing on
the GPU. There is no extra margin: all the MTP groups (every nextn layer and the output group) go to the preferred GPU
when they fit in its free memory, otherwise each group goes to the GPU where it fits best, and a group that fits on no
GPU stays in system memory with the warning `no selected GPU has enough free memory for MTP layer N; using system
memory`. Each placement logs `MTP layer N assigned to <device> (… MiB)`. The buffer list of every MTP group
(`dMtpBufferLists`) is the device buffer type followed by the CPU ones, so only a tensor that the device cannot hold
falls back to the CPU and the load never fails on it. `--fit` measures by loading the model without allocating it, so it sees the MTP weights on the
device and fits the rest around them; the expert cache takes what remains. With a separate MTP GGUF,
`fCommonModelParamsToMgs` leaves the MTP layers grafted onto the target unloaded instead of keeping an unused
copy.

**Kimi-K3 (`models/kimi-k3.cpp`).** KDA linear-attention layers (full-rank gate `ssm_g` with a bounded-sigmoid decay, the shared `fBuildGdnL2Norm` and the per-channel gate of `mBuildRecurrentAttn`) alternate with MLA layers in the absorbed `k_b`/`v_b` form with a sigmoid output gate. A cross-layer residual mix built with `ggml_dsv4_hc_pre` reads `attn_res_score`, `ffn_res_score` and `output_res_score`. The MoE is latent: the router works at full width and the 896 experts at the latent width (`ffn_routed_down` → experts → `ffn_routed_norm` → `ffn_routed_up`), with the `situ` activation (`cLlmFfnSitu`) handled in `mBuildMoeFfn`; `MGS_MAX_EXPERTS` is 1024 for it. The recurrent state supports rollback (`n_rs_seq`). Published GGUFs carry no MTP. The chat template uses `<|open|>`/`<|sep|>`/`<|close|>` and is parsed by `fCommonChatParamsInitKimiK3`; the tokeniser keeps the `kimi-k2` pre-tokeniser.

**GLM-5.3-Flash (`models/glm5-next.cpp`) and `glm5v`.** KDA layers and nope-only MLA layers with the k-pool DSA indexer (tensors `blk.N.indexer_compressor_gate` and `blk.N.indexer_compressor_ape`), hyper-connection streams with the fused hc ops and a DeepSeek-style MoE with `ggml_swiglu_clamp`, a new op (CPU, CUDA and Vulkan) that keeps the CUDA mat-vec + GLU fusion during decoding. The NextN block is a DSA layer: MTP turns on with only `--model` and its weights take the VRAM-first placement. Memory is `mgs_memory_hybrid_idx`. The `glm5v` projector reuses the glm4v graph with an optional post-conv norm, a clamped SwiGLU, its own preprocessor and `<|begin_of_image|>`/`<|end_of_image|>` markers. The `glm4` and `glm5` pre-tokenisers use ChatGLM4 with ignored merges (`vIgnoreMerges`).

**Qwen3.8-Flash-Next (`models/qwen4exp.cpp`).** A low-rank hyper-connection mixer and combine (`ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_post` with identity mixing), n-gram hashed per-layer embeddings whose table `per_layer_token_embd` (about 29 GB) stays mapped and is read on demand with row prefetch, a dilated conv history in the recurrent cache (`cache_ple_r_l`), gated delta-net layers with rollback, QSA block-sparse attention layers (k-pool indexer cache, `ggml_lightning_indexer` scoring, a top-k selection mask on top of the KQ mask, computed with dense flash attention because the upstream sparse kernels are not ported), MoE with a gated shared expert, IMROPE and an MTP block with its own hyper-connection mixer and draft memory. `mgs_memory_hybrid_idx` (`mgs-memory-hybrid-idx.{h,cpp}`) combines the KV cache, the recurrent cache and the k-pool indexer cache for qwen4exp and glm5-next; KV cells record the token id (`vTok`) for the n-gram lookups and `seq_pos` is a set of (position, cell).

**DeepSeek-V4.1-Flash (`models/deepseek41.cpp`, `mgs-kv-cache-dsv41.{h,cpp}`).** Two published layouts declare this architecture: antirez's DwarfStar files (keys taken from the Hugging Face configuration such as `deepseek41.hidden_size`, a `deepseek41.config` JSON string and an I8 Engram table of E4M3 values with E8M0 scales, 264 bytes per row) and the files of the llama.cpp ecosystem (standard keys, Engram table in a ggml type). `fMgsDeepseek41AdaptMetadata` translates the first layout into the standard keys before the model is created (scoring function → gating enum, scalar `swiglu_limit` → per-layer arrays, 40 or 43 compression ratios, Engram offsets as the running sum of primes), and the loader accepts both names of the Engram projections. Layer roles (KV source, index-key owner, top-k source) come from the tensors present. The Engram table (about 188 GiB) is created with `cTensorExternal`: it is counted but never allocated, prefetching stops before it, and the rows of every token are read with `pread` on a private descriptor (`mEngramReadRows`, decoding E4M3+E8M0 or dequantizing with `to_float`). The cache keeps one group per compression ratio (gated pooling for ratio 2, a full-length stream for ratio 1 from layer 20), index-key caches only on the key owners, and reader layers that address their source layer's storage; Engram takes the previous tokens from the raw cache cells. The graph uses lagged hyper-connection mixes (a one-hot first copy, a final collapse with the last FFN mix, no HC head), no q head norm, index keys from the latent before RoPE, top-k reuse and the two-level candidate-block pool, Engram before layers 1 and 14, and `ggml_swiglu_clamp` in the routed and shared experts. When the GGUF has no chat template, `DEEPSEEK41_TEMPLATE_SRC` (a Jinja source) is used; DSML tags carry a leading space and the server passes `reasoning_effort` (1–100) to the template. There is no MTP and no vision. The `dsv4_*` and `lightning_indexer` ggml ops and the `vDsv4HcMult`/`aDsv4CompressRatios` hparams stay because Kimi-K3, GLM-5.3-Flash and Qwen3.8 use them; on Vulkan those ops run on the CPU.

**Flint (`models/flint.cpp`).** Supported in addition to the required families. Two leading dense layers, then MoE layers with sigmoid routing (normalised weights) and always-active shared experts. Only the sliding-window layers use RoPE: `attention.rope_pattern` fills `aRopePattern` (1 for every layer of the other models), `mgs_hparams::mHasRope` tells the graph which layers to rotate and the K-shift (`mBuildGraphShift`) skips the others, and `freq_base_swa` takes the frequency of the model so that both use the same one. Every layer has attention sinks and Q/K norms. The `flint` pre-tokeniser (`cMgsVocabPreTypeFlint`) has its own regex, `<|user|>` and `<|observation|>` end the generation, the chat template needs the `\xHH` escapes of the Jinja lexer and its tool calls (`<tool_call>name<arg_key>…</arg_key><arg_value>…</arg_value></tool_call>`) go through the automatic parser. The input of the expert down projection can exceed the F16 range that several kernels use for it (F16 activations, F16 sums of the Q8_1 blocks), so `mBuildMoeFfn` divides every [expert, token] row by the power of two that keeps it within ±1024 with `ggml_amax_pow2`, a single op with CPU, CUDA and Vulkan kernels that take the same exact factor from the exponent bits (1 when the row already fits), and multiplies the factor into the expert weights before the projection, so the down projection and the weighting stay adjacent and keep their fusion; with a down bias, and in each branch of the hybrid execution, the branch multiplies its own output. Upstream builds the same factor from nine generic ops (`abs`, `pool_1d`, `log`, `ceil`, `clamp`, `exp`…), and the CUDA backend of this fork has no `POOL_1D`. `-sm tensor` is denied because the factor needs the whole row. On Vulkan the factor, the MUL of the weights and the DIV of the rows run as one dispatch (`AMAX_POW2_MUL_DIV`, or `AMAX_POW2_DIV` in the hybrid branches) whose result is bit-identical to the three ops, and the routing of sigmoid layers without a selection bias is fused into `TOPK_MOE` (`TOPK_MOE_SIGMOID_NORM`), as CUDA already did.

**Context checkpoints.** Models whose memory cannot be rolled back (recurrent or SWA layers) restore from
checkpoints. They are created at the start of a batch that starts a user, assistant or tool message (the
boundaries where agents edit the context), near the end of the prompt, and at any batch once the previous
checkpoint is `--checkpoint-min-step` tokens behind (default 1024). That last case also skips a batch less than `--checkpoint-min-step` tokens before the first checkpoint near the end of the prompt (`4 + n_ubatch` tokens before the end), which covers the same edits, because every checkpoint waits for the device and copies the recurrent state. A message boundary only cuts a batch whose
last micro-batch is at least 3/4 full, because every extra micro-batch streams the offloaded experts again.
When `--ctx-checkpoints` is reached, the checkpoint with the closest neighbours is removed, so the remaining
ones stay spread over the context.

**Monitor and status bar.** `GET /api/monitor` reports CPU usage (global, per physical processor and per logical CPU, from `/proc/stat` deltas; each logical CPU is matched by number and grouped by the `physical_package_id` of sysfs, and each processor takes its model from its blocks of `/proc/cpuinfo`), RAM (`/proc/meminfo`) and every GPU (NVML through `dlopen("libnvidia-ml.so.1")`, then every DRM card of a GPU driver that NVML did not list: amdgpu with its `gpu_busy_percent` and VRAM from sysfs, and i915, xe, nouveau or nvidia without usage, completed with the name and memory of their backend once a model uses them; display-only adapters are left out, and the UI draws no VRAM bar for a GPU without memory figures), plus the memory of the loaded models split by purpose. The memory never goes through the task queue: every posted task resets `vTimeLastTask`, so a page polling every two seconds would keep the model awake forever, and `mCreateResponse` waits for a sleeping model to wake up. Instead the main loop publishes a snapshot (`mRefreshMonitorSnapshot`) after `mLoadModel`, at most once per second while slots work and always once they are idle (the end of a request saves its prompt); the HTTP threads only copy it under a mutex, and entering sleep publishes `{"state": "sleeping"}`. The snapshot combines `mgs_get_memory_breakdown` (model, context and compute per buffer type) with `mgs_model_get_weight_breakdown` (MTP and routed-expert weights, computed once after loading because it walks every tensor) and `mgs_get_expert_memory_breakdown` (expert cache buffers and the prefetch slots of the scheduler, which the regular breakdown does not see). An MTP context on the target model shares its weights, so only its KV cache and compute buffers count; a separate MTP GGUF counts as MTP weights and any other draft model as draft weights. Host buffer types (pinned host memory of a GPU included) go to the RAM bar and device ones to their GPU, matched with NVML by PCI bus id (lower case, without the `-vN` suffix of CUDA virtual devices). `fMonitorReport` adds "other" (used memory that no segment explains: other processes, driver contexts, the projector) and the free remainder. The router parent never initialises a GPU backend, which would create a CUDA context of its own: it reads the GPUs through NVML and asks every ready child for `/api/monitor/memory` (1 s timeout), while loading and sleeping children only report their state. `GET /api/monitor/usage` (only the usage: global CPU, every physical processor without its logical CPUs, and every GPU) is also allowed while the model loads. CPU and GPU readings are shared for 750 ms by concurrent pollers; a CPU baseline older than 10 s is replaced by a fresh 250 ms interval. In the UI, `cMonitorStore` polls only while something is subscribed and pauses while the tab is hidden; the status bar reuses the report while the Monitor page is open. The page only draws usage and memory: the per-model entries of the report (state, resident memory, expert cache, MTP draft tokens) are read by the Model page and stay in the API for other clients. The usage cards use a six-column grid on wide screens (`fUsageCardSpan`): two per row, and three in the last row when their number is odd. Its cards are titled with the device label in bold (`gpu-N` and `cpu-N`, in report order, one card per GPU and per physical processor) followed by the device name; every processor card shows the system load average, and every usage meter (`MonitorMeter`, the per-core bars and the status bar) is a green bar (`--monitor-meter-free`) filled in red by the usage (`--monitor-meter-used`), apart from the categorical palette of the memory bars. The status bar is fixed at the bottom: `.has-status-bar` sets `--status-bar-height`, which the chat form, the sidebar, sticky footers and the `body` padding add, so every offset stays as before when the bar is hidden (Settings → Display). The memory bars use the eight validated categorical colours plus a neutral "other" in a fixed order (`aMonitorSegmentGroups`), so related server segments share a colour (MTP and draft weights, expert cache and prefetch). The reasoning menu sizes its entries by their content (`w-max`, names with `whitespace-nowrap`): with the global `min-width: 0` and `overflow-wrap: anywhere`, a `flex-1` name next to a hint used to be split letter by letter.

**Vulkan backend.** `build/build-local.sh --vulkan` and the Debian installer (`--vulkan`) configure `-DGGML_VULKAN=ON` with CUDA off; the shaders are compiled with `glslc` at build time and CMake needs the Vulkan and SPIR-V headers (`libvulkan-dev`, `spirv-headers`). The installer adds those packages plus `mesa-vulkan-drivers`; the local build only checks for `glslc` and turns a failed configuration into a hint naming the packages. The local bundle copies the Vulkan loader `libvulkan.so.1` through the regular `ldd` closure, while the driver (ICD) is opened by the loader from `/usr/share/vulkan/icd.d/` and loads its own system libraries (RADV pulls in LLVM, libdrm and X/Wayland client libraries); sonames already in `lib/mgs/` are shared, which is why the bundle must be built on the Debian release that runs it. The Vulkan device reports caps `async` and `events`, so the expert prefetch and the expert cache run unchanged, and its `device_id` is the PCI bus id, so the Monitor matches it with NVML or with the amdgpu sysfs card (whose generic name is then replaced by the backend description). Vulkan does not export `ggml_backend_register_host_buffer`, so mapped expert pages stay pageable: measured on an RTX 4060 Ti through Vulkan (Qwen3.6-35B-A3B Q4_K) before the staging ring described next, expert uploads reached 2.7 GB/s with mmap and 13.1 GB/s with `--load-mode none` (pinned host buffers), and generation 27.5 and 36.6 tokens/s; the loader now says that no backend can pin mapped memory instead of blaming CUDA. Uploads from pageable memory (the expert-cache fills and the expert prefetch of large micro-batches) used to copy through one staging buffer and wait for the device after every call (`fGgmlVkSynchronize`), so the partition stopped at every fill and the prefetch did not overlap. They now go through a 64 MiB host-visible staging ring per backend (`fVkStagingWrite` in `ggml-vulkan.cpp`): the data is copied into the ring at once, in pieces of up to 16 MiB, and the device copy is recorded in the open context. Every submission that carries ring copies signals a timeline semaphore of the backend, the open context is sent as soon as it carries half of the ring, and the space of a copy (with its command buffer) is reused once the semaphore has reached its value, after sending the context first when the copy has not reached the queue yet (`vSubmitCount`, counted by `fGgmlVkSubmit`). Measured on the RTX 4060 Ti with Qwen3.6-35B-A3B Q8_0 (2625-token prompt, 256 generated tokens, `--spec-type none`, three runs each): prompt 455 → 515 tokens/s and generation 20.6 → 23.2 tokens/s; with every miss uploaded (`MGS_MOE_CACHE_FILL_RATIO=1`) the output is byte-identical to the old path, also with the transfer queue. `GGML_VK_STAGING_RING=0` restores the old path for diagnostics. When the input of the expert products has to be converted to f16 (NVIDIA matrix cores with f32 activations, BF16 experts or a non-contiguous input), `fGgmlVkMulMatIdQF16` writes it to `vPreallocY`, which used to be sized for `vPaddedN` rows (the tile width, 128 on the RTX 4060 Ti) per token although the shaders read only the routed rows: 512 KiB per token with a 2048-wide input, so once the expert cache had taken the VRAM a 3594-token prompt asked for 1.9 GB and every later graph failed with `ErrorOutOfDeviceMemory`. It now reserves `ne11` rows per token and at least `vPaddedN` rows, which still cover the B tensor layout of one tile: 32 MiB for a 4096-token micro-batch of Qwen3.6-35B-A3B instead of 2 GiB. Only the decode-vector staged layout keeps `vPaddedN` rows per token. Measured on the RTX 4060 Ti with Qwen3.6-35B-A3B Q8_0 (2625-token prompt, 256 generated tokens, `--spec-type none`, three runs each): prompt 515 → 549 tokens/s and generation unchanged (23.5 and 23.4 tokens/s); with every miss uploaded (`MGS_MOE_CACHE_FILL_RATIO=1`) the output of 3594 and 11637-token prompts is byte-identical to the old sizing. Render nodes need the `render` group, which `configure-web.sh` grants to the service account (also `video`, idempotently on Alpine).

**Real VRAM with Vulkan.** On a discrete GPU `ggml-vulkan` counts and allocates only device-local memory (VRAM); GTT, the part of the system RAM (normally half) that AMD and Intel GPUs can map, is never counted as GPU memory, because the GPU reads it over PCIe. Three safeguards keep the model in real VRAM. Without resizable BAR the CPU-visible device-local heap is a small window (256 MiB on an RX 580) shared with the desktop, and `ggml-vulkan` used to try it first for every device buffer: the small ones (about 99 MiB, among them the MTP KV cache) landed there and the kernel evicted 67 MiB of them to GTT. When that heap is under half of the largest device-local heap `vDisableHostVisibleVidmem` is now set automatically, so device buffers go to the large heap (on the RX 580: 0 evicted, 872 KiB left in the window), and that window is not counted either in the free memory reported for device buffers, so `--fit` and the expert cache do not plan with memory those buffers never use. `VK_EXT_memory_priority` is enabled whenever the device offers it and its `memoryPriority` feature is available, with no environment variable. The expert cache pools use a second Vulkan buffer type with `VK_EXT_memory_priority` 0.5 (exported as `ggml_backend_dev_get_cache_buffer_type` and picked by `fPoolBufferType`), so under VRAM pressure the driver evicts the cache before the MTP layers, the weights and the KV cache, which keep priority 1.0; the async copy checks accept any device buffer type of the same GPU (`fGgmlBackendVkBufferIsDeviceOf`). Finally every inference process reads `/proc/self/fdinfo` (`fMonitorDrmResidency`: `drm-resident-*`/`drm-memory-*` and `amd-evicted-vram`, published by amdgpu, i915 and xe), attaches it to the Monitor snapshot of each discrete GPU (an integrated GPU has no VRAM of its own, so it is never checked), warns once in the log when more than 64 MiB (or 2 %) of its GPU allocations are outside VRAM (`mCheckVramResidency`), and the Monitor shows the real location and a warning. `--load-mode none` is not chosen automatically: on AMD the pinned host memory counts against GTT, and 18.9 GB of experts with 16.8 GB of GTT made RADV fail with "Not enough memory for command submission" (`ErrorDeviceLost`). On an AMD integrated GPU, `fGgmlVkBufferRead2d` no longer reads a host-visible buffer without host caching with a CPU `memcpy`, because that memory is write-combined and the CPU reads it very slowly; as upstream does, it first copies it with the device into the cached staging buffer. With Qwen3.6-35B-A3B on a Radeon 860M, saving the state of a slot before a new request and the checkpoint of the recurrent state took about 0.3 s each: a request now starts about 0.27 s earlier and a 17-token prompt takes about 360 ms instead of 615 ms.

**Vulkan kernels and fusions.** A per-operation profile of the prefill (`GGML_VK_PERF_LOGGER=1`, Qwen3.6-35B-A3B Q8_0 on a Radeon 860M) against llama.cpp b11927 showed where this backend lagged, and these generic pieces were ported or extended. Row norms (`RMS_NORM`, also fused with `MUL` and `ROPE`, and `L2_NORM`) run with a block of 128, 256 or 512 invocations picked from the row length (`fGgmlVkRowNormPipeline`) and reduce with subgroup additions on AMD, Intel and NVIDIA (the `_subgroup` shader variants); a fixed 512-wide block left 3/4 of it idle on the 128-wide per-head norms of gated delta net and attention layers. A `GELU`, `SIGMOID`, `SILU` or `SOFTPLUS` is fused with the `MUL` that consumes it (`fGgmlVkUnaryMul`, `aPipelineUnaryMul`, `UNARY_MUL_FUSION` in `unary.comp`), and the graph reordering lets a `MUL` follow its `UNARY` or `RMS_NORM` once the nodes between them are scheduled or empty. A product with one output row (the gate of a shared expert) runs the matrix-vector kernel with the activations as the matrix (`fGgmlVkMulMatVecQF16` with `pSwapInputs`) instead of a tiled matmul that fills one row of each tile. `graph_optimize` receives `ggml_backend_graph_optimize_params`, whose `add_alloc_dep` keeps a tensor allocated until a later node, and `ggml_backend_sched_split_graph` adds those dependencies to the graph copy as `GGML_OP_NONE` nodes; Vulkan keeps the inputs of every `TOPK_MOE` pattern alive until its last node. Without that the allocator placed the normalised expert weights over the router logits, freed after the softmax, the fused kernel would have overwritten rows not yet read, and the fusion was disabled in every layer, so routing ran as separate `ARGSORT`, `GET_ROWS`, `SUM_ROWS`, `CLAMP` and `DIV`. `CLAMP` may also run in place (`ggml_op_can_inplace`), as upstream. The output did not change (the same 256 tokens at temperature 0), and the prefill went from 2.5–2.8% behind llama.cpp to even on that device (within 0.6% at 2048 tokens, equal at 4096). The remaining differences are `GATED_DELTA_NET` (the same shader and dispatch as upstream, but about 25% more GPU time there, because this backend reads about 3 GB/s more from DRAM, which in the 15 W package leaves its GPU clock about 10% lower), the down projection of the experts and flash attention, while the dense products of this fork are faster. CUDA takes the new `graph_optimize` signature but adds no dependencies yet. On coopmat1 devices (cooperative matrices without coopmat2) the quantized `MUL_MAT_ID` kernels also exist with f16 activations (`aPipelineDequantMulMatMatIdF16B`), and `fGgmlVkMulMatIdQF16` converts the f32 activations once instead of letting every weight tile read them in f32. That APU runs with its package limited to 15 W, so its GPU clock depends on the DRAM traffic: `gpu_metrics` showed this backend at about 1750 MHz reading 27.6 GB/s where llama.cpp ran at about 1965 MHz reading 22.4 GB/s, both in the same time. The f16 activations cut the traffic by 6% and the prefill time by 1.6%, with the same output, and leave the prefill about 1% ahead of llama.cpp at 4096 tokens. Devices without cooperative matrices (such as Polaris) and those with coopmat2 keep their path. On an AMD integrated GPU with cooperative matrices those pipelines use their own small tile, 64x32 with two subgroups instead of 32x32 with one (`s_warptile_mmidf16` in `fGgmlVkLoadShaders`): with about 16 rows routed to each expert in a micro-batch of 512, the prefill of Qwen3.6-35B-A3B Q8_0 on the Radeon 860M went from 184 to 196 tokens per second on a 2625-token prompt (6.5% faster, also with MTP) and took 20.7 s instead of 22.1 s for 4096 tokens, about 7% ahead of llama.cpp, with the same output and the same generation speed. A 64x64 tile brought the DRAM traffic down to that of llama.cpp but wasted the columns of those 16 rows and was 5% slower. Other GPUs keep the tiles of the quantized matmul. The DeepSeek V4 ops that Kimi-K3, GLM-5.3-Flash, Qwen3.8-Flash-Next and DeepSeek-V4.1 use have Vulkan kernels ported from llama.cpp b11927: `dsv4_hc_comb.comp` (it needs subgroups of at least 16 lanes with shuffle), `dsv4_hc_pre.comp` (with and without the sigmoid gate), `dsv4_hc_post.comp` (with and without the comb matrix, `fGgmlVkDsv4HcPost`) and `lightning_indexer.comp` (`fGgmlVkLightningIndexer`, head size 128, F32, F16, BF16, Q8_0, Q5_1, Q5_0, Q4_1, Q4_0 or IQ4_NL keys through `flash_attn_dequant.glsl`, whose type helpers now live in `fa_types.glsl`, shared with flash attention). The scale -> sigmoid -> scale gate in front of a hyper-connection post is folded into its kernel (`HC_POST_GATE`, `hc_post_gate_pattern`), and the graph reordering keeps those four nodes together. Before, the lightning indexer ran on the CPU and the hyper-connections were built from generic ops: with Qwen3.8-Flash-Next on a Radeon 860M a token took 114 graph splits and 8101 nodes, now 90 and 6853, as in llama.cpp. `GGML_VK_PERF_LOGGER` also profiles a graph split between devices, whose input copies may already be recorded in the open compute context.

**GGML backends and ROCm.** Only the CPU, CUDA, Vulkan and ROCm (HIP, `backend/ggml/src/ggml-hip`, which compiles the CUDA sources with HIP) backends remain; BLAS, CANN, ET, Hexagon, Metal, MUSA, OpenCL, OpenVINO, RPC, SYCL, virtgpu, WebGPU, zDNN and ZenDNN were removed with their CMake options and what depended on them (`--rpc` among it). `build/build-local.sh --rocm` and the Debian installer (`--rocm`, with `--rocm-targets`) locate ROCm through `hipconfig` (`PATH` or `/opt/rocm/bin/hipconfig`), take the clang compiler from `hipconfig -l` unless `HIPCXX` names another, export `HIP_PATH` and `ROCM_PATH`, detect the GPU targets with `fDetectRocmTargets` (`amdgpu-arch`, then `rocminfo`) and configure `-DGGML_HIP=ON -DCMAKE_HIP_COMPILER=… -DGPU_TARGETS=…`; `backend/ggml/src/ggml-hip/CMakeLists.txt` requires HIP 6.1 or later with hipBLAS and rocBLAS. Neither script installs ROCm. The local bundle carries the ROCm user-space libraries and the rocBLAS/hipBLASLt kernel folders (see the local build above); the installed `/usr/local/bin/mgs` loads the system ROCm through the run path recorded by CMake, which the installer checks with `ldd`. The ROCm and Vulkan backends open `/dev/kfd` and `/dev/dri`, so `configure-web.sh` adds the service account to the `render` and `video` groups.

**Local shell MCP server.** `--local-shell-mcp-server`, or the switch of Settings → MCP servers, turns on `server_shell_mcp` (`backend/tools/server/server-shell-mcp.cpp`), an MCP Streamable HTTP server written in C++ inside `mgs`, so the self-contained bundle needs no Python or extra packages. It is not a separate listener: it is registered as `<api prefix>/mcp/shell` on the same server as the API, so the Web UI reaches it through the same origin, TLS certificate, API key and Apache proxy from any machine, while a `127.0.0.1` port would only be reachable from the server itself. Its endpoints are always registered and answer 403 while it is off (`fServerShellMcpEnabled`): `mSetEnabled` detects the shells the first time it is turned on (`vStarted`, so a call in flight never sees the list cleared) and keeps the state in atomics that `/api/props` reports through `fServerShellMcpProps` (`shell_mcp_server`, `shell_mcp_server_forced` and `shell_mcp_server_toggle`). At startup it is on with the option or when the section `localShellMcpServer` of `~/.mgs/config/ui-settings.json` says so (`fUiSettingsLocalShellMcpServer`). `POST /api/mcp/shell/enabled` turns it on or off: it answers 409 while the option keeps it on and, through `fServerShellMcpMayToggle`, 403 unless the page has the same origin (`fOriginAllowed`) and either an API key is set or the request comes from a loopback address without proxy headers (`vRemoteAddr` of `server_http_req`); it saves the choice with `fUiSettingsSaveLocalShellMcpServer`, and the UI (`SettingsMcpServers`, `PropsService.mSetShellMcpServer`) copies it into its document and fetches `/api/props` again, so that `mSyncShellServer` adds or removes the entry. At startup `mStart` looks for `bash`, `zsh`, `sh` and `pwsh`/`powershell` in the absolute `PATH` entries and the usual directories, and exposes only the tools whose interpreter exists and is executable (`bash.run`, `zsh.run`, `sh.run`, `psh.run`). The server keeps no state: one JSON-RPC message per POST, JSON responses, no SSE stream (GET returns 405) and no session. `fRunCommand` starts the interpreter with `posix_spawn` in a new session (its own process group, without the server's controlling terminal, so sudo never prompts on the terminal that started `mgs`), with `/dev/null` as input, default signal handling (the server ignores SIGPIPE) and separate pipes for stdout and stderr read with `poll`; the timeout (default 60 s, maximum 3600 s) or a closed connection kill the whole group, and after the shell exits the pending output is read for 250 ms, so background processes cannot hold the call. Each stream keeps its beginning and its end (8+8 KiB of stdout, 4+4 KiB of stderr). Every call to a shell tool also leaves its own JSONL file, even when its arguments are rejected or the tool is unknown (the file is opened before the tool is looked up), (`server_shell_mcp_call_log`) in `~/.mgs/local-shell-mcp-server/` of the user that runs `mgs`, named after the local time of the call down to the millisecond (`y2026m10d12h23m59s59ms731.jsonl`, created with `O_EXCL`, so calls in the same millisecond get `-2`, `-3`…): a `command` line written before the run (tool, shell, cwd, timeout, command), then one `stdout` or `stderr` line per read with the whole output in arrival order (`fRunCommand` hands every piece to `pOutput`, and `mOutput` holds back a UTF-8 character split between two reads), and last a `result` line (exit code, signal, timed out, cancelled, seconds and the bytes of each stream) or an `error` line (a rejected call, also one for an unknown tool, has its `command` line, with what was asked, and the `error` line; the answer to the request does not change). The output is never kept in memory, so the file has everything that the tool result cuts and survives a stop of `mgs` during the run. The folder is created with mode 0700 and the files with 0600, because outputs may hold secrets; a file that cannot be written only leaves a warning in the log. `mToolsCallResult` answers a JSON object (`vExitCode`, null when a killed shell could not be reaped, `stdout`, `stderr`, `signal`, `vTimedOut`, `cancelled`, `timeout`, `seconds`, `shell`, `cwd`) both as `structuredContent` and as the text block, because the UI only keeps the text of a tool result: the model reads the same JSON, and the chat splits it into boxes without guessing where one stream ends. Requests with an `Origin` header must come from a page of this server (`fOriginAllowed`, compared with `Host`/`X-Forwarded-Host`; loopback pages are accepted for the development proxy) and must use `Content-Type: application/json`, which blocks cross-site requests; clients without `Origin` depend on the API key. Like the other agent features, the option adds a startup warning; the CORS origin is localhost by default. Router children never receive it, and the route also answers while the model loads. `/api/props` publishes `shell_mcp_server`; `cMcpStore.mSyncShellServer` (called from the root layout) adds the `mgs-shell` entry (named `local shell mcp server`, like the server's `serverInfo.title`) enabled the first time, keeps its URL on the current origin and its name, and removes it when the server stops offering it, and `MCPService.mCreateTransport` sends the UI's API key to same-origin MCP servers. Tool calls still go through the UI's permission prompt. In the chat, `ChatMessageToolCallBlock` sends the `bash.run`, `zsh.run`, `sh.run` and `psh.run` calls (`fIsLocalShellTool`: names in `aShellMcpToolNames` that no other MCP server owns) to `ChatMessageToolCallBlockLocalShell`, which keeps the tool name as title and shows the same grey monospace boxes as the Input box of the other tools: stdin with the bare command, parsed from the partial arguments while they stream, and stdout and stderr only when they have content, with the exit code in the title (`stdout (code 2):`, or `stdin (code 0):` without output); the stdin box has a white border (dark grey on the light theme), the stdout box a green one and the stderr box a red one, the same for the four tools (the `borderColor` of `SyntaxHighlightedCode` with `--local-shell-stdin-border`, `--local-shell-stdout-border` and `--local-shell-stderr-border`). A result that is not that JSON object (argument error, denied permission, failed request) is shown in the stderr box. The `expandLocalShellCommands` setting (Display) makes `ChatMessageAgenticContent.fGetDefaultExpanded` open those calls, so the boxes appear as their contents become known.

**Web UI settings.** Every setting of the interface lives in one JSON document that the server keeps in `~/.mgs/config/ui-settings.json` of the user that runs `mgs` (`backend/tools/server/server-ui-settings.cpp`: folders 0700, file 0600, written under a mutex through a temporary file renamed over the old one), so every browser shares it. `GET /api/ui/settings` returns `{"settings": DOCUMENT}` (`null` before the first save) and `POST /api/ui/settings` replaces it whole; both require the API key, are registered in every mode (the router parent serves them itself) and answer while the model loads. `/api/config.js` publishes the saved language as `globalThis.cUiLanguage` (only a valid language tag), because `i18n.ts` fixes the language at module import, and the saved theme as `globalThis.cUiTheme` (`fUiSettingsTheme`: `system`, `light` or `dark`, otherwise `null`). The theme no longer uses mode-watcher: an inline script of `frontend/src/app.html`, right after `/api/config.js`, puts the `dark` class and `color-scheme` on `<html>` before the first paint (`null` counts as `system`), and `cTheme` (`frontend/src/lib/stores/theme.svelte.ts`: `vPreference` system/light/dark, `vIsSystemDark`, the derived `vCurrent` and `mSetPreference`) takes over, follows `prefers-color-scheme` live while the preference is `system` and switches without transitions; nothing of the theme is kept in the browser. In the interface, `cUiSettingsStore` (`frontend/src/lib/stores/ui-settings.svelte.ts`) loads the document when the root layout mounts and hands each section to the store that registered it: `config` and `userOverrides` (settings store), `favoriteModels` (models), `disabledToolKeys` (tools), `alwaysAllowedTools` (permissions), `reasoningEffortDefault` (conversations), `dismissedRecommendedMcpServers` (add-MCP-server dialog) and `modelsFolder` (the folder of Settings → Models, written by the server through `POST /api/models/folder` and copied into the document by `SettingsChatModelsTab`); `language` is written by `fSetLanguage`, which waits for the save before reloading. `mSet` saves the whole document 300 ms after the last change, and a change still waiting is sent with `keepalive` when the page unloads. Nothing is saved before the document arrives, so a partial state never overwrites the file; a failed load is retried every 5 s, except 401/403, which waits for the API key. The server-default sync and the shell MCP entry wait for both `/api/props` and the document; an absent document is the first visit, when the `--ui-config` defaults apply once. Only the API key stays in the browser (`MgsUi.apiKey`), because it authenticates the request that loads the rest; the conversations are on the server too (**Chats on the server**), and the stream-resume and build-version keys stay in `localStorage`.

**Chats on the server.** The chats of the interface live in `~/.mgs/chats/` of the user that runs `mgs` (`backend/tools/server/server-chats.cpp`), so every browser sees the same ones; the `MgsUi` IndexedDB database of older versions is not read, and `dexie` is no longer a dependency. Every chat is one JSONL file, mode 0600 in a 0700 folder, named after its creation date in UTC with `-2`, `-3`… on a collision (`2026-11-03@14-59-59.723.jsonl`): the first line is `{"conversation": {...}}` and every other one `{"message": {...}}`. Following `Rules/Global-Dates.md`, the files keep `createdAt`, `lastModified` and `timestamp` in the native format `2026-11-03@14-59-59.723` (UTC) and the API in milliseconds, converted by `fChatsNativeDate` and `fChatsDateToMs`. The first request reads the first line of every file into an index (`dChats`, behind `vChatsMutex`); every write goes through a temporary file renamed over the old one (`fWriteChatFile`) and raises `vChatsVersion`, which starts at the time of the start, so a restart is noticed too. `POST /api/chats/:id_chat` (`fChatsMakePostHandler`) creates a chat (the conversation is then required) or changes it: the conversation replaces the saved one, `messages` are added or replaced by id, `deleted` removes ids and `replace` makes `messages` the whole list; a conversation without a valid number (1 to 99, not held by another chat) gets the lowest free one (`fFreeChatNumber`), and one without `createdAt` the current time. `GET /api/chats/search` folds the query and the contents with `fChatsFoldText` (lower case, Latin letters without accents, Greek and Cyrillic in lower case) and returns the newest matching message of the user or the assistant of every chat, without attachments. The `/api/chats` routes are registered in every mode and answer while the model loads. In the interface, `DatabaseService` keeps its methods but works on a copy in memory of what it read (the conversations and the messages of every chat opened) and sends every change to the server with `fSaveChat`, one after the other for the same chat, keeping the number and the creation date that the server gives (a new, forked or imported chat goes with number 0). `mGetConversationMessages` reads the chat again from the server, after the writes still pending for it, so `mLoadConversation` reads the messages before the conversation and uses its current node of the server. A read whose answer may be older than the copy in memory does not replace it: `fSaveChat` and `fDeleteChat` number the writes of every chat (`fAskWrite`, `dWritesAsked`, `dWritesAnswered`), and `mGetConversationMessages` and `mGetAllConversations` keep the copy of a chat that had writes not answered yet when the read started, or got new ones during it (`fServerHasEveryChange`). Otherwise the read that `ChatMessages.svelte` makes when a new chat opens could drop its root message, and the first message would fail because its parent message is not found; for the same reason `mCreateMessageBranch` makes every read before its changes, so no wait separates a change from its write. `ConversationsStore::mSyncWithServer` runs every `cChatsSyncIntervalMs` (3 s) while the page is visible: when `GET /api/chats/version` is not the version of the last read or write of the page (`mGetKnownVersion`), it reloads the list and, unless the page is writing to it (`mIsChatBusy`, registered with `mRegisterChatBusyCheck`), the open chat; when that chat was deleted elsewhere it goes to a new chat. The default name of a new chat shows the date in the display format of the project (`fFormatDisplayDate`, UTC, `2026/11/03@14:59:59.723`).

**Request queue.** The server has one slot by default (`-np 1`, `common_params::vNParallel`; the upstream automatic mode with four slots sharing a unified KV cache was removed, so `--kv-unified` is also off by default): each request gets the whole context, whether it comes from the Web UI or directly from the API, and the others wait in the deferred queue of `server_queue`, which runs them in arrival order: a released slot moves to the front of the task queue the first deferred task, in arrival order, that can use it (one that asked for no slot or for that one, `mPopDeferredTask`), and a task deferred again keeps its place, because `mDefer` inserts it by its `vQueueOrder`. `-np N` runs up to N requests in parallel and splits the context among them. The API does not depend on the interface or on its settings document; the only link is that the Web UI marks its requests with `"mgs_client": "webui"` (a `field_str` of the completion schema that sets `task_params::vFromWebui`), so the server knows the origin of every running and waiting request. When a task finds no free slot, `mDeferTask` counts the busy slots (`mCountRunning`) and the deferred tasks ahead of it (`server_queue::mDeferredTasks`), split into API and Web UI, and, when the request asked for notices (`vQueueNotice`: Web UI, streaming, and any format except Anthropic Messages and OpenAI Responses, whose event streams have a fixed grammar), sends a `server_task_result_queue`, which reaches the stream as `data: {"mgs_queue": {"ahead": N, "running_api": RA, "running_webui": RW, "waiting_api": WA, "waiting_webui": WW}}` (`ahead` is their sum). The streaming handlers wait for the first result before they send the headers, so that event also opens the response at once. When a queued task gets its slot it receives a last notice with every count at 0, and `mNotifyQueuePositions` updates the tasks still waiting. Clients that do not send `mgs_client` never receive these events, so their OpenAI-compatible streams stay unchanged. In the UI, `ChatService.mHandleStreamResponse` passes the events to `onQueue` and clears the state on the first regular chunk; `cChatStore` keeps it per conversation (`mGetQueueStatus`) and `ChatMessageAssistantProcessingInfo` shows `fQueueStatusText` before any other progress text: the API variant while a request sent directly to the API is running (`running_api` > 0), otherwise the Web UI variant, both with the number of requests ahead. The requests that the UI sends by itself (KV cache pre-fill after a response, generated titles) carry the same mark and also take their turn.

**Shutdown.** The first SIGINT or SIGTERM after the model has loaded stops the server in order (before that the default action ends the process at once, and a second signal calls `exit(1)`). `fSignalHandler` only writes the signal number into a pipe, and the thread started by `fStartShutdownThread` runs the shutdown handler, because that handler takes the mutex of the task queue, which the interrupted thread may hold. `server_queue::mTerminate` also sets `vTerminateRequested`, so a signal that arrives before `mStartLoop` is not undone when the loop starts. A decode in progress stops as well: `server_context::mTerminate` sets `vTerminating`, which the abort callback of the target and draft contexts (`fAbortWhenTerminating`) reads; the CPU backend checks it between nodes and the scheduler between splits (`ggml_backend_sched_set_abort_callback`), so a graph computed on GPUs stops too, `mgs_decode` returns 2 and `mDecode` answers the requests with a 503. `server_http_context::mStop` then sets the flag read by `fServerHttpIsStopping`, which is part of the stop condition of every request (`server_http_req::vShouldStop`) and of resumable streams (`X-Conversation-Id`): the handlers waiting for results give up within a polling second even when the client is still connected, and a request that is not streamed gets a 503 instead of an empty response, as does a request that the router was still forwarding; all of them say `The server is shutting down.`. Previously those handlers waited for the client, stopping the HTTP server waited for them and only a second signal ended the process, and a prompt in progress first finished its whole batch. With Qwen3.8-Flash-Next on a Radeon 860M it now exits in 1.1 s when idle, 1.4 s while generating, 1.3 s while streaming, 1.5 s in the middle of a 2625-token prompt (35 s when the batch had to finish) and 1.7 s for a router and its model process signalled together in the middle of a prompt, as systemd does.

**sudo password prompts.** On Linux, when sudo exists, `mStart` also creates `server_shell_mcp_askpass`: an abstract Unix socket (no file to protect or clean up) served by its own thread, with one thread per connection. A `tools/call` whose `_meta` carries `mgs/callId` (the UI generates one per call in `cMcpStore.mExecuteTool`) is registered with a random token, and its command gets `SUDO_ASKPASS` (the `mgs` executable itself: `MGS_EXECUTABLE`, published by the launcher, or `/proc/self/exe`), `MGS_LOCAL_SHELL_ASKPASS` (socket name and token) and, when the server has none, `DISPLAY=:mgs-askpass`, because sudo only falls back to the askpass helper without a terminal when `DISPLAY` exists. sudo runs `mgs <prompt>`; `fServerShellMcpAskpassMain`, the first thing `mgs_server` calls, recognises that case (the variable, a single argument and a sudo parent) and sends the token and the prompt through the socket. `mServe` checks with `SO_PEERCRED` that the helper belongs to the same user and with `fParentIsSudo` that its parent is sudo (name `sudo`, our real uid, root as effective or saved uid: an unprivileged process cannot read the executable of a setuid process, so this is the strongest check available), so a command cannot launch the helper itself with a fake prompt to capture the password. The prompt then waits (5 minutes at most) while `fRunCommand` moves its deadline by the time spent waiting (`mPaused`); `DialogLocalShellAskpass`, mounted once in the root layout so it opens on any page, polls `GET /api/mcp/shell/askpass?call=` every 500 ms for every running call (`cMcpStore.mActiveShellCalls`, filled by `mExecuteTool` with the tool and the command) and shows the first prompt in a centred dialog (ShadCN `Dialog` without the close button: the password field takes the focus as soon as a prompt shows (`fFocusPassword`, an attachment of the field, because `onOpenAutoFocus` runs before its ref is bound), Accept or Enter (`fHandlePasswordKeydown`) answers, Cancel or Escape cancels, a click outside does nothing) with the sudo prompt, the tool and the command, and a notice when sudo asks again after a password; `POST /api/mcp/shell/askpass` delivers the password or a cancellation, the helper writes it to the pipe that sudo reads and the copies are wiped. The password never reaches the tool result, the conversation or the logs; errors (cancelled, unanswered, command ended) reach the stderr of the command as `mgs: ...`. Other MCP clients send no call id, so their commands get no askpass variables and sudo fails for lack of a terminal as before.
**Security hardening.** Version 0.1.9 closes the findings of an external static security review (21 findings: 20 fixed; the one about the installers is left by design, see below).
- **HTTP (`server-http.cpp`):** public paths skip the API key only for GET/HEAD, and `GET /v1/models?reload=...` needs the key when keys exist. With the `localhost` CORS mode, the default since 0.1.40 (`common_params::vCorsOrigins`), a request whose method is not GET, HEAD or OPTIONS gets 403 before routing when its `Origin` is neither loopback nor this same server (`Host` or `X-Forwarded-Host`; Apache keeps `Host` with `ProxyPreserveHost On`); requests without `Origin` (curl, SDKs) pass. `POST /tools` needs `Content-Type: application/json` (415), so a cross-site form cannot reach it without a preflight that CORS refuses. While a request is received, each read waits 30 s at most (`cHttpRequestReadTimeoutSec`); `--timeout` still governs writes, so long generations are not cut. Both thread pools queue at most 256 accepted connections (`cHttpMaxQueuedConnections`), and `mPost`/`mDel` refuse bodies nested deeper than 1024 arrays or objects (`fJsonNestingExceeds`, `cHttpMaxRequestJsonDepth`) before any handler parses them, because nlohmann copies and dumps documents recursively.
- **Router (`server-models.cpp`):** `fRedactArgs` and `fRedactPreset` replace the values of secret options (`sSecretOptionEnvs`: HF token, API key and key file, SSL key, MCP server configuration) with `<redacted>` in `status.args`, `status.preset` and the spawn log; children still receive the real values. `mProxyRequest` drops `Origin` when forwarding to a child, because the router has already checked it.
- **CORS proxy (`server-cors-proxy.h`):** navigation and embedding requests (`Sec-Fetch-Mode` navigate, `Sec-Fetch-Dest` document, frame, object or worker) get 403 (`fProxyIsNavigation`), and every proxied answer is made inert (`fProxyMakeInert`): sandbox CSP, `nosniff`, `Content-Disposition: attachment` and same-origin CORP, without the upstream cookies, CSP, CORS, HSTS, redirect, link or service-worker headers. `Content-Type`, `mcp-session-id` and `WWW-Authenticate` stay for the MCP client of the UI.
- **Remote media (`download.{h,cpp}`, `server-common.cpp`):** `fCommonRemoteGetContent` applies a connect timeout, a total deadline (`set_max_timeout` plus a check in the body receiver) and follows redirects by hand. For `image_url`, `input_audio` and `input_video` (`vPublicHostsOnly`), the host is resolved once and every address must be public: no loopback, RFC 1918, CGNAT, link-local (169.254.169.254 included), documentation, multicast or reserved ranges, and in IPv6 only 2000::/3, with mapped, NAT64 and 6to4 addresses judged by their IPv4. The connection is pinned to the checked address (`set_hostname_addr_map`) and every redirect is checked again; `--media-allow-private-urls` lifts the address check. Media downloads take 10 s per connection, read or write, 30 s in total, 5 redirects, 10 MiB and 8 at once (`media_download_slot`); `ffprobe` and `ffmpeg` only read pipes when the input is a request buffer. All the media of one chat request share `media_request_budget` (256 items, 512 MiB of encoded bytes, 120 s for all its downloads), which also bounds `--media-path` files before they are read.
- **Decoding (`mtmd-helper.cpp`, `server-common.cpp`):** images up to 32768 px per side and 100 megapixels, checked with `stbi_info_from_memory` before decoding; audio up to one hour, checked before the samples are allocated; video frames up to 8192 px per side and 2 GiB of RGB frames per video; at most 2 GiB of decoded images, audio and video frames per request (`fProcessMtmdPrompt`, which hands its counter to every video with `mtmd_helper_video_set_decoded_budget`, so the frames decoded later, while the prompt is tokenised, count against the same total).
- **Parsers:** the GBNF converter (`json-schema-to-grammar.cpp`) rejects empty patterns and quantifiers with nothing to repeat; it limits schema nesting, nested visits and `$ref` chains to 256 (`cMaxSchemaDepth`, measured iteratively by `fJsonExceedsDepth`), pattern groups to 128, excluded property names to 1024 bytes and `type` lists to 7 entries, and sanitises rule names with a loop instead of the recursive `std::regex`. The Jinja runtime (`jinja/value.h`) limits `range()` to one million elements, built strings to 256 MiB and 1 Mi parts, `indent()`/`tojson()` indentation to 256, statement execution nesting to 1024 and parse nesting to 256. `gguf.cpp` skips zero dimensions in the overflow check instead of dividing by them; empty tensors stay valid.
- **RPC:** the frame-size and tensor-bound checks of the RPC server were part of this review; the RPC backend itself was removed in 0.1.19 with the other unused ggml backends, so `mgs` serves no RPC peers.
- **Web UI:** a Markdown render that fails shows escaped text. Links whose scheme is not http, https, mailto or tel (or relative) lose their `href`, image attachments must be `data:image/...;base64`, and the broken-image notice is built with DOM nodes (`fCreateImageErrorFallback`). Conversation import checks the file (512 MB), the ZIP entries (10 000), each JSONL (256 MB) and the extracted total (1 GB) before decompressing, validates every record, requires each message's `convId` to match its conversation and writes with `bulkAdd`, skipping a conversation whose message ids already exist. One identity per tool name (`mResolveEnabledEntry`) serves the model, the approval and the execution, which goes to that exact server (`mExecuteTool(pToolCall, pServerId, pSignal)`); a name offered by two enabled MCP servers is withheld with a warning, and "always allow this server" applies by server id, bound since 0.1.40 to the endpoint of that id (`ToolEntry.permissionKey`).
- **Web UI dependencies (`frontend/package.json`, 0.1.10):** the packages flagged by `npm audit` that reach the browser bundle move to fixed releases: DOMPurify 3.4.17, mermaid 11.17.2 and `@modelcontextprotocol/sdk` 1.32.1. SvelteKit 2.70.3 and `@vite-pwa/assets-generator` 1.0.4 (sharp 0.35.5, Node.js 20.9 or later) are updated too, and `npm audit fix` refreshes the build-time transitive packages within their ranges; direct versions stay pinned exactly. What `npm audit` still lists only touches build tooling (`postcss-selector-parser` through `@tailwindcss/typography`, the esbuild development server on Windows) or KaTeX, whose fix (0.18.2) is outside the `^0.16` range that `rehype-katex` and mermaid accept; that KaTeX advisory needs an existing prototype pollution to be exploited.
- **Not addressed:** pinning the `curl | bash` installers to an immutable revision or signature (the project rules require installing from `main`), an absolute deadline for the whole header block (cpp-httplib applies the timeout to each read), a global CPU and memory budget for Jinja templates and the recursion of `mgs-grammar.cpp` over the request `grammar`.

**Second security review (0.1.40).** A second external static review reported 13 findings; 12 are fixed and the one about the installers is left by design, as in the first review.

- **CORS and DNS rebinding (`common.h`, `arg.cpp`, `server-http.cpp`):** `--cors-origins` defaults to `localhost` instead of `*` with credentials, so foreign pages can neither read the API (no `Access-Control-Allow-Origin` for them) nor write to it (403 before routing); the automatic switch that only tools and MCP servers turned on is gone with `vCorsOriginsExplicit`. On a plain HTTP TCP listener without an API key (`cCheckRebindHost`: not HTTPS, not a Unix socket, not Vertex AI), the pre-routing handler answers 403 `Host not allowed` unless `fHostIsRebindSafe` accepts the `Host` header: an IP literal, `localhost` or `*.localhost`, or one of `fLocalHostNames` (the machine name, the same with `.local`, the `--host` name). `X-Forwarded-Host` is not trusted there. Router children are not affected because `server_http_proxy` rewrites `Host` to their loopback address.
- **Vertex AI (`server-http.cpp`):** `mRegisterGcpCompat` only resolves `@requestFormat` (alias or path) among `sGcpPredictPaths`, the inference, tokenisation and token-counting routes, so a prediction can no longer reach settings, models, tools, MCP servers, the CORS proxy or the predict route itself (which spawned one `std::async` task per nested instance).
- **Hugging Face token (`arg.cpp`):** `fUrlDownloadOpts` clears `vBearerToken` for every plain URL task (`--model-url`, the projector and draft URLs, multi-part models) unless the URL starts with `fCommonGetModelEndpoint()`; Hugging Face plan tasks keep it, and cpp-httplib already drops `Authorization` on cross-host redirects.
- **Media (`server-common.cpp`, `mtmd-helper.cpp`):** `media_request_budget` (see the remote media item) and the request-wide decoded budget for video frames (see the decoding item).
- **Projectors (`clip.cpp`):** `n_merge` must be greater than 0, and at least 2 for the projectors whose graph calls `mBuildPatchMergePermute` (Idefics3, LFM2, dots.ocr, Nemotron V2 VL, Kimi-VL, PaddleOCR, Kimi-K2.5); the MiniCPM-V 4.6 merge factor, the InternVL tile range and the Parakeet subsampling and kernel size throw load errors instead of `GGML_ASSERT`, so `fClipInit` reports them and the process keeps running.
- **`read_file` (`server-tools.cpp`):** `tools_io::mOpenRead` opens the file and `server_tool_read_file::mInvoke` scans it in 64 KiB blocks, keeping only the characters of the requested lines, up to 16 KB of output and 256 MiB scanned (`cServerToolReadFileMaxScan`); the whole-file size check without `end_line` stays.
- **Web UI:** `fMountSvgShadow` attaches the shadow root to an inner element and gives the host `contain: paint`, because shadow CSS can restyle its own host (`:host`, even with `!important`) but not the host's light-DOM box, so an SVG can no longer paint over the tool approval card. `fMessageGraphHasCycle` makes `DatabaseService.mImportConversations` skip conversations whose parent or children links loop, and `fFilterByLeafNodeId`, `fFindLeafNode` and `fFindDescendantMessages` keep visited sets for data already stored. `MCPService.mCollectPages` bounds resource and template pagination (`cMcpListMaxPages`, `cMcpListMaxItems`, `cMcpListMaxDurationMs`, repeated cursors). MCP resources are identified by server and URI (`fMcpResourceKey`) in selection, cache, subscriptions, attachments and reads (`cMcpStore.mReadResource`, `mAttachResource`, `mSubscribeToResource` and `mUnsubscribeFromResource` take the server first, and `mFindServerForUri` is gone). Always-allow grants of MCP tools use `ToolEntry.permissionKey`, the tool key plus `cMcpStore.mGetServerIdentity` (transport, proxy use, normalised URL and an `fFingerprint` of the headers), so a server id that now points at another endpoint or credentials asks again.
- **Not addressed:** the installers still fetch the mutable `main` branch without a signature (the same decision as above).

<a id="flows"></a>
## Main call paths

1. **Installation:** Debian file/stdin entry → validation → log and lock → local checkout or GitHub `main` archive → source validation/synchronisation → child Bash with closed stdin → `install-common.sh:fMain` → `configure-web.sh --check` with the web options → backend toolkit checks (CUDA `nvcc`, ROCm `hipconfig` and `fDetectRocmTargets`, `glslc`) → dependencies (`fInstallSystemDependencies`, `fInstallNccl`) → stable `_/temp/source` staging including `build/` → CMake with `-S _/temp/source/build` → `bin/mgs` installation (ROCm: `ldd` check) → `configure-web.sh --binary PREFIX/bin/mgs` with the web options (flow 2). Alpine calls the helper directly from a local checkout.
2. **Deployment:** `configure-web.sh` (from the installer or alone) → domain (`--domain` or `fDetectDomain`) and `--proxy-ip` validation → service account and `render`/`video` groups → API key and `/root/webapp-credentials.txt` → certificate in `/opt/moe-gguf-server/certificates/` (kept, copied or created once) → standalone template with or without the `@PROXY@` lines (`fProxyExceptions`) and `web-proxy-ip` → systemd/OpenRC units (`mgs --http --host /opt/moe-gguf-server/_/temp/web/mgs.sock`) → service restarts → `start-web.sh` → occupied listeners → 11080+/11443+ selection → Apache bind → ownership of both listeners → `ports.json` → HTTPS requests → `ProxyPass` to the Unix socket. A real bind conflict returns to selection; other failures stop the service.
3. **Chat:** component → `ChatService.mSendMessage` → normalised messages and custom JSON → `fApplyResponseLanguage` using the current `respondInInterfaceLanguage` flag and UI locale → `fApiUrl` → HTTP registration → authentication/readiness → `server_routes` → task queue/slot → mgs/GGML evaluation → JSON or SSE → browser storage and rendering. `mGenerateTitle` and every agentic turn use this same path; `mPreEncode` applies the same system instruction before preparing the KV cache.
4. **Router:** external handler → canonical internal path → model selection → child `/api` request → response or retained stream. Lookup, resume and cancellation follow the same contract.
5. **MTP:** `mgs_server` (before the MoE-only check) or common initialisation → `fCommonMaybeEnableMtp` → `fDetectMtp` on `--model`, or on the `--spec-draft-model` GGUF without requiring a trunk → all GGUF shard headers/tensors → architecture/trunk/head checks → `draft-mtp` selection unless `--spec-type` was given → model load: `mgs_model_base::mLoadTensors` places the MTP layers and the output layer on a GPU → `mgs_model_loader::mCreateTensor` skips the overrides to host memory for them. Without `--spec-draft-n-max`, the integrated MTP takes the number of draft tokens saved in `~/.mgs/tuning/mtp.json` (0 leaves it out) or is measured while generating (`common_spec_tuner::mStep` from `mUpdateSlots`, then `mSaveSpecTuning`).
6. **MoE:** mapped weights → host registration → graph split → `fInitializeExpertPrefetch` → separate-backend transfer → ready/free events → computation. Memory pressure reduces the slot count or restores regular copies. Each slot takes the padded size of the largest tensor, its padding is zeroed after every transfer, and it is allocated only while the device keeps the reserve free.
7. **Language:** URL `lang` (priority) / storage → one of 15 catalogues (default `en-US`) → `fTranslate` → Svelte-escaped text; root layout → HTML `lang`/`dir` → logical navigation and bidirectional chat text; selector → persistence → reload.
8. **Updated inference:** microbatch original indices → independent output/no-output arena → CPU/CUDA/HIP/Vulkan kernels → restore NextN row order → accept until EOG → completed-slot speculative metrics.
9. **Export/tools:** selected IDs → persisted conversation/message read → JSONL/ZIP; tools HTTP 403 → retained disabled state → explicit panel retry.
10. **Local build:** `build/build-local.sh` from a file or stdin → options → local/remote selection → private workspace and log in `/tmp/moe-gguf-server-build.XXXXXXXX/` → toolchain, CUDA and Node.js checks → local copy or HTTPS archive download/validation/extraction into `source/`, including `build/` → CMake with `-S source/build` in `cmake/` → `mgs` → static launcher → loader, `ldd` closure (with the ROCm libraries in ROCm builds) and NSS modules in `bundle/lib/mgs/` → server binary and `DT_RPATH` `$ORIGIN` → marker in `bundle/lib/mgs/` → `build/licenses/` and the root `LICENSE` in `bundle/licenses/` → prefix lock → finished artefacts copied next to their places (ROCm: `fBundleRocmKernels` adds the kernel folders) → atomic replacement of `lib/mgs/`, `bin/mgs` and `share/doc/mgs/licenses/` → `<loader> --list` verification → `--version` through the launcher → `fCleanup` removes the private workspace. At run time: launcher → `/proc/self/exe` → `MGS_EXECUTABLE` → prefix from `bin/` → `fExportKernelFolders` (ROCm kernel folders) → `execv(lib/mgs/<loader>, lib/mgs/mgs, arguments)` → router children re-enter through the launcher.


11. **Native web startup:** `common_params` / CLI → `server_http_context::mInit` → `fCreateHttpsServer` (PEM, or `fPersistentServerIdentity`: load or create `~/.mgs/certificates/`) → `start` → `fBindServerPort` for HTTPS → distinct HTTP port → two listener threads → actual URLs in the log → stop and join both threads.
12. **MoE expert cache:** first request after loading → `mgs_context::mDecode` → `mgs_expert_cache::mFCreate` → eligible layers (discrete GPUs only) and groups → budget of every GPU → pools and identifier buffers on every GPU → bandwidth probe per GPU → `mSchedReserve` with the hybrid graph and the upload callback. Micro-batches below 32 tokens: router on the device → `mPartition` on the CPU (selection copy, SLRU hits, balanced uploads, identifiers) → device branch over the pool → CPU branch over host weights at the same time → `mMeasureCpu` → merge on the device → router weights. Large micro-batches: prefetch → `mUploadWeights` (device copies for cached experts, host uploads for the rest) → computation. `POST /api/expert-cache` → task queue → `mgs_set_expert_cache_size` → the next decode rebuilds the cache and the graphs.
13. **Context checkpoints:** prompt batch filling → message start in a micro-batch at least 3/4 full, or last user message → batch cut → checkpoint at the batch start (message start, prompt end or `--checkpoint-min-step` since the last one) → `mCreateCheckpoint` (evicts the closest neighbours) → a later request that diverges at position p restores the newest checkpoint before p → only the suffix is processed.
14. **Automatic configuration (fit, batches, context, threads):** argument parsing → `fPostprocessCpuParams` → `fCommonDefaultThreads` when `-t` is absent → `mLoadModel` adds the measured draft/MTP context to the device margins → `common_init_result` → `fCommonFitParams` (`pAutoBatch` = no `-b`/`-ub`) → `fCommonParamsFitImpl`: measurement with the initial parameters → shared budget of an integrated GPU (`fDeviceIsUma`, `lDeviceFree`) → step 2 reduces an unset context to `--fit-ctx` when the model does not fit → dense-only layers back to front → every expert in RAM (expert cache, never on an integrated GPU) or whole expert layers → `fRaiseBatch` → `fRaiseContext` (both before the whole expert layers) → `n_batch` copied back into the parameters → thread log → model and target context load → draft context with `n_ctx` and `n_batch` of the target → the expert cache takes the rest of the device memory on the first request. The draft/MTP context enters the margins with what it takes at `--fit-ctx` tokens, and every measurement of the fit adds its growth per token for the context size measured. After the whole expert layers, `fRaiseMicroBatch` with `pUnusedMemory` raises the micro-batch again with the memory they leave below the target. <a id="impact"></a>
## Impact analysis

- **Reply language:** apply the instruction after custom JSON so replacing `messages` cannot bypass the enabled setting. Read the current flag for every new request, rather than storing a locale instruction in the conversation. Both completion and prefill must use the same helper to preserve the KV prefix. Stream reconnection reuses the already-running generation and cannot change its language instruction. Keep all 15 `responseLanguage.*` catalogue entries aligned; regional guidance is explicit for Argentine/Spain Spanish, UK/US English and Brazilian/European Portuguese. Following a prompt remains model-dependent; external API callers are unaffected.

- **Remote installation:** URL, GitHub archive layout and entry/helper protocol changes affect `curl | bash`. Keep help options aligned and the repository origin fixed. The marker and lock protect the managed tree; do not store local edits there that must survive synchronisation.
- **Native TLS:** direct clients must use HTTPS and trust the certificate or supply a known PEM pair. `--http` is explicit for the Apache backend and router children; children do not inherit public TLS variables. An explicit main port is never silently changed. Builds without OpenSSL require explicit HTTP.
- **Deployment in one step:** the installers check the web options with `configure-web.sh --check` before compiling and pass them to `configure-web.sh` after installing, so a new web option must be added to the option lists of `install-update-reinstall-debian.sh`, `install-common.sh` and `configure-web.sh` and to their `fShowHelp`. Every run of `configure-web.sh` rewrites the template, `web-domain` and `web-proxy-ip` from its options, so a run without `--proxy-ip` or `--domain` removes the proxy or returns to the detected domain. The inference socket path `/opt/moe-gguf-server/_/temp/web/mgs.sock` appears in the systemd and OpenRC units and in `apache2.conf.in`; change them together, and keep the folder owned by `moe-gguf-server` (Apache runs as that account). With `--proxy-ip`, a wrong address makes Apache wait for a PROXY header from a client that does not send it, and `RemoteIPProxyProtocolExceptions` must list every other network (`fProxyExceptions`), or direct clients fail on HTTPS.
- **Web ports:** affect redirects, public addresses, firewalls and the browser storage origin. `ports.json` is published only after both listeners belong to the launched Apache process. An exclusive lock prevents concurrent launchers. HTTPS is reserved before searching HTTP so overlapping sequences never share a port. Port exhaustion produces an explicit error.
- **Prefixes and middleware:** affect every HTTP client, authentication, router, streams, frontend and Swagger. Change `server-http`, `server-models`, `api-url` and their documentation together.
- **Request hardening:** the cross-site check relies on `Host` or `X-Forwarded-Host` naming the public address: a reverse proxy that rewrites `Host` without sending `X-Forwarded-Host` makes the UI's writes fail with 403 (`deploy/apache2.conf.in` keeps `ProxyPreserveHost On`). On a plain HTTP TCP listener without an API key, `fHostIsRebindSafe` also refuses `Host` names that are not this machine's, so a reverse proxy in front of `--http` must either keep such a `Host`, use the Unix socket or configure an API key; widening `fHostIsRebindSafe` to any name, or trusting `X-Forwarded-Host` there, brings DNS rebinding back. Raising `cHttpRequestReadTimeoutSec` or removing the queue bound brings back slow-client exhaustion; lowering `cHttpMaxRequestJsonDepth` below about twice `cMaxSchemaDepth` would refuse JSON schemas that the converter accepts.
- **Secret options:** an option that holds a credential must be listed in `sSecretOptionEnvs`, or its value appears in the public router listing and in the spawn log.
- **Remote media policy:** `common_remote_params` defaults keep the previous behaviour for Hugging Face and Docker manifests; only the media path sets `vPublicHostsOnly`. Following redirects automatically, or connecting by name after the check, reopens DNS rebinding and redirect-based SSRF. The decode limits are generic constants in `mtmd-helper.cpp` and `server-common.cpp`; lowering them refuses legitimate large media.
- **UI tool identity:** approval, permissions and execution must use the entry returned by `mResolveEnabledEntry` and its server id; resolving by bare name again (first match in the UI, last writer in `MCPStore`) lets one server's approval run another server's tool, including the local shell. Always-allow grants must use `ToolEntry.permissionKey`, not `key`: `key` only names the server id, which an edit or an import can point at another endpoint.
- **MCP resource identity:** every read, cache entry, subscription, selection and attachment is keyed by server and URI (`fMcpResourceKey`); looking a resource up by URI alone again lets one server supply the content of a resource chosen from another.
- **Completion schema:** affects inference validation, defaults and OpenAPI documentation. Extensions must retain protocol field names.
- **Catalogues/selector:** affect all views and labels initialised during module import. Keep keys, language names and data parameters aligned across all 15 catalogues; English plural suffix parameters may be omitted where a translation uses count labels. Preserve HTML tags and title-template tokens such as `{{USER}}` and `{{ASSISTANT}}`. Register new locales in both `aLanguages` and `dCatalogs`. Hebrew also affects navigation direction; code must remain LTR. Do not translate protocol identifiers or user data.
- **Registration/prefetch:** affect RAM/VRAM use, GPU events and mapping/buffer lifetimes. Never release a registered page or slot while it remains in use. A slot must take the size its buffer type allocates for the tensor (`ggml_backend_buft_get_alloc_size`) and its padding must be zero: sized with `ggml_nbytes`, the CUDA products read past its end.
- **MTP:** affects decoder selection before weight allocation. Preserve explicit-option precedence and inspect every GGUF shard. MTP weights ignore the overrides to host memory and take device memory before `--fit` places the trunk and before the expert cache is sized, so changing the MTP layer assignment in `mLoadTensors` changes the VRAM use of every model with MTP. The saved measurement is keyed by version, model, GPUs and memory: a change that alters the speed of MTP within one version needs the file removed to measure again; every new version measures again by itself.
- **CMake/installers:** affect every build platform. Do not reuse caches from the old layout or hide local UI build failures.
- **Reasoning budget:** `fOaicompatChatParamsParse` sets a zero budget whenever thinking is disabled, so changes to the thinking tags that the chat parser reports (`vThinkingStartTag`, `lThinkingEndTags`) or to the forcing in `fCommonReasoningBudgetAccept` affect every model with a reasoning block, including those whose template already closes it when thinking is off.
- **KV cache type:** `fMgsKvTypeForWeights` sets by default the memory per context token and the precision of the attention of every model, and the `--fit` context and the expert cache budget follow it. Only `q8_0` and `q4_0` are candidates because CUDA compiles only the `q4_0-q4_0`, `q8_0-q8_0`, `f16-f16` and `bf16-bf16` vector kernels by default (`GGML_CUDA_FA_QUANTS`). Its other Flash Attention kernels (the prompt, several tokens per step as in the MTP verification, heads other than 64, 128 or 256) convert a quantized cache to `f16` on every call, so with CUDA and ROCm, which share these kernels, a quantized cache is slower than `f16`. The automatic choice keeps the quantized type anyway, on every backend, because the memory it saves gives a much longer context, which is preferred to those few percent of speed (on a Radeon 860M with Vulkan, Qwen3.6-35B-A3B Q6_K and `--spec-type none`, `q8_0` generated 3.8% fewer tokens per second than `f16` after a short prompt and 2.7% fewer after an 8060-token prompt). Versions 0.1.48 and 0.1.49 kept `f16` on CUDA and ROCm devices; 0.1.56 removed that exception. The fallback to `f16` only catches a Flash Attention that does not run with the type (`supports_op`), not a slower one. Measure every backend and architecture before changing the thresholds.
- **Version:** `MGS_VERSION` names the shared library files (`libmgs-engine.so.0.1.57`; the soname stays `.so.0`) and reaches `/api/props`, `system_fingerprint`, the shell MCP `serverInfo.version`, the download `User-Agent` and the UI `build.json`. Keep the `MAJOR.MINOR.PATCH` form: the UI build rejects characters outside `[A-Za-z0-9._-]`.
- **Vulkan:** the bundle shares the C/C++ runtime with the system driver it loads, so a bundle built on an older or newer Debian release may fail to load the ICD. Pinned expert uploads only exist with CUDA; any change to `--load-mode` defaults or to the host buffer types changes Vulkan transfer speed. Every expert-cache fill and every expert prefetch from pageable memory goes through the staging ring of its backend: a new path that sends a context must go through `fGgmlVkSubmit`, which counts `vSubmitCount`, and keep the signal semaphores of its submissions, or the ring waits for a copy that never reaches the queue. Service accounts without the `render` group cannot open the GPU. Device buffers must stay in device-local memory; never enable `GGML_VK_ALLOW_SYSMEM_FALLBACK` or `GGML_VK_PREFER_HOST_MEMORY` for MoE serving. A new cache-like device allocation should use the cache buffer type, and any new async path in `ggml-vulkan` must accept every device buffer type of the GPU. The work buffers of `ggml-vulkan` (`vPreallocX`, `vPreallocY`, `vPreallocSplitK`) grow lazily with the graphs that run and `--fit` does not count them: they come out of `--moe-cache-reserve`, so a change that makes them grow with the tokens of the micro-batch can make long prompts fail with `ErrorOutOfDeviceMemory`.
- **Local bundle:** newly linked libraries are picked up automatically through `ldd`. Data that a library loads at run time is not: the rocBLAS and hipBLASLt kernel folders are copied by `fBundleRocmKernels` and found through the variables that `fExportKernelFolders` exports, so a ROCm release that moves them, or another library with such folders, needs both places updated. Changes to `OUTPUT_NAME`, the re-execution paths of the router and of the integrated-GPU restart (`fGetServerExecPath`, `fWaitPassivelyOnIntegratedGpu`, `MGS_EXECUTABLE`), the loader's explicit-execution mode or the library search order affect `build/build-local.sh` and the launcher. Running `lib/mgs/mgs` directly bypasses the bundled loader and is unsupported. Driver libraries must remain excluded.
- **MoE expert cache:** affects device memory (the pool takes what remains after the context; `--moe-cache-reserve` covers other processes and lazily allocated buffers), split synchronisation in the scheduler, the CPU `mul_mat_id`/`add_id` kernels (negative identifiers) and the graph of every MoE architecture (`mBuildMoeFfn`). Device kernels for expert products must accept slot identifiers that are distinct within a token. Changing `--fit` placement changes the RAM needed: keeping every expert in RAM falls back to whole expert layers when `MemAvailable` is short. With several GPUs every GPU holds its own pool for its layers; the layer split (`--fit`, `--tensor-split`) decides which experts each GPU caches. An integrated GPU never gets a pool, from `--fit` or from `mFCreate`: changing the device type a backend reports (`GGML_BACKEND_DEVICE_TYPE_IGPU`) or `fDeviceIsUma` changes both the memory budget of `--fit` and whether the cache exists. The victim order of the per-layer segmented LRU (`mTouch`, `mInsert`, `mFindVictim`) sets the hit rate and, through the misses, generation speed: a new path that places an expert in a slot must call `mInsert` with the layer that owns the slot and one that reuses a cached expert `mTouch`, or `vProtectedCount` stops matching the protected list; a slot never moves to another layer. The host memory budget (`mgs_host_memory_available`, `mgs_host_memory_total`) decides whether the experts stay in RAM, how large the prompt cache is and whether the mapped weights are pinned: a change in how it reads `/proc/meminfo` or the cgroups changes all three.
- **Batch sizes and threads:** `cBatchShare` in `fRaiseMicroBatch` (used by `fRaiseBatch` and around an explicit placement) trades device memory for prompt speed; the micro-batch is chosen before the context, so a larger micro-batch also shortens the default context (Qwen3.6-35B-A3B Q8_0 on 16 GB: 122880 tokens with 512, 89856 with 4096). The server cuts prompts and places context checkpoints by `mgs_n_batch`/`mgs_n_ubatch` of the target, so their positions follow the chosen sizes. Any change that makes the draft or MTP context take a batch larger than its own `n_batch` overflows its batch buffer. `fCommonDefaultThreads` changes the CPU share of every MoE layer with experts in RAM; measure generation with `--spec-type none` on a virtual machine and on bare metal before changing the cap. The second raise after the whole expert layers only takes memory in which no expert tensor fits; moving it before step 4 would take memory from the experts.
- **Context size in `--fit`:** `pContextShare` in `fRaiseContext` trades context for experts: every byte of KV cache it allows comes out of the expert cache pool or out of the whole expert layers placed on the devices, so a larger share lowers the generation speed and a smaller one shortens the default context. The draft context follows the target context, so changing how `mLoadModel` sizes it changes the device memory left to the expert cache of every model with MTP or a draft model. Its growth per token reaches the fit through `lFitParamsTargetPerCtx`: a new measurement in `fCommonParamsFitImpl` has to go through `fGetDeviceMemoryData`, or it leaves that growth out.
- **Allocation dependencies:** `graph_optimize` may only name as `until` a node of the split it received (`ggml_backend_sched_split_graph` asserts it), and every dependency lengthens a lifetime, so the compute buffer can grow. The row-norm blocks must keep `ncols <= 2 * block` for the `RMS_NORM`+`MUL`+`ROPE` fusion, whose shared array is two blocks wide.
- **Context checkpoints:** spacing and placement affect host memory (up to `--ctx-checkpoints` states per slot) and prefill batching; every additional cut costs one more pass over the offloaded experts.
- **Removed compatibility:** clients, router presets, service overrides and build scripts must use current names; removed aliases now fail as unknown options, are ignored as environment variables or return 404 as routes. Reintroducing a name requires adding it in `common/arg.cpp`, `server.cpp` or CMake and documenting it in the CODE and MANUAL variants. Update the README only when its overview or installation command changes.
- **Monitor:** the snapshot is built on the main loop, the only thread that may touch the contexts; a buffer allocated outside `mgs_get_memory_breakdown` (a new cache or pool) shows up as "other" until a breakdown call reports it. Never route the monitor through the task queue: it would reset the idle timer and wake sleeping models. The router aggregation relies on the child contract (`/api` prefix, no API key). New fixed or bottom-anchored UI elements must add `--status-bar-height`.
- **Shell MCP server:** anyone who can use the API (or open the UI) can run commands as the service user, so it is only for trusted environments and should be combined with an API key. Changing the route, the `shell_mcp_server` property or the `mgs-shell` identifier affects the UI synchronisation and stored settings; changing the Origin or Content-Type checks reopens cross-site command execution; changing `fRunCommand` affects process-group cleanup, timeouts and output limits; changing the JSON fields of `mToolsCallResult` affects what the model reads and `fParseLocalShellResult`, which then shows the whole result as stderr text, and the `result` lines of the call logs; changing `cCallLogFolder`, the file name or the 0700/0600 modes of `server_shell_mcp_call_log` moves the call logs or exposes command output to other users.
- **Web UI settings:** the document is shared by every browser and the last save wins; a save always sends every section, so a store that keeps settings outside `cUiSettingsStore` would lose them on other browsers. Saving before the document loads would overwrite the file with a partial state, which `mSet` prevents. Renaming a section or a config key leaves the old value unread (no migration). The file can hold MCP headers, hence mode 0600; anyone with the API key can read it through the API.
- **Models folder:** `--models-dir` must keep priority over the saved section `modelsFolder` (explicit options prevail), and a missing `--models-dir` must still stop the server; a saved folder that disappeared only leaves the list empty. `mSetModelsFolder` reloads the list, which unloads the running models of the previous folder, and `POST /api/models/folder` waits for that. `fRemoveDenseModels` reads the header of every GGUF of the folder on each reload (`GET /api/v1/models?reload=1`, or choosing a folder in Settings → Models, the same one included) and must apply the same rule as the MoE-only check of `mgs_server` (`load_mtp` off). The server writes `modelsFolder` into `ui-settings.json` and the interface copies the same value into its document with `cUiSettingsStore.mSet`: without that copy, its next save (of any setting) would write the previous folder back; a browser with an older copy of the document can still do so, as with every section (the last save wins). Renaming the fields of `load`, `path` or `file_size` affects `SettingsChatModelsTab` and API clients. `GET /api/models/folder/browse` lists the folders that the user running `mgs` can read, anywhere on the computer, behind the API key like every route; it returns folder names and a count of `.gguf` files, never other file names, and the interface has no other way to set the folder, so renaming its fields affects `DialogModelsFolderPicker`.
- **sudo password prompts:** the password crosses the browser, the API (HTTPS and API key) and the abstract socket; changing `fParentIsSudo`, the `SO_PEERCRED` check or the token lookup lets a command read the password with a fake prompt; changing `fServerShellMcpAskpassMain` or its position at the start of `mgs_server` breaks the helper or makes ordinary runs of `mgs` inside a command act as it; changing `cAskpassDisplay` or the condition that sets `DISPLAY` makes sudo stop using the helper; starting commands without a session of their own (`POSIX_SPAWN_SETSID`) makes sudo prompt on the terminal that started `mgs` instead; unmounting `DialogLocalShellAskpass` from the root layout leaves the prompts unanswered until they expire; changing `mgs/callId` affects `cMcpStore.mExecuteTool` and the polling of the UI; logging the request bodies of `/mcp/shell/askpass` would write passwords to the logs.
- **Request queue:** the default of one slot gives every request the whole context; raising the default of `-np` (or bringing back an automatic mode) splits the context among the slots and shortens long answers. The `mgs_queue` events only reach requests marked with `mgs_client: "webui"`: sending them to other clients, or in the Anthropic Messages or OpenAI Responses streams, would break their parsers. Every streaming handler must accept a `server_task_result_queue` as its first or a later result, and every new deferral path must go through `mDeferTask` so the waiting requests keep their positions. A requeued task keeps its place (`vQueueOrder`, assigned the first time `mDefer` sees it) and a released slot takes the first task in arrival order that can use it; changing `mDefer` or `mPopDeferredTask` breaks the arrival order the API promises.
- **Shutdown:** the task loop stops before the HTTP server, and stopping the HTTP server waits for every request thread, so an HTTP thread that waits for the loop must use the request's `vShouldStop` (or `fServerHttpIsStopping`): a wait that only watches the client keeps the process alive until systemd kills it (`TimeoutStopSec`, 90 s by default for `moe-gguf-server`). The signal handler must stay async-signal-safe; anything that takes a lock belongs in the shutdown handler, which runs on its own thread. The abort callback of the contexts is only for the shutdown: an aborted decode drops the positions of its ubatch from the memory module, and since the scheduler checks the callback between splits, any user of `mgs_set_abort_callback` now stops at the next split, also on GPUs.
- **Removed architectures:** Gemma 4, every DeepSeek architecture older than V4.1, the 85 `llm_arch` entries that could not load, the DFlash, DSpark and Eagle3 draft architectures and the Gemma 3 projectors are gone; reintroducing one means restoring its arch entries, tables, graph, vocab and chat pieces and adding it back to `RulesForThisProjectOnly.md`. GGUFs of other models converted as `deepseek2` (Kimi-K2.x, GLM-4.7-Flash and others) no longer load. Version 0.1.38 also removed every MoE architecture outside the supported families and Flint, with their tensors, KV keys, size labels, chat handlers and the engine code that only they reached.
- **MoE-only check:** `fMgsModelIsMoe` is the only definition of a loadable model. `mgs_model_file_is_moe` must read the counts as the loader does (architecture name of the file, DeepSeek-V4.1 translation, KV overrides of type int); otherwise the server either rejects a model that the engine would load or lets a dense model reach `--fit` and fail twice. Removing an architecture leaves its dense models rejected as dense and its MoE models as unknown.
- **Shared DSV4 pieces:** `ggml_dsv4_hc_pre`, `ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_comb`, `ggml_dsv4_hc_post`, `ggml_lightning_indexer`, `vDsv4HcMult`, `aDsv4CompressRatios` and the fused hc cparams serve Kimi-K3, GLM-5.3-Flash, Qwen3.8 and DeepSeek-V4.1; a change there affects the four. With Vulkan they run on the device (back on the CPU only without fp16 for the indexer, or without 16-lane subgroups with shuffle for `ggml_dsv4_hc_comb`).
- **Down-projection rescale (`ggml_amax_pow2`):** the CPU (`fGgmlAmaxPow2F32`), CUDA (`fAmaxPow2`) and Vulkan (`amax_pow2.comp`) versions must give the same factor. It goes into the expert weights only without a down bias and outside the hybrid branches; moving the weighting away from the down projection breaks the `MUL_MAT_ID` + `MUL` fusion. A new architecture whose down input exceeds F16 is added to the condition in `mBuildMoeFfn`.
- **RoPE pattern (`aRopePattern`):** it starts at 1 for every layer; a model that clears a layer must skip RoPE for it in its graph, and `mBuildGraphShift` skips it in the K-shift.
- **Hybrid index memory:** shared by qwen4exp and glm5-next; KV cells store token ids and `seq_pos` holds (position, cell) pairs, which the n-gram embeddings and the state restore rely on.
- **External tensors:** `cTensorExternal` tensors are never allocated and prefetching stops at the first one; code that walks tensor data (quantization, saving, memory reports) must skip them. The Engram rows need a POSIX `pread` on the model file during the whole run.

Project-specific rules prohibit writing or running tests. Review is static and does not establish runtime, GPU, remote installation or mobile overflow correctness. `tests/` is reserved without executable tests.

Later integration (2026-11-02, version 0.1.37): Flint (#30928) with the Jinja `\xHH` escapes (#30929), a K-shift that skips the layers without RoPE and the down-projection rescale of #30861 (with the 1024 threshold of #30928) as the single op `ggml_amax_pow2`. Measured with Flint-40B-A2.5B Q8_0, a 2,055-token prompt and 128 greedy tokens: on the CPU the next-token probabilities of mgs and llama.cpp 785322d17f2d are identical; with the RTX 4060 Ti (CUDA, experts in RAM with the expert cache) mgs processes the prompt at 615 t/s and generates 26–27 t/s, against 154–167 t/s and 22–23 t/s of llama.cpp with `-t 8` (its 16 default threads gave 7 t/s and `--moe-cache-mib 8192` 14 t/s); with the Radeon 860M (Vulkan) mgs reaches 199–205 t/s and 19 t/s, while llama.cpp does not load the model by default or with `--n-cpu-moe 30` (RADV runs out of memory for command submission, `ErrorDeviceLost`). On Vulkan `TOPK_MOE_SIGMOID_NORM` raised generation by 4 % and the fused rescale costs 2–3 % of it; with CUDA the rescale costs nothing measurable.

The multi-token CUDA fusion intentionally covers only operations already available in this fork; it did not introduce SWIGLU_CLAMP, which arrived later with GLM-5.3-Flash (#27930). GLM automatic MTP still requires a complete GGUF trunk/head and exactly one head. The UI initialisation refactor was unnecessary because this fork initialises persisted settings synchronously; only the user-settings preservation fix was ported.

Deferred: CPU tiled K/IQ matmul (#27851) needs the newer workspace/quant-block integration; weighted expert reduction and unconditional top-k fusion (#25952/#28432/#28422) need the CUDA side of the allocator dependencies (the scheduler and the Vulkan top-k fusions already use them); Metal work (#28301/#28948) needs its reorganised kernels/fusion infrastructure; OpenCL MTP dispatch (#27637) needs newer binary kernels.
