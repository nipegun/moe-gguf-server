## Architecture and decisions

**MoE model loading and MTP priority.** The engine compiles an explicit source list in `backend/src/CMakeLists.txt`. Dense-only decoder implementations are removed. Shared graphs belong to the MoE implementations that use them (including Phi-MoE, Granite, Nemotron, Ernie and Nomic); dense blocks inside a MoE model remain necessary. `mgs_model_create` checks the expert count before loading weights and rejects dense main models. A head-only GGUF explicitly loaded as MTP is the exception: a dense prediction head can serve a MoE target. Qwen35 retains only its MTP graph.

MTP placement considers every selected GPU, accounts for backend allocation sizes and alignment, and includes the output head (or its tied token embedding). It first looks for a GPU that can hold all heads; otherwise it places the largest groups across GPUs. A group falls back to RAM only when no selected GPU can hold it. The separate `dMtpContexts` are allocated and uploaded before trunk contexts; tensor overrides cannot replace that placement. External MTP weights are preloaded before the target, including with `--fit off`, and transferred into speculative initialisation without loading a second copy. The fit estimate reserves their context/compute memory without counting their already allocated weights twice.

**Source conventions and CLI validation.** Project identifiers use CamelCase with the function, method, parameter and value prefixes specified by the project rules. Public C APIs, GGUF names, protocol fields, third-party names and framework-required callback/component names retain their contracts. C++ formatting uses two spaces. The naming also covers the preprocessor branches that no Linux build compiles (Windows, macOS, debug macros, `MGS_LLGUIDANCE`, `#if 0`): the compiler cannot catch an old name there, so any rename must be checked in those branches by hand. `--chat-template-kwargs` rejects `vEnableThinking`; use `--reasoning on` or `--reasoning off`. Option spellings with underscores are not rewritten, and repeated options are rejected except for the explicitly repeatable `--spec-type`. `Github-Repo-Push.sh` uses `set -euo pipefail`, `fCleanup`, its EXIT trap and an explicitly checked `fMain`; every failed publication step stops the script.

`frontend/` contains the UI; `backend/` the engine, server and dependencies;
`deploy/` installers, services and asset scripts; `build/` the local
self-contained build script and its relocatable launcher; `doc/` documentation; `_/` local working material. Imported dependencies are preserved.

The Svelte interface lives in `frontend/`, the C++ engine/server in `backend/`, and installation in `deploy/`. The engine retains the relative relationships between `src/`, `common/`, `include/`, `ggml/`, `vendor/` and `tools/`. The CMake entry point in `build/CMakeLists.txt` delegates to the backend; the UI library is built from `frontend/` and embedded in the executable. The CMake targets are `mgs-engine` (the engine library, `backend/src/`), `mgs-common-base` and `mgs-common` (`backend/common/`), `mtmd`, `server-context` and `mgs-server-impl` (`backend/tools/`), `mgs-ui` (the embedded interface) and the executable target `mgs`; both build output and installation use `mgs`.

**Naming.** The code inherited from llama.cpp uses the project's own names: the public C API of `backend/include/mgs.h` and `mgs-cpp.h` uses the `mgs_` and `MGS_` prefixes, the engine sources are `backend/src/mgs*.{h,cpp}`, the server entry function is `mgs_server`, environment variables are `MGS_*` (`MGS_ARG_*`, `MGS_API_KEY`, `MGS_CACHE`, `MGS_MOE_CACHE*`, `MGS_SERVER_*`), CMake options are `MGS_*`, the Prometheus metrics are `mgs:*`, the CORS proxy header prefix is `x-mgs-proxy-header-`, the browser storage uses `MgsUi`, the download cache is `~/.cache/mgs/` and the tinyBLAS CPU kernels are `GGML_TINYBLAS` in `ggml-cpu/tinyblas/`. The remaining `llama` spellings are deliberate: the llama.cpp licence notices (`LICENSE`, `build/licenses/LICENSE-llama.cpp`) and the README tagline; mentions of the upstream project as such (provenance, comparisons), without links to its repository; values stored inside GGUF files (the SentencePiece tokeniser model `llama` and the `llama-bpe` and `llama4` pre-tokenisers, with their `cMgsVocabPreTypeLlama3`/`LLAMA4` identifiers and `fUnicodeRegexSplitCustomLlama3`); names of third-party models and code in comments (CodeLlama, Llama-3_1-Nemotron, LLaDA, the Ultravox model and the `LlamaYaRNScaledRotaryEmbedding.py` YaRN reference implementation); a bibliographic reference in the tinyBLAS sources; the `APIR_LLAMA_CPP_*` variables of the virglrenderer API remoting used by the virtgpu backend; and Spanish words such as «llamada». Meta's Llama architectures (`llama`, `llama4`, `llama-embed`), their built-in chat templates and the Llama 4 vision projector were removed.

HTTP registration applies the API prefix to each published route. Handlers receive canonical paths without the prefix; the router adds `/api` when forwarding to model children. Public authentication allowlists use complete external paths. The UI stays at `/`; `/api/config.js` publishes the prefix before application modules load. Swagger and OpenAPI live under `/api/doc/`, including during model loading. The route/method registry supplies the live inventory; completion parameters come from `server-schema`.

JSON catalogues hold interface translations for 15 locales: `de-DE`, `en-GB`, `en-US`, `es-AR`, `es-ES`, `fr-FR`, `he-IL`, `hi-IN`, `it-IT`, `ja-JP`, `ko-KR`, `pt-BR`, `pt-PT`, `ru-RU` and `zh-CN`. `aLanguages` and `dCatalogs` register them in locale-code alphabetical order; `en-US` remains the default and message fallback. Each catalogue includes the localised names of all 15 languages. `fTranslate` interpolates named values without modifying conversation data. The new translations use count labels in deletion/import messages instead of interpolating English plural suffixes. Changing language saves it in the server's settings document and reloads the interface so labels calculated at module import also change; `/api/config.js` publishes the saved language before the modules load, and `?lang=` in the URL overrides it. The root layout sets the HTML language and direction (`rtl` only for Hebrew); navigation uses logical positioning, chat input and plain user text use `dir="auto"`, and code/terminal text stays left to right. Framework contracts, protocol fields and imported symbols retain their original names; project-owned functions follow the required naming prefixes.

**Documentation languages.** The README, MANUAL and CODE documents exist in the same 15 locales as the interface: `README.md` (en-US) is in the root and its translations are `doc/README.<locale>.md`; the manual and this guide are `doc/MANUAL.md` and `doc/CODE.md` (en-US) and `doc/MANUAL.<locale>.md` and `doc/CODE.<locale>.md`. Every variant opens with a language bar that links all the others in locale-code alphabetical order. Headings carry the same `<a id>` anchors in every language, so links between documents (such as `MANUAL.<locale>.md#local-build`) work in all of them. Code blocks, commands, paths, options and identifiers are identical in every translation; only the prose changes. The Hebrew variants are plain Markdown: GitHub and Gitea detect the direction of each paragraph, so the text reads right to left while code blocks stay left to right.

Installation requires root, handles command failures explicitly and stages only under `_/temp/`. The UI is built locally instead of downloading an upstream interface lacking project changes. Deployment creates unprivileged inference and web services. Its dedicated Apache instance searches HTTP ports from 11080 and HTTPS from 11443 on every startup; inference stays on loopback:8080. No HAProxy is configured. The program's configuration lives in `/opt/moe-gguf-server/.mgs/config/`, the `~/.mgs/config/` of the service account, owned by it with mode 0600: `api.key`, `web-domain` and `apache2.conf.in` (the Apache `ServerRoot`), written by `configure-web.sh`, and `ui-settings.json`, written by `mgs`; only the system integration (systemd or OpenRC units) stays under `/etc`. Conversations live in the browser; there is no backend user database.

The server itself enables HTTPS by default: `common_params` starts at 11443 and `server_http_context` binds the first free port, followed by HTTP from 11080. The second listener returns 308 to the selected HTTPS port, preserving host, path and query, with `Cache-Control: no-store`. `--port` fixes the main port (0 delegates to the OS); `--http-port` changes the HTTP search start. Only address-in-use conflicts advance the search; other errors stop startup. `server-tls.cpp` loads the supplied PEM pair or, without one, the self-signed identity of `~/.mgs/certificates/` (`fPersistentServerIdentity`): it reuses `fullchain.pem` and `privkey.pem` while they match and the certificate has not expired, and otherwise generates an ECDSA P-256 certificate (365 days, SANs for localhost, loopback, the configured host, the machine name and the addresses of its interfaces) and saves it through temporary files and renames (folder 0700, key 0600), so every run and every build serves the same certificate and browsers keep their trust exception. No external command is invoked; if the folder cannot be written, the run uses its identity from memory. Without OpenSSL support, HTTPS fails explicitly. `--http` selects deliberate plain HTTP, used by router children and the Apache backend on 8080; Unix sockets and Vertex AI retain HTTP. The destructor stops and joins both listeners. These decisions live in C++, independently of installers and launchers.

`build/build-local.sh` covers manual use on a workstation: it needs no root, installs no packages or services and leaves nothing running. It copies a complete local source tree or downloads the GitHub `main` archive without Git when invoked through `curl | bash` or as a standalone script, builds the `mgs` target in `/tmp/moe-gguf-server-build.XXXXXXXX/` and installs a relocatable, self-contained copy under a prefix (default `~/.local`, only for the current user; `--prefix` changes it): `bin/mgs`, `lib/mgs/` and `share/doc/mgs/licenses/`. `lib/mgs/` holds the server binary, its transitive `ldd` closure, the glibc dynamic loader and the NSS modules that glibc opens with `dlopen`. The kernel only honours an absolute `PT_INTERP`, so `bin/mgs` is a static launcher (`build/mgs-launcher.c`) that reads `/proc/self/exe`, goes up from `bin/` to the prefix and executes `lib/mgs/<loader> lib/mgs/mgs` with the remaining arguments; nothing in the prefix depends on its absolute location. The server binary and bundled libraries carry `DT_RPATH` `$ORIGIN`, deliberately chosen because it outranks `LD_LIBRARY_PATH`. Since the server's process image is then the loader, the launcher exports `MGS_EXECUTABLE` and `fGetServerExecPath` returns it, so router children re-enter through the launcher. NVIDIA driver libraries (`libcuda`, `libnvidia-*`) are never bundled because they must match the kernel module. A marker file inside `lib/mgs/` prevents replacing an installation that the script did not create.

Each local run uses a fresh private directory from `mktemp -d /tmp/moe-gguf-server-build.XXXXXXXX`. The downloaded archive, its member list, copied or extracted sources, CMake output, npm/Node/CUDA caches, scratch files, the log and the assembled `bundle/` stay there. Automatic compiler caching is disabled (`GGML_CCACHE=OFF`, `CCACHE_DISABLE=1`), so no cache server survives the build. Once the artefacts are ready, the script locks the prefix directory itself with `flock`, copies the finished files to temporary entries next to their final places, then renames them into place on the same filesystem. `fCleanup` waits for the log writer and removes the private workspace on success, failure and handled INT/TERM/HUP signals. No build files are written into the source tree or `/opt/`; the local builder has no `--build-dir` option.

The entry script path is captured with `${BASH_SOURCE[0]:-}` before calling `fMain`, so stdin execution also works with `set -u`. Options are parsed before source discovery; `--help` needs neither a source tree nor a source download. `fHasProjectSources` checks the build entry points, launcher, frontend manifests and licence directory. A complete local copy is staged with the existing exclusions. Otherwise, `fDownloadSources` requires existing curl/gzip, downloads over HTTPS with retries, validates the archive paths and extracts into the private `source/` directory before checking the required files. `fMain` runs with stdin redirected from `/dev/null`, so build tools cannot consume the piped script. Remote options use `bash -s --`; packages are never installed.


The Debian entry point is standalone: it detects a complete local checkout or downloads `main` from GitHub. Remote mode uses `/opt/moe-gguf-server-source` (overridden by `MGS_INSTALL_SOURCE_DIR`), checks the source-origin marker and holds a lock across synchronisation and compilation. `rsync --checksum --no-times --delete` removes obsolete sources, preserves `_/` and gives changed files fresh timestamps. The helper runs in a separate Bash with stdin closed and without duplicating its parent log stream.

No backward-compatibility layer is kept. Deprecated CLI aliases and removed-option tombstones, duplicate long option names (each option keeps one short and one long name), `MGS_ARG_NO_*` environment fallbacks and environment variables named after former options, legacy HTTP route aliases (`/completion`, `/embedding`, `/reranking`) and duplicate request fields (`thinking_budget_tokens`, `content` in the embedding routes), the `deepseek-legacy` reasoning format, the non-Jinja template engine (`--jinja`/`--no-jinja`, the built-in C++ templates of `mgs-chat.cpp` and `mgs_chat_apply_template`: every chat template goes through Jinja, and `chatml` names the built-in ChatML source), old CMake variable names, browser-data migrations and installer shims were removed, so each option, route, variable and stored value has a single current name. Because the project has never been deployed, the public mgs/GGML/mtmd C APIs keep no deprecated symbols either: only their current functions remain (the removed ones are listed in [MANUAL.en-GB.md](MANUAL.en-GB.md#removed-compatibility)). The exceptions are deliberate: loading GGUF files through fallbacks that current conversions or the most downloaded published GGUFs of the supported families still depend on, checked against their headers on Hugging Face (the Qwen3.6 recurrent layout derived from `full_attention_interval` and the built-in GLM-5.2 indexer layout for GLM-5.2/5.3 files without `attention.indexer.types`), toolchain and operating-system version guards, and interoperability with external protocols (OpenAI, Anthropic, TEI/Jina, GCP Vertex, MCP) and with external peers such as the virglrenderer guests of ggml-virtgpu. Old-file shims were removed: Grok-1, MiniCPM, the unsplit `attn_kv_b` (non-MLA) path of Kimi-Linear, the `ssm_in` path of Qwen3-Next, missing `expert_gating_func`, `rope.scaling.finetuned` and `full_attention_interval` keys, the scalar SWA period of Cohere2-MoE, missing pre-tokenisers and Kimi-K2 merges, the `llama3`, `llama-v3`, `jina-es`, `jina-de` and `llada-moe` pre-tokeniser names, `rope.scale_linear`, early Gemma 2, GGUF versions 1 and 2, the old `tokenizer.ggml.prefix/suffix/middle_token_id` keys, and in `mtmd` the projectors of the old one-off scripts (`mlp`, `mlp_norm`, `ldp`, `ldpv2`, `resampler`, `adapter`, files without a projector type), the swapped FFN of old surgery conversions and the defaults for missing Kimi-K2.5 and Step3-VL keys. Whole architectures were also removed by decision of the user: Gemma 4 and every DeepSeek architecture older than V4.1 (see the supported families below).

Configure manually with `cmake -S build -B _/temp/cmake` from the project root. Build scripts stage `build/` alongside the sources and select `source/build` as the CMake source directory. Deploy scripts keep generated files under `_/temp/` and reset `CMakeCache.txt` and `CMakeFiles/` if a cached configuration points to another source directory. The local build always uses a fresh disposable workspace under `/tmp/`. The TLS library of cpp-httplib is chosen in `backend/vendor/cpp-httplib/CMakeLists.txt` from the options declared in `backend/CMakeLists.txt`: `MGS_BUILD_BORINGSSL` and `MGS_BUILD_LIBRESSL` (both off) download and build that library, and take precedence in that order over `MGS_OPENSSL` (on, the system OpenSSL); with none of them the server has no HTTPS.

**Version.** The project version is defined once, as `MGS_VERSION` in `backend/cmake/build-info.cmake` (starting at `0.1.0`), and every change to the project raises its patch number (0.1.1, 0.1.2, ...). The local build and the Debian installer configure the same CMake tree, so both produce the same version: CMake prints `mgs version: …`, `build-info.cpp` returns it from `mgs_version()`, and it also sets the file versions of the shared libraries (the soname stays `.so.0`), `mgs.pc`, `mgs-config.cmake` and the interface's `build.json`. The project does not use Git, so there is no build number or commit: `--version`, the `build_info` property of `/api/props`, the OpenAI `system_fingerprint`, the shell MCP `serverInfo.version` and the download `User-Agent` (`mgs/0.1.0`) all report this version. `deploy/scripts/ui-assets.cmake` rebuilds the interface when `build.json` holds another version, so a version change reaches a reused `_/temp/` build tree without touching the interface sources.

Formatting configuration is scoped to folders: `.clang-format` is present in `backend/`, `frontend/` and `build/`; `.editorconfig` is present in those folders plus `deploy/` and `tests/`. Licence notices in `build/licenses/` inherit `build/.editorconfig`. Keep equivalent settings in sync. Files in the project root and `doc/` require editor settings for UTF-8, LF and two-space indentation.

The `doc/` folder contains reading documentation. The Swagger page lives in `frontend/api.html` and CMake embeds it in the server. The backend generates `/api/doc/openapi.json` from registered routes on each request; there is no static `openapi.json` source file.

The fork retains llama.cpp's server, multimodal support and GGML backends, with
MoE optimisations for weights split between GPU memory and system RAM. Host
registration and expert prefetch derive from
the `fable5/host-register` and `fable5/prefetch-experts` branches of
thecodacus's fork.
The prefetch slots hold gate/up/down expert tensors and overlap their transfers
with computation. Automatic MTP checks `nextn_predict_layers`, the model trunk
and all integrated heads before selecting `draft-mtp`; the checks include every
GGUF shard. See the [manual](MANUAL.en-GB.md#performance) for tuning and limitations.

**MoE expert cache.** `backend/src/mgs-expert-cache.{h,cpp}` keeps the most recently used experts of
every layer whose experts stay in system memory in one device pool per GPU shared by the layers assigned to it (one LRU list per
group of layers of the same GPU with identical per-expert tensor types and shapes). A slot holds every per-expert tensor of one
expert: weights, biases and per-expert scales, with separate or merged gate/up projections. For micro-batches
below the op-offload limit (32 tokens, `GGML_OP_OFFLOAD_MIN_BATCH`), `mBuildMoeFfn` builds the expert chain
twice: a device branch that reads the pool through slot identifiers and a CPU branch that reads the host
weights. A CPU partition operation (`mPartition`) runs first: it counts the hits, uploads a bandwidth-balanced
share of the misses (about m·B_upload/(B_upload+B_cpu), at least one) and queues the slot identifiers and the
uploads on the device stream before the device branch; the CPU branch then computes the remaining misses at the
same time. Experts handled by the other branch get identifier -1 on the CPU (the CPU `mul_mat_id`/`add_id`
kernels skip them and write zeros) and an empty slot on the device (position k uses empty slot k, so no slot
repeats within a token, as the CUDA MMQ helper requires), so the sum of both branches equals the regular
execution up to rounding. The scheduler only synchronises an input-free split with the previous split when that
split had copied inputs or its backend can access the current buffer type; this keeps the fix of upstream
#26040 and lets both branches overlap. The upload bandwidth is measured at creation with real experts and the
CPU bandwidth is estimated online from the CPU branch duration. Large micro-batches keep the expert prefetch:
`ggml_backend_sched_set_weight_upload` lets the cache copy its experts device-to-device into the prefetch slot
and upload only the others from host memory. The cache takes the device memory left after the context minus
`--moe-cache-reserve` and the prefetch slots. It is created by the first request after every context and
projector is loaded (the common warmup defers it), can be resized at run time (`mgs_set_expert_cache_size`,
`POST /api/expert-cache`) and reports its counters through `mgs_get_expert_cache_info`, `/api/expert-cache`
and `/api/metrics`. Settings travel through `MGS_MOE_CACHE*` environment variables, set by the
`--moe-cache*` options, which keeps the public API unchanged. With the cache enabled and enough
RAM, `--fit` keeps every expert in system memory and leaves the free device memory to the cache, because an LRU
cache serves decoding better than whole static expert layers; with several GPUs it spreads the dense-only layers
over them by memory target, so every GPU caches the experts of its own layers. The upload bandwidth is measured
per GPU, a requested size is split among the GPUs by the host experts they cache, and the cache stays off with
pipeline parallelism, which keeps several micro-batches in flight. `--fit` also counts the nextn (MTP) layers, which
the loader numbers among the layers it offloads; otherwise the first layer stayed on the CPU when MTP was off.

**Context size with `--fit`.** Step 2 of `fCommonParamsFitImpl` reduces a context that the user did not set as
if every weight had to fit in device memory, so a model larger than the devices always fell to `--fit-ctx`
(4096 tokens) even though its experts then stay in system memory, and reasoning answers were cut off. Once the dense weights fit, `fRaiseContext` measures the dense-only placement at
the reduced and at the training context, interpolates linearly and raises the context (rounded down to 256 and
checked with one more measurement) until the KV cache and the buffers that grow with it take at most a quarter
(`cContextShare`) of the device memory left after the dense weights. It runs after the placement with every
expert in RAM (expert cache) is chosen and before whole expert layers fill the devices, so the experts always
keep at least three quarters of that memory. An explicit `--ctx-size` is never changed, `--fit-ctx` stays the
minimum, and nothing changes when the KV cache lives in system memory. The draft context takes the context size of
the target (`vParamsDft.n_ctx = n_ctx` in `mLoadModel`): with a context size of 0 it used to allocate its KV
cache for the training context of the model, which took device memory from the expert cache.

**Automatic configuration.** `mgs --model FILE` has to pick the fastest settings for the machine by itself;
explicit options always prevail. With experts in system memory, every micro-batch of a prompt streams the experts
that are not on the device over PCIe (about 2 s per micro-batch for Qwen3.6-35B-A3B Q8_0 on an RTX 4060 Ti), so
prompt speed grows almost linearly with the micro-batch while generation does not depend on it: a 2514-token prompt
went from 215 tokens/s with 512 to 408 with 2048 and 737–755 with 4096, with the same generation speed. Before the
context is raised, `fRaiseBatch` tries micro-batches of 4096, 2048 and 1024 tokens at the chosen placement and keeps
the largest whose extra memory stays within an eighth (`cBatchShare`) of the device memory left after the dense
weights; the logical batch grows with it. It only runs when `-b`/`-ub` (or their variables) were not given
(`common_params::vBatchExplicit`, passed as `pAutoBatch`). `common_init_result` copies the resulting `n_batch` back
into the parameters, because the draft and MTP contexts copy them and take every target batch into a buffer of
their own `n_batch`; their micro-batch keeps its default. The default CPU thread count (`fCommonDefaultThreads`,
applied by `fPostprocessCpuParams` when `-t` is absent) is the number of cores useful for maths, capped at half of
the logical CPUs of the process affinity mask: the CPU share of MoE inference is bound by memory bandwidth, and
using every logical CPU of a virtual machine without visible SMT made the workers compete with the thread that
drives the GPU (16 vCPUs: 4 to 12 threads within noise of each other, 16 threads 13% slower). With visible SMT the
cap equals the physical cores, so bare-metal machines keep the previous default. `common_init_result` logs the
thread counts; `--fit` logs the micro-batch and context it chose.

**MTP placement.** MTP weights live in device memory ahead of every other placement rule: the nextn layers
grafted onto a model, every layer of an MTP-only GGUF passed with `--spec-draft-model`.
`mgs_model_base::mLoadTensors` assigns their layers and the output layer to a GPU even when `n_gpu_layers`
leaves them on the CPU, and `mgs_model_loader::mCreateTensor` ignores the overrides that send them to host
memory (`--fit` partial layers, `--cpu-moe`, `--n-cpu-moe`, `--override-tensor` and their `--spec-draft-*`
equivalents). The token embeddings stay on the CPU like those of the trunk, because a row lookup gains nothing on
the GPU. When the MTP layers do not fit in the free memory of the device with a 512 MiB margin, the regular
placement applies. `--fit` measures by loading the model without allocating it, so it sees the MTP weights on the
device and fits the rest around them; the expert cache takes what remains. With a separate MTP GGUF,
`fCommonModelParamsToMgs` leaves the MTP layers grafted onto the target unloaded instead of keeping an unused
copy.

**Supported families.** The MoE families that must work are Qwen3.6 (`qwen35moe`), Qwen3.8-Flash-Next (`qwen4exp`), GLM-5.3 (`glm-dsa`), GLM-5.3-Flash (`glm5-next`), Kimi-K3 (`kimi-k3`), DeepSeek-V4.1-Flash (`deepseek41`), MiniMax-M3 (`minimax-m3`), Nemotron-3 (`nemotron_h_moe`) and MiMo-V2.6 (`mimo2`). By decision of the user, Gemma 4 (`gemma4`, `gemma4-assistant`, the `gemma4v`, `gemma4uv`, `gemma4a` and `gemma4ua` projectors and the `peg-gemma4` chat format) and every DeepSeek architecture older than V4.1 were removed: `deepseek`, `deepseek2` (which Kimi-K2.x, GLM-4.7-Flash, Moonlight, GigaChat3, Kanana-2, Mistral-Large-3 and Youtu also used), `deepseek2-ocr` with the `deepseekocr` projectors, `deepseek32`, `mistral4` and `deepseek4`. Their GGUFs are rejected as unknown architectures.

**Kimi-K3 (`models/kimi-k3.cpp`).** KDA linear-attention layers (full-rank gate `ssm_g` with a bounded-sigmoid decay, the shared `fBuildGdnL2Norm` and the per-channel gate of `mBuildRecurrentAttn`) alternate with MLA layers in the absorbed `k_b`/`v_b` form with a sigmoid output gate. A cross-layer residual mix built with `ggml_dsv4_hc_pre` reads `attn_res_score`, `ffn_res_score` and `output_res_score`. The MoE is latent: the router works at full width and the 896 experts at the latent width (`ffn_routed_down` → experts → `ffn_routed_norm` → `ffn_routed_up`), with the `situ` activation (`cLlmFfnSitu`) handled in `mBuildMoeFfn`; `MGS_MAX_EXPERTS` is 1024 for it. The recurrent state supports rollback (`n_rs_seq`). Published GGUFs carry no MTP. The chat template uses `<|open|>`/`<|sep|>`/`<|close|>` and is parsed by `fCommonChatParamsInitKimiK3`; the tokeniser keeps the `kimi-k2` pre-tokeniser.

**GLM-5.3-Flash (`models/glm5-next.cpp`) and `glm5v`.** KDA layers and nope-only MLA layers with the k-pool DSA indexer (`indexer_kpool_gate`, `indexer_kpool_ape`), hyper-connection streams with the fused hc ops and a DeepSeek-style MoE with `ggml_swiglu_clamp`, a new op (CPU, CUDA and Vulkan) that keeps the CUDA mat-vec + GLU fusion during decoding. The NextN block is a DSA layer: MTP turns on with only `--model` and its weights take the VRAM-first placement. Memory is `mgs_memory_hybrid_idx`. The `glm5v` projector reuses the glm4v graph with an optional post-conv norm, a clamped SwiGLU, its own preprocessor and `<|begin_of_image|>`/`<|end_of_image|>` markers. The `glm4` and `glm5` pre-tokenisers use ChatGLM4 with `ignore_merges`.

**Qwen3.8-Flash-Next (`models/qwen4exp.cpp`).** A low-rank hyper-connection mixer and combine (`ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_post` with identity mixing), n-gram hashed per-layer embeddings whose table `per_layer_token_embd` (about 29 GB) stays mapped and is read on demand with row prefetch, a dilated conv history in the recurrent cache (`cache_ple_r_l`), gated delta-net layers with rollback, QSA block-sparse attention layers (k-pool indexer cache, `ggml_lightning_indexer` scoring, a top-k selection mask on top of the KQ mask, computed with dense flash attention because the upstream sparse kernels are not ported), MoE with a gated shared expert, IMROPE and an MTP block with its own hyper-connection mixer and draft memory. `mgs_memory_hybrid_idx` (`mgs-memory-hybrid-idx.{h,cpp}`) combines the KV cache, the recurrent cache and the k-pool indexer cache for qwen4exp and glm5-next; KV cells record the token id (`vTok`) for the n-gram lookups and `seq_pos` is a set of (position, cell).

**DeepSeek-V4.1-Flash (`models/deepseek41.cpp`, `mgs-kv-cache-dsv41.{h,cpp}`).** Two published layouts declare this architecture: antirez's DwarfStar files (keys taken from the Hugging Face configuration such as `deepseek41.hidden_size`, a `deepseek41.config` JSON string and an I8 Engram table of E4M3 values with E8M0 scales, 264 bytes per row) and the files of the llama.cpp ecosystem (standard keys, Engram table in a ggml type). `fMgsDeepseek41AdaptMetadata` translates the first layout into the standard keys before the model is created (scoring function → gating enum, scalar `swiglu_limit` → per-layer arrays, 40 or 43 compression ratios, Engram offsets as the running sum of primes), and the loader accepts both names of the Engram projections. Layer roles (KV source, index-key owner, top-k source) come from the tensors present. The Engram table (about 188 GiB) is created with `cTensorExternal`: it is counted but never allocated, prefetching stops before it, and the rows of every token are read with `pread` on a private descriptor (`mEngramReadRows`, decoding E4M3+E8M0 or dequantizing with `to_float`). The cache keeps one group per compression ratio (gated pooling for ratio 2, a full-length stream for ratio 1 from layer 20), index-key caches only on the key owners, and reader layers that address their source layer's storage; Engram takes the previous tokens from the raw cache cells. The graph uses lagged hyper-connection mixes (a one-hot first copy, a final collapse with the last FFN mix, no HC head), no q head norm, index keys from the latent before RoPE, top-k reuse and the two-level candidate-block pool, Engram before layers 1 and 14, and `ggml_swiglu_clamp` in the routed and shared experts. When the GGUF has no chat template, `DEEPSEEK41_TEMPLATE_SRC` (a Jinja source) is used; DSML tags carry a leading space and the server passes `reasoning_effort` (1–100) to the template. There is no MTP/DSpark and no vision. The `dsv4_*` and `lightning_indexer` ggml ops and the `vDsv4HcMult`/`aDsv4CompressRatios` hparams stay because Kimi-K3, GLM-5.3-Flash and Qwen3.8 use them; on Vulkan and Metal those ops run on the CPU.

**Context checkpoints.** Models whose memory cannot be rolled back (recurrent or SWA layers) restore from
checkpoints. They are created at the start of a batch that starts a user, assistant or tool message (the
boundaries where agents edit the context), near the end of the prompt, and at any batch once the previous
checkpoint is `--checkpoint-min-step` tokens behind (default 1024). A message boundary only cuts a batch whose
last micro-batch is at least 3/4 full, because every extra micro-batch streams the offloaded experts again.
When `--ctx-checkpoints` is reached, the checkpoint with the closest neighbours is removed, so the remaining
ones stay spread over the context.

**Monitor and status bar.** `GET /api/monitor` reports CPU usage (global, per physical processor and per logical CPU, from `/proc/stat` deltas; each logical CPU is matched by number and grouped by the `physical_package_id` of sysfs, and each processor takes its model from its blocks of `/proc/cpuinfo`), RAM (`/proc/meminfo`) and every GPU (NVML through `dlopen("libnvidia-ml.so.1")`, then every DRM card of a GPU driver that NVML did not list: amdgpu with its `gpu_busy_percent` and VRAM from sysfs, and i915, xe, nouveau or nvidia without usage, completed with the name and memory of their backend once a model uses them; display-only adapters are left out, and the UI draws no VRAM bar for a GPU without memory figures), plus the memory of the loaded models split by purpose. The memory never goes through the task queue: every posted task resets `vTimeLastTask`, so a page polling every two seconds would keep the model awake forever, and `mCreateResponse` waits for a sleeping model to wake up. Instead the main loop publishes a snapshot (`mRefreshMonitorSnapshot`) after `mLoadModel`, at most once per second while slots work and always once they are idle (the end of a request saves its prompt); the HTTP threads only copy it under a mutex, and entering sleep publishes `{"state": "sleeping"}`. The snapshot combines `mgs_get_memory_breakdown` (model, context and compute per buffer type) with `mgs_model_get_weight_breakdown` (MTP and routed-expert weights, computed once after loading because it walks every tensor) and `mgs_get_expert_memory_breakdown` (expert cache buffers and the prefetch slots of the scheduler, which the regular breakdown does not see). An MTP context on the target model shares its weights, so only its KV cache and compute buffers count; a separate MTP GGUF counts as MTP weights and any other draft model as draft weights. Host buffer types (pinned host memory of a GPU included) go to the RAM bar and device ones to their GPU, matched with NVML by PCI bus id (lower case, without the `-vN` suffix of CUDA virtual devices). `fMonitorReport` adds "other" (used memory that no segment explains: other processes, driver contexts, the projector) and the free remainder. The router parent never initialises a GPU backend, which would create a CUDA context of its own: it reads the GPUs through NVML and asks every ready child for `/api/monitor/memory` (1 s timeout), while loading and sleeping children only report their state. `GET /api/monitor/usage` (only the usage: global CPU, every physical processor without its logical CPUs, and every GPU) is also allowed while the model loads. CPU and GPU readings are shared for 750 ms by concurrent pollers; a CPU baseline older than 10 s is replaced by a fresh 250 ms interval. In the UI, `cMonitorStore` polls only while something is subscribed and pauses while the tab is hidden; the status bar reuses the report while the Monitor page is open. The page only draws usage and memory: the per-model entries of the report (state, resident memory, expert cache) stay in the API for other clients. Its cards are titled with the device label in bold (`gpu-N` and `cpu-N`, in report order, one card per GPU and per physical processor) followed by the device name; every processor card shows the system load average, and every usage meter (`MonitorMeter`, the per-core bars and the status bar) is a green bar (`--monitor-meter-free`) filled in red by the usage (`--monitor-meter-used`), apart from the categorical palette of the memory bars. The status bar is fixed at the bottom: `.has-status-bar` sets `--status-bar-height`, which the chat form, the sidebar, sticky footers and the `body` padding add, so every offset stays as before when the bar is hidden (Settings → Display). The memory bars use the eight validated categorical colours plus a neutral "other" in a fixed order (`aMonitorSegmentGroups`), so related server segments share a colour (MTP and draft weights, expert cache and prefetch). The reasoning menu sizes its entries by their content (`w-max`, names with `whitespace-nowrap`): with the global `min-width: 0` and `overflow-wrap: anywhere`, a `flex-1` name next to a hint used to be split letter by letter.

**Vulkan backend.** `build/build-local.sh --vulkan` and the Debian installer (`--vulkan`, also through `MGS_BUILD_BACKEND=vulkan`) configure `-DGGML_VULKAN=ON` with CUDA off; the shaders are compiled with `glslc` at build time and CMake needs the Vulkan and SPIR-V headers (`libvulkan-dev`, `spirv-headers`). The installer adds those packages plus `mesa-vulkan-drivers`; the local build only checks for `glslc` and turns a failed configuration into a hint naming the packages. The local bundle copies the Vulkan loader `libvulkan.so.1` through the regular `ldd` closure, while the driver (ICD) is opened by the loader from `/usr/share/vulkan/icd.d/` and loads its own system libraries (RADV pulls in LLVM, libdrm and X/Wayland client libraries); sonames already in `lib/mgs/` are shared, which is why the bundle must be built on the Debian release that runs it. The Vulkan device reports caps `async` and `events`, so the expert prefetch and the expert cache run unchanged, and its `device_id` is the PCI bus id, so the Monitor matches it with NVML or with the amdgpu sysfs card (whose generic name is then replaced by the backend description). Vulkan does not export `ggml_backend_register_host_buffer`, so mapped expert pages stay pageable: measured on an RTX 4060 Ti through Vulkan (Qwen3.6-35B-A3B Q4_K), expert uploads reached 2.7 GB/s with mmap and 13.1 GB/s with `--load-mode none` (pinned host buffers), and generation 27.5 and 36.6 tokens/s; the loader now says that no backend can pin mapped memory instead of blaming CUDA. Render nodes need the `render` group, which `configure-web.sh` grants to the service account (also `video`, idempotently on Alpine).

**Real VRAM with Vulkan.** On a discrete GPU `ggml-vulkan` counts and allocates only device-local memory (VRAM); GTT, the part of the system RAM (normally half) that AMD and Intel GPUs can map, is never counted as GPU memory, because the GPU reads it over PCIe. Three safeguards keep the model in real VRAM. Without resizable BAR the CPU-visible device-local heap is a small window (256 MiB on an RX 580) shared with the desktop, and `ggml-vulkan` used to try it first for every device buffer: the small ones (about 99 MiB, among them the MTP KV cache) landed there and the kernel evicted 67 MiB of them to GTT. When that heap is under half of the largest device-local heap `disable_host_visible_vidmem` is now set automatically, so device buffers go to the large heap (on the RX 580: 0 evicted, 872 KiB left in the window). The expert cache pools use a second Vulkan buffer type with `VK_EXT_memory_priority` 0.5 (exported as `ggml_backend_dev_get_cache_buffer_type` and picked by `fPoolBufferType`), so under VRAM pressure the driver evicts the cache before the MTP layers, the weights and the KV cache, which keep priority 1.0; the async copy checks accept any device buffer type of the same GPU (`ggml_backend_vk_buffer_is_device_of`). Finally every inference process reads `/proc/self/fdinfo` (`fMonitorDrmResidency`: `drm-resident-*`/`drm-memory-*` and `amd-evicted-vram`, published by amdgpu, i915 and xe), attaches it to its Monitor snapshot, warns once in the log when more than 64 MiB (or 2 %) of its GPU allocations are outside VRAM (`mCheckVramResidency`), and the Monitor shows the real location and a warning. `--load-mode none` is not chosen automatically: on AMD the pinned host memory counts against GTT, and 18.9 GB of experts with 16.8 GB of GTT made RADV fail with "Not enough memory for command submission" (`ErrorDeviceLost`).

**Local shell MCP server.** `--local-shell-mcp-server` turns on `server_shell_mcp` (`backend/tools/server/server-shell-mcp.cpp`), an MCP Streamable HTTP server written in C++ inside `mgs`, so the self-contained bundle needs no Python or extra packages. It is not a separate listener: it is registered as `<api prefix>/mcp/shell` on the same server as the API, so the Web UI reaches it through the same origin, TLS certificate, API key and Apache proxy from any machine, while a `127.0.0.1` port would only be reachable from the server itself. At startup `mStart` looks for `bash`, `zsh`, `sh` and `pwsh`/`powershell` in the absolute `PATH` entries and the usual directories, and exposes only the tools whose interpreter exists and is executable (`bash.run`, `zsh.run`, `sh.run`, `psh.run`). The server keeps no state: one JSON-RPC message per POST, JSON responses, no SSE stream (GET returns 405) and no session. `fRunCommand` starts the interpreter with `posix_spawn` in a new session (its own process group, without the server's controlling terminal, so sudo never prompts on the terminal that started `mgs`), with `/dev/null` as input, default signal handling (the server ignores SIGPIPE) and separate pipes for stdout and stderr read with `poll`; the timeout (default 60 s, maximum 3600 s) or a closed connection kill the whole group, and after the shell exits the pending output is read for 250 ms, so background processes cannot hold the call. Each stream keeps its beginning and its end (8+8 KiB of stdout, 4+4 KiB of stderr). Every call to a shell tool also leaves its own JSONL file, even when its arguments are rejected, (`server_shell_mcp_call_log`) in `~/.mgs/local-shell-mcp-server/` of the user that runs `mgs`, named after the local time of the call down to the millisecond (`y2026m10d12h23m59s59ms731.jsonl`, created with `O_EXCL`, so calls in the same millisecond get `-2`, `-3`…): a `command` line written before the run (tool, shell, cwd, timeout, command), then one `stdout` or `stderr` line per read with the whole output in arrival order (`fRunCommand` hands every piece to `pOutput`, and `mOutput` holds back a UTF-8 character split between two reads), and last a `result` line (exit code, signal, timed out, cancelled, seconds and the bytes of each stream) or an `error` line (a rejected call has its `command` line, with what was asked, and the `error` line). The output is never kept in memory, so the file has everything that the tool result cuts and survives a stop of `mgs` during the run. The folder is created with mode 0700 and the files with 0600, because outputs may hold secrets; a file that cannot be written only leaves a warning in the log. `mToolsCallResult` answers a JSON object (`vExitCode`, null when a killed shell could not be reaped, `stdout`, `stderr`, `signal`, `vTimedOut`, `cancelled`, `timeout`, `seconds`, `shell`, `cwd`) both as `structuredContent` and as the text block, because the UI only keeps the text of a tool result: the model reads the same JSON, and the chat splits it into boxes without guessing where one stream ends. Requests with an `Origin` header must come from a page of this server (`fOriginAllowed`, compared with `Host`/`X-Forwarded-Host`; loopback pages are accepted for the development proxy) and must use `Content-Type: application/json`, which blocks cross-site requests; clients without `Origin` depend on the API key. Like the other agent features, the option limits the default CORS origin to localhost and adds a startup warning. Router children never receive it, and the route also answers while the model loads. `/api/props` publishes `shell_mcp_server`; `cMcpStore.mSyncShellServer` (called from the root layout) adds the `mgs-shell` entry (named `local shell mcp server`, like the server's `serverInfo.title`) enabled the first time, keeps its URL on the current origin and its name, and removes it when the server stops offering it, and `MCPService.mCreateTransport` sends the UI's API key to same-origin MCP servers. Tool calls still go through the UI's permission prompt. In the chat, `ChatMessageToolCallBlock` sends the `bash.run`, `zsh.run`, `sh.run` and `psh.run` calls (`fIsLocalShellTool`: names in `aShellMcpToolNames` that no other MCP server owns) to `ChatMessageToolCallBlockLocalShell`, which keeps the tool name as title and shows the same grey monospace boxes as the Input box of the other tools: stdin with the bare command, parsed from the partial arguments while they stream, and stdout and stderr only when they have content, with the exit code in the title (`stdout (code 2):`, or `stdin (code 0):` without output); the stdin box has a white border (dark grey on the light theme), the stdout box a green one and the stderr box a red one, the same for the four tools (the `borderColor` of `SyntaxHighlightedCode` with `--local-shell-stdin-border`, `--local-shell-stdout-border` and `--local-shell-stderr-border`). A result that is not that JSON object (argument error, denied permission, failed request) is shown in the stderr box. The `expandLocalShellCommands` setting (Display) makes `ChatMessageAgenticContent.fGetDefaultExpanded` open those calls, so the boxes appear as their contents become known.

**Web UI settings.** Every setting of the interface lives in one JSON document that the server keeps in `~/.mgs/config/ui-settings.json` of the user that runs `mgs` (`backend/tools/server/server-ui-settings.cpp`: folders 0700, file 0600, written under a mutex through a temporary file renamed over the old one), so every browser shares it. `GET /api/ui/settings` returns `{"settings": DOCUMENT}` (`null` before the first save) and `POST /api/ui/settings` replaces it whole; both require the API key, are registered in every mode (the router parent serves them itself) and answer while the model loads. `/api/config.js` publishes the saved language as `globalThis.cUiLanguage` (only a valid language tag), because `i18n.ts` fixes the language at module import. In the interface, `cUiSettingsStore` (`frontend/src/lib/stores/ui-settings.svelte.ts`) loads the document when the root layout mounts and hands each section to the store that registered it: `config` and `userOverrides` (settings store), `favoriteModels` (models), `disabledToolKeys` (tools), `alwaysAllowedTools` (permissions), `reasoningEffortDefault` (conversations) and `dismissedRecommendedMcpServers` (add-MCP-server dialog); `language` is written by `fSetLanguage`, which waits for the save before reloading. `mSet` saves the whole document 300 ms after the last change, and a change still waiting is sent with `keepalive` when the page unloads. Nothing is saved before the document arrives, so a partial state never overwrites the file; a failed load is retried every 5 s, except 401/403, which waits for the API key. The server-default sync and the shell MCP entry wait for both `/api/props` and the document; an absent document is the first visit, when the `--ui-config` defaults apply once. Only the API key stays in the browser (`MgsUi.apiKey`), because it authenticates the request that loads the rest; conversations stay in IndexedDB, and the stream-resume and build-version keys in `localStorage`.

**Request queue.** The server has one slot by default (`-np 1`, `common_params::vNParallel`; the upstream automatic mode with four slots sharing a unified KV cache was removed, so `--kv-unified` is also off by default): each request gets the whole context, whether it comes from the Web UI or directly from the API, and the others wait in the deferred queue of `server_queue`, which runs them in arrival order (a released slot moves the first deferred task to the front of the task queue, `mPopDeferredTask`). `-np N` runs up to N requests in parallel and splits the context among them. The API does not depend on the interface or on its settings document; the only link is that the Web UI marks its requests with `"mgs_client": "webui"` (a `field_str` of the completion schema that sets `task_params::vFromWebui`), so the server knows the origin of every running and waiting request. When a task finds no free slot, `mDeferTask` counts the busy slots (`mCountRunning`) and the deferred tasks ahead of it (`server_queue::mDeferredTasks`), split into API and Web UI, and, when the request asked for notices (`vQueueNotice`: Web UI, streaming, and any format except Anthropic Messages and OpenAI Responses, whose event streams have a fixed grammar), sends a `server_task_result_queue`, which reaches the stream as `data: {"mgs_queue": {"ahead": N, "ahead_api": A, "ahead_webui": W}}`. The streaming handlers wait for the first result before they send the headers, so that event also opens the response at once. When a queued task gets its slot it receives a last notice with every count at 0, and `mNotifyQueuePositions` updates the tasks still waiting. Clients that do not send `mgs_client` never receive these events, so their OpenAI-compatible streams stay unchanged. In the UI, `ChatService.mHandleStreamResponse` passes the events to `onQueue` and clears the state on the first regular chunk; `cChatStore` keeps it per conversation (`mGetQueueStatus`) and `ChatMessageAssistantProcessingInfo` shows `fQueueStatusText` before any other progress text: the API variant when any request ahead came directly from the API, otherwise the Web UI variant, both with the number of requests ahead. The requests that the UI sends by itself (KV cache pre-fill after a response, generated titles) carry the same mark and also take their turn.

**sudo password prompts.** On Linux, when sudo exists, `mStart` also creates `server_shell_mcp_askpass`: an abstract Unix socket (no file to protect or clean up) served by its own thread, with one thread per connection. A `tools/call` whose `_meta` carries `mgs/callId` (the UI generates one per call in `cMcpStore.mExecuteTool`) is registered with a random token, and its command gets `SUDO_ASKPASS` (the `mgs` executable itself: `MGS_EXECUTABLE`, published by the launcher, or `/proc/self/exe`), `MGS_LOCAL_SHELL_ASKPASS` (socket name and token) and, when the server has none, `DISPLAY=:mgs-askpass`, because sudo only falls back to the askpass helper without a terminal when `DISPLAY` exists. sudo runs `mgs <prompt>`; `fServerShellMcpAskpassMain`, the first thing `mgs_server` calls, recognises that case (the variable, a single argument and a sudo parent) and sends the token and the prompt through the socket. `mServe` checks with `SO_PEERCRED` that the helper belongs to the same user and with `fParentIsSudo` that its parent is sudo (name `sudo`, our real uid, root as effective or saved uid: an unprivileged process cannot read the executable of a setuid process, so this is the strongest check available), so a command cannot launch the helper itself with a fake prompt to capture the password. The prompt then waits (5 minutes at most) while `fRunCommand` moves its deadline by the time spent waiting (`mPaused`); `DialogLocalShellAskpass`, mounted once in the root layout so it opens on any page, polls `GET /api/mcp/shell/askpass?call=` every 500 ms for every running call (`cMcpStore.mActiveShellCalls`, filled by `mExecuteTool` with the tool and the command) and shows the first prompt in a centred dialog (ShadCN `Dialog` without the close button: the password field takes the focus as soon as a prompt shows (`fFocusPassword`, an attachment of the field, because `onOpenAutoFocus` runs before its ref is bound), Accept or Enter (`fHandlePasswordKeydown`) answers, Cancel or Escape cancels, a click outside does nothing) with the sudo prompt, the tool and the command, and a notice when sudo asks again after a password; `POST /api/mcp/shell/askpass` delivers the password or a cancellation, the helper writes it to the pipe that sudo reads and the copies are wiped. The password never reaches the tool result, the conversation or the logs; errors (cancelled, unanswered, command ended) reach the stderr of the command as `mgs: ...`. Other MCP clients send no call id, so their commands get no askpass variables and sudo fails for lack of a terminal as before.
**Security hardening.** Version 0.1.9 closes the findings of an external static security review (21 findings: 20 fixed; the one about the installers is left by design, see below).
- **HTTP (`server-http.cpp`):** public paths skip the API key only for GET/HEAD, and `GET /models?reload=...` needs the key when keys exist. With the `localhost` CORS mode that tools and MCP servers turn on, a request whose method is not GET, HEAD or OPTIONS gets 403 before routing when its `Origin` is neither loopback nor this same server (`Host` or `X-Forwarded-Host`; Apache keeps `Host` with `ProxyPreserveHost On`); requests without `Origin` (curl, SDKs) pass. `POST /tools` needs `Content-Type: application/json` (415), so a cross-site form cannot reach it without a preflight that CORS refuses. While a request is received, each read waits 30 s at most (`cHttpRequestReadTimeoutSec`); `--timeout` still governs writes, so long generations are not cut. Both thread pools queue at most 256 accepted connections (`cHttpMaxQueuedConnections`), and `mPost`/`mDel` refuse bodies nested deeper than 1024 arrays or objects (`fJsonNestingExceeds`, `cHttpMaxRequestJsonDepth`) before any handler parses them, because nlohmann copies and dumps documents recursively.
- **Router (`server-models.cpp`):** `fRedactArgs` and `fRedactPreset` replace the values of secret options (`sSecretOptionEnvs`: HF token, API key and key file, SSL key, MCP server configuration) with `<redacted>` in `status.args`, `status.preset` and the spawn log; children still receive the real values. `mProxyRequest` drops `Origin` when forwarding to a child, because the router has already checked it.
- **CORS proxy (`server-cors-proxy.h`):** navigation and embedding requests (`Sec-Fetch-Mode` navigate, `Sec-Fetch-Dest` document, frame, object or worker) get 403 (`fProxyIsNavigation`), and every proxied answer is made inert (`fProxyMakeInert`): sandbox CSP, `nosniff`, `Content-Disposition: attachment` and same-origin CORP, without the upstream cookies, CSP, CORS, HSTS, redirect, link or service-worker headers. `Content-Type`, `mcp-session-id` and `WWW-Authenticate` stay for the MCP client of the UI.
- **Remote media (`download.{h,cpp}`, `server-common.cpp`):** `fCommonRemoteGetContent` applies a connect timeout, a total deadline (`set_max_timeout` plus a check in the body receiver) and follows redirects by hand. For `image_url`, `input_audio` and `input_video` (`vPublicHostsOnly`), the host is resolved once and every address must be public: no loopback, RFC 1918, CGNAT, link-local (169.254.169.254 included), documentation, multicast or reserved ranges, and in IPv6 only 2000::/3, with mapped, NAT64 and 6to4 addresses judged by their IPv4. The connection is pinned to the checked address (`set_hostname_addr_map`) and every redirect is checked again; `--media-allow-private-urls` lifts the address check. Media downloads take 10 s per connection, read or write, 30 s in total, 5 redirects, 10 MiB and 8 at once (`media_download_slot`); `ffprobe` and `ffmpeg` only read pipes when the input is a request buffer.
- **Decoding (`mtmd-helper.cpp`, `server-common.cpp`):** images up to 32768 px per side and 100 megapixels, checked with `stbi_info_from_memory` before decoding; audio up to one hour, checked before the samples are allocated; video frames up to 8192 px per side and 2 GiB of RGB frames per video; at most 2 GiB of decoded images and audio per request (`fProcessMtmdPrompt`).
- **Parsers:** the GBNF converter (`json-schema-to-grammar.cpp`) rejects empty patterns and quantifiers with nothing to repeat; it limits schema nesting, nested visits and `$ref` chains to 256 (`cMaxSchemaDepth`, measured iteratively by `fJsonExceedsDepth`), pattern groups to 128, excluded property names to 1024 bytes and `type` lists to 7 entries, and sanitises rule names with a loop instead of the recursive `std::regex`. The Jinja runtime (`jinja/value.h`) limits `range()` to one million elements, built strings to 256 MiB and 1 Mi parts, `indent()`/`tojson()` indentation to 256, statement execution nesting to 1024 and parse nesting to 256. `gguf.cpp` skips zero dimensions in the overflow check instead of dividing by them; empty tensors stay valid.
- **RPC (`ggml-rpc/`):** the variable `recv_msg` takes a per-command ceiling (SET_TENSOR: header plus the largest live buffer of the connection; GRAPH_COMPUTE: `INT32_MAX`, the most a client can send) and catches `std::length_error`. Tensor bounds sent by the peer are checked with overflow-safe helpers (`rpc_checked_nbytes`, `rpc_tensor_region_ok`) and answer errors instead of `GGML_ASSERT`; any exception closes only that connection, and freeing a buffer drops the stored graphs that use it. RDMA receives never copy more than requested and keep the rest in `rx_pending`; the queue pair grants no remote access.
- **Web UI:** a Markdown render that fails shows escaped text. Links whose scheme is not http, https, mailto or tel (or relative) lose their `href`, image attachments must be `data:image/...;base64`, and the broken-image notice is built with DOM nodes (`fCreateImageErrorFallback`). Conversation import checks the file (512 MB), the ZIP entries (10 000), each JSONL (256 MB) and the extracted total (1 GB) before decompressing, validates every record, requires each message's `convId` to match its conversation and writes with `bulkAdd`, skipping a conversation whose message ids already exist. One identity per tool name (`mResolveEnabledEntry`) serves the model, the approval and the execution, which goes to that exact server (`mExecuteTool(pToolCall, pServerId, pSignal)`); a name offered by two enabled MCP servers is withheld with a warning, and "always allow this server" applies by server id.
- **Web UI dependencies (`frontend/package.json`, 0.1.10):** the packages flagged by `npm audit` that reach the browser bundle move to fixed releases: DOMPurify 3.4.17, mermaid 11.17.2 and `@modelcontextprotocol/sdk` 1.32.1. SvelteKit 2.70.3 and `@vite-pwa/assets-generator` 1.0.4 (sharp 0.35.5, Node.js 20.9 or later) are updated too, and `npm audit fix` refreshes the build-time transitive packages within their ranges; direct versions stay pinned exactly. What `npm audit` still lists only touches build tooling (`postcss-selector-parser` through `@tailwindcss/typography`, the esbuild development server on Windows) or KaTeX, whose fix (0.18.2) is outside the `^0.16` range that `rehype-katex` and mermaid accept; that KaTeX advisory needs an existing prototype pollution to be exploited.
- **Not addressed:** pinning the `curl | bash` installers to an immutable revision or signature (the project rules require installing from `main`), an absolute deadline for the whole header block (cpp-httplib applies the timeout to each read), RPC read deadlines and concurrent clients, an iterative `create_node` in the RPC server, a global CPU and memory budget for Jinja templates and the recursion of `mgs-grammar.cpp` over the request `grammar`.

<a id="flows"></a>
## Main call paths

1. **Installation:** Debian file/stdin entry → validation → log and lock → local checkout or GitHub `main` archive → source validation/synchronisation → child Bash with closed stdin → `install-common.sh:fMain` → dependencies → stable `_/temp/source` staging including `build/` → CMake with `-S _/temp/source/build` → `bin/mgs` installation. Alpine calls the helper directly from a local checkout.
2. **Deployment:** `configure-web.sh` → service account → API key/certificate → standalone template and services → `start-web.sh` → occupied listeners → 11080+/11443+ selection → Apache bind → ownership of both listeners → `ports.json`. A real bind conflict returns to selection; other failures stop the service.
3. **Chat:** component → `ChatService.mSendMessage` → normalised messages and custom JSON → `fApplyResponseLanguage` using the current `respondInInterfaceLanguage` flag and UI locale → `fApiUrl` → HTTP registration → authentication/readiness → `server_routes` → task queue/slot → mgs/GGML evaluation → JSON or SSE → browser storage and rendering. `mGenerateTitle` and every agentic turn use this same path; `mPreEncode` applies the same system instruction before preparing the KV cache.
4. **Router:** external handler → canonical internal path → model selection → child `/api` request → response or retained stream. Lookup, resume and cancellation follow the same contract.
5. **MTP:** common initialisation → `fCommonMaybeEnableEmbeddedMtp` → `fDetectEmbeddedMtp` → all GGUF shard headers/tensors → architecture/trunk/head checks → `draft-mtp` selection unless explicitly overridden → model load: `mgs_model_base::mLoadTensors` places the MTP layers and the output layer on a GPU → `mgs_model_loader::mCreateTensor` skips the overrides to host memory for them.
6. **MoE:** mapped weights → host registration → graph split → `fInitializeExpertPrefetch` → separate-backend transfer → ready/free events → computation. Memory pressure reduces the slot count or restores regular copies.
7. **Language:** URL `lang` (priority) / storage → one of 15 catalogues (default `en-US`) → `fTranslate` → Svelte-escaped text; root layout → HTML `lang`/`dir` → logical navigation and bidirectional chat text; selector → persistence → reload.
8. **Updated inference:** microbatch original indices → independent output/no-output arena → CPU/CUDA/HIP/Vulkan/SYCL kernels → restore NextN row order → accept until EOG → completed-slot speculative metrics.
9. **Export/tools:** selected IDs → persisted conversation/message read → JSONL/ZIP; tools HTTP 403 → retained disabled state → explicit panel retry.
10. **Local build:** `build/build-local.sh` from a file or stdin → options → local/remote selection → private workspace and log in `/tmp/moe-gguf-server-build.XXXXXXXX/` → toolchain, CUDA and Node.js checks → local copy or HTTPS archive download/validation/extraction into `source/`, including `build/` → CMake with `-S source/build` in `cmake/` → `mgs` → static launcher → loader, `ldd` closure and NSS modules in `bundle/lib/mgs/` → server binary and `DT_RPATH` `$ORIGIN` → marker in `bundle/lib/mgs/` → `build/licenses/` and the root `LICENSE` in `bundle/licenses/` → prefix lock → finished artefacts copied next to their places → atomic replacement of `lib/mgs/`, `bin/mgs` and `share/doc/mgs/licenses/` → `<loader> --list` verification → `--version` through the launcher → `fCleanup` removes the private workspace. At run time: launcher → `/proc/self/exe` → `MGS_EXECUTABLE` → prefix from `bin/` → `execv(lib/mgs/<loader>, lib/mgs/mgs, arguments)` → router children re-enter through the launcher.


11. **Native web startup:** `common_params` / CLI → `server_http_context::mInit` → `fCreateHttpsServer` (PEM, or `fPersistentServerIdentity`: load or create `~/.mgs/certificates/`) → `start` → `fBindServerPort` for HTTPS → distinct HTTP port → two listener threads → actual URLs in the log → stop and join both threads.
12. **MoE expert cache:** first request after loading → `mgs_context::mDecode` → `mgs_expert_cache::mFCreate` → eligible layers and groups → budget of every GPU → pools and identifier buffers on every GPU → bandwidth probe per GPU → `mSchedReserve` with the hybrid graph and the upload callback. Micro-batches below 32 tokens: router on the device → `mPartition` on the CPU (selection copy, LRU hits, balanced uploads, identifiers) → device branch over the pool → CPU branch over host weights at the same time → `mMeasureCpu` → merge on the device → router weights. Large micro-batches: prefetch → `mUploadWeights` (device copies for cached experts, host uploads for the rest) → computation. `POST /api/expert-cache` → task queue → `mgs_set_expert_cache_size` → the next decode rebuilds the cache and the graphs.
13. **Context checkpoints:** prompt batch filling → message start in a micro-batch at least 3/4 full, or last user message → batch cut → checkpoint at the batch start (message start, prompt end or `--checkpoint-min-step` since the last one) → `mCreateCheckpoint` (evicts the closest neighbours) → a later request that diverges at position p restores the newest checkpoint before p → only the suffix is processed.
14. **Automatic configuration (fit, batches, context, threads):** argument parsing → `fPostprocessCpuParams` → `fCommonDefaultThreads` when `-t` is absent → `mLoadModel` adds the measured draft/MTP context to the device margins → `common_init_result` → `fCommonFitParams` (`pAutoBatch` = no `-b`/`-ub`) → `fCommonParamsFitImpl`: measurement with the initial parameters → step 2 reduces an unset context to `--fit-ctx` when the model does not fit → dense-only layers back to front → every expert in RAM (expert cache) or whole expert layers → `fRaiseBatch` → `fRaiseContext` (both before the whole expert layers) → `n_batch` copied back into the parameters → thread log → model and target context load → draft context with `n_ctx` and `n_batch` of the target → the expert cache takes the rest of the device memory on the first request.
15. **Monitor:** `mLoadModel` → `mgs_model_get_weight_breakdown` (once) → `mRefreshMonitorSnapshot` (after loading, at most 1/s while slots work, always when idle) → `mBuildMonitorSnapshot` (`mgs_get_memory_breakdown` and `mgs_get_expert_memory_breakdown` of the target and draft contexts, prompt cache and checkpoints, `ggml_backend_dev_get_props` per GPU) → mutex. `GET /api/monitor` → `vGetMonitor` (router: `vGetRouterMonitor` → `fCollectMonitorSnapshots` → child `/api/monitor/memory`) → `fMonitorReport` (`fCpuJson`, `fRamJson`, `fGpusJson` → NVML/sysfs, segments per GPU by PCI id and in RAM, "other", free) → `cMonitorStore` → `MonitorScreen`. Status bar: `StatusBar` → `cMonitorStore.mSubscribeUsage` → `GET /api/monitor/usage` → `fMonitorUsageJson` every 2 s.
16. **Vulkan build:** `--vulkan` → `vBuildBackend=vulkan` → (installer: `libvulkan-dev spirv-headers glslc mesa-vulkan-drivers`) → `glslc` check → CMake with `-DGGML_VULKAN=ON -DGGML_CUDA=OFF` (failure names the packages) → shaders and `mgs` → local build: `libvulkan.so.1` in `lib/mgs/` → run time: loader → ICD from `/usr/share/vulkan/icd.d/` → `Vulkan0` device → `--fit`, expert cache and prefetch as with CUDA.
17. **Local shell MCP server:** `--local-shell-mcp-server` → `vShellMcpServer` (localhost CORS default, removed from router children) → `mgs_server` → `server_shell_mcp::mStart` (shell detection) → registration of `POST/GET/DELETE /mcp/shell` and warning → `shell_mcp_server` in `/api/props` → root layout → `cMcpStore.mSyncShellServer` → `mgs-shell` entry → health check and `MCPService.connect` (StreamableHTTP, same-origin API key) → `initialize`/`tools/list` → model tool call → permission prompt → `tools/call` → `mHandlePost` → `fOriginAllowed` → `mToolsCallResult` → `server_shell_mcp_call_log::mOpen` and `command` line → `fRunCommand` (`posix_spawn`, `poll`, group kill; every read → `pOutput` → `mOutput` → `stdout`/`stderr` line) → `mFlushOutput` → `result` or `error` line → JSON object (`vExitCode`, `stdout`, `stderr`...) as text and `structuredContent` → tool message → `ChatMessageToolCallBlock` → `fIsLocalShellTool` → `ChatMessageToolCallBlockLocalShell` (`fParseLocalShellCommand`, `fParseLocalShellResult`) → stdin, stdout and stderr boxes, open by default with `expandLocalShellCommands`.
18. **sudo password prompt:** `cMcpStore.mExecuteTool` (`mgs/callId` in `_meta`, `dShellCalls`) → `mToolsCallResult` → `server_shell_mcp_askpass::mRegister` and `mEnvironment` (`SUDO_ASKPASS`, `MGS_LOCAL_SHELL_ASKPASS`, `DISPLAY`) → `fRunCommand` → sudo without a terminal → `mgs <prompt>` → `mgs_server` → `fServerShellMcpAskpassMain` → abstract socket → `mServe` (`SO_PEERCRED`, `fParentIsSudo`, token) → pending prompt and paused deadline (`mPaused`) → `DialogLocalShellAskpass` (`mActiveShellCalls`, `LocalShellAskpassService.mPending` every 500 ms) → centred password dialog → `mAnswer`/`mCancel` → `mHandleAskpassPost` → `server_shell_mcp_askpass::mAnswer` → reply to the helper → password written to the pipe that sudo reads (or `mgs: ...` on stderr) → `mUnregister` when the command ends.
19. **Request queue:** `ChatService.mSendMessage` (`mgs_client: "webui"`, `stream`) or an API client → `server_routes` → `fEvalMgsCmplSchema` (`vFromWebui`) → `vQueueNotice` → task queue → `mProcessSingleTask` → `mGetAvailableSlot` → no free slot → `mDeferTask` (`mCountRunning`, `server_queue::mDeferredTasks`) → `server_queue::mDefer` → `server_task_result_queue` → first stream result → `data: {"mgs_queue": ...}` → `mHandleStreamResponse` → `onQueue` → `ChatStore::mSetQueueStatus` → `fQueueStatusText` → `ChatMessageAssistantProcessingInfo`. Slot released → `vCallbackOnRelease` → `mPopDeferredTask` (first deferred task to the front) → `mProcessSingleTask` → `mLaunchSlotWithTask` → notice with 0 → `mNotifyQueuePositions` → first token → `onQueue(null)`.
20. **DeepSeek-V4.1 loading and Engram:** `mgs_model_loader` → `fMgsDeepseek41AdaptMetadata` (DwarfStar keys → standard keys) → `mgs_model_deepseek41` hparams and tensors (Engram tables with `cTensorExternal`, prefetching stops before them) → layer roles → `mgs_kv_cache_dsv41` → per ubatch `llm_graph_input_dsv41_engram::mSetInput` (n-gram hash over the token history → `mEngramReadRows` via `pread` → F32 input) → `mBuildEngram` before layers 1 and 14 → attention over the shared compressed KV with index keys and the candidate pool → MoE with `ggml_swiglu_clamp`.
21. **Remote media and decoding:** request part (`image_url`, `input_audio`, `input_video`) → `fHandleMedia` → data URI, `--media-path` file or `media_download_slot` (8 at once) → `fCommonRemoteGetContent` (`vPublicHostsOnly` unless `--media-allow-private-urls`) → `fRemoteResolveHost` → `fRemoteIpv4IsPublic`/`fRemoteIpv6IsPublic` for every address → `set_hostname_addr_map` → GET within 30 s and 10 MiB → each redirect checked again (5 at most) → `fProcessMtmdPrompt` (2 GiB decoded per request) → `stbi_info_from_memory` before decoding, audio duration before allocating, video frame size and budget → mtmd chunks. A refused address is a 400 that names the option.

<a id="impact"></a>
## Impact analysis

- **Reply language:** apply the instruction after custom JSON so replacing `messages` cannot bypass the enabled setting. Read the current flag for every new request, rather than storing a locale instruction in the conversation. Both completion and prefill must use the same helper to preserve the KV prefix. Stream reconnection reuses the already-running generation and cannot change its language instruction. Keep all 15 `responseLanguage.*` catalogue entries aligned; regional guidance is explicit for Argentine/Spain Spanish, UK/US English and Brazilian/European Portuguese. Following a prompt remains model-dependent; external API callers are unaffected.

- **Remote installation:** URL, GitHub archive layout and entry/helper protocol changes affect `curl | bash`. Keep help options aligned and the repository origin fixed. The marker and lock protect the managed tree; do not store local edits there that must survive synchronisation.
- **Native TLS:** direct clients must use HTTPS and trust the certificate or supply a known PEM pair. `--http` is explicit for the Apache backend and router children; children do not inherit public TLS variables. An explicit main port is never silently changed. Builds without OpenSSL require explicit HTTP.
- **Web ports:** affect redirects, public addresses, firewalls and the browser storage origin. `ports.json` is published only after both listeners belong to the launched Apache process. An exclusive lock prevents concurrent launchers. HTTPS is reserved before searching HTTP so overlapping sequences never share a port. Port exhaustion produces an explicit error.
- **Prefixes and middleware:** affect every HTTP client, authentication, router, streams, frontend and Swagger. Change `server-http`, `server-models`, `api-url` and their documentation together.
- **Request hardening:** the cross-site check relies on `Host` or `X-Forwarded-Host` naming the public address: a reverse proxy that rewrites `Host` without sending `X-Forwarded-Host` makes the UI's writes fail with 403 while tools or MCP servers are on (`deploy/apache2.conf.in` keeps `ProxyPreserveHost On`). Raising `cHttpRequestReadTimeoutSec` or removing the queue bound brings back slow-client exhaustion; lowering `cHttpMaxRequestJsonDepth` below about twice `cMaxSchemaDepth` would refuse JSON schemas that the converter accepts.
- **Secret options:** an option that holds a credential must be listed in `sSecretOptionEnvs`, or its value appears in the public router listing and in the spawn log.
- **Remote media policy:** `common_remote_params` defaults keep the previous behaviour for Hugging Face and Docker manifests; only the media path sets `vPublicHostsOnly`. Following redirects automatically, or connecting by name after the check, reopens DNS rebinding and redirect-based SSRF. The decode limits are generic constants in `mtmd-helper.cpp` and `server-common.cpp`; lowering them refuses legitimate large media.
- **UI tool identity:** approval, permissions and execution must use the entry returned by `mResolveEnabledEntry` and its server id; resolving by bare name again (first match in the UI, last writer in `MCPStore`) lets one server's approval run another server's tool, including the local shell.
- **Completion schema:** affects inference validation, defaults and OpenAPI documentation. Extensions must retain protocol field names.
- **Catalogues/selector:** affect all views and labels initialised during module import. Keep keys, language names and data parameters aligned across all 15 catalogues; English plural suffix parameters may be omitted where a translation uses count labels. Preserve HTML tags and title-template tokens such as `{{USER}}` and `{{ASSISTANT}}`. Register new locales in both `aLanguages` and `dCatalogs`. Hebrew also affects navigation direction; code must remain LTR. Do not translate protocol identifiers or user data.
- **Registration/prefetch:** affect RAM/VRAM use, GPU events and mapping/buffer lifetimes. Never release a registered page or slot while it remains in use.
- **MTP:** affects decoder selection before weight allocation. Preserve explicit-option precedence and inspect every GGUF shard. MTP weights ignore the overrides to host memory and take device memory before `--fit` places the trunk and before the expert cache is sized, so changing the MTP layer assignment in `mLoadTensors` changes the VRAM use of every model with MTP.
- **CMake/installers:** affect every build platform. Do not reuse caches from the old layout or hide local UI build failures.
- **Version:** `MGS_VERSION` names the shared library files (`libmgs-engine.so.0.1.0`; the soname stays `.so.0`) and reaches `/api/props`, `system_fingerprint`, the shell MCP `serverInfo.version`, the download `User-Agent` and the UI `build.json`. Keep the `MAJOR.MINOR.PATCH` form: the UI build rejects characters outside `[A-Za-z0-9._-]`.
- **Vulkan:** the bundle shares the C/C++ runtime with the system driver it loads, so a bundle built on an older or newer Debian release may fail to load the ICD. Pinned expert uploads only exist with CUDA; any change to `--load-mode` defaults or to the host buffer types changes Vulkan transfer speed. Service accounts without the `render` group cannot open the GPU. Device buffers must stay in device-local memory; never enable `GGML_VK_ALLOW_SYSMEM_FALLBACK` or `GGML_VK_PREFER_HOST_MEMORY` for MoE serving. A new cache-like device allocation should use the cache buffer type, and any new async path in `ggml-vulkan` must accept every device buffer type of the GPU.
- **Local bundle:** newly linked libraries are picked up automatically through `ldd`. Changes to `OUTPUT_NAME`, the router's re-execution path (`fGetServerExecPath`, `MGS_EXECUTABLE`), the loader's explicit-execution mode or the library search order affect `build/build-local.sh` and the launcher. Running `lib/mgs/mgs` directly bypasses the bundled loader and is unsupported. Driver libraries must remain excluded.
- **MoE expert cache:** affects device memory (the pool takes what remains after the context; `--moe-cache-reserve` covers other processes and lazily allocated buffers), split synchronisation in the scheduler, the CPU `mul_mat_id`/`add_id` kernels (negative identifiers) and the graph of every MoE architecture (`mBuildMoeFfn`). Device kernels for expert products must accept slot identifiers that are distinct within a token. Changing `--fit` placement changes the RAM needed: keeping every expert in RAM falls back to whole expert layers when `MemAvailable` is short. With several GPUs every GPU holds its own pool for its layers; the layer split (`--fit`, `--tensor-split`) decides which experts each GPU caches.
- **Batch sizes and threads:** `cBatchShare` in `fRaiseBatch` trades device memory for prompt speed; the micro-batch is chosen before the context, so a larger micro-batch also shortens the default context (Qwen3.6-35B-A3B Q8_0 on 16 GB: 122880 tokens with 512, 89856 with 4096). The server cuts prompts and places context checkpoints by `mgs_n_batch`/`mgs_n_ubatch` of the target, so their positions follow the chosen sizes. Any change that makes the draft or MTP context take a batch larger than its own `n_batch` overflows its batch buffer. `fCommonDefaultThreads` changes the CPU share of every MoE layer with experts in RAM; measure generation with `--spec-type none` on a virtual machine and on bare metal before changing the cap.
- **Context size in `--fit`:** `cContextShare` in `fRaiseContext` trades context for experts: every byte of KV cache it allows comes out of the expert cache pool or out of the whole expert layers placed on the devices, so a larger share lowers the generation speed and a smaller one shortens the default context. The draft context follows the target context, so changing how `mLoadModel` sizes it changes the device memory left to the expert cache of every model with MTP or a draft model.
- **Context checkpoints:** spacing and placement affect host memory (up to `--ctx-checkpoints` states per slot) and prefill batching; every additional cut costs one more pass over the offloaded experts.
- **Removed compatibility:** clients, router presets, service overrides and build scripts must use current names; removed aliases now fail as unknown options, are ignored as environment variables or return 404 as routes. Reintroducing a name requires adding it in `common/arg.cpp`, `server.cpp` or CMake and documenting it in the CODE and MANUAL variants. Update the README only when its overview or installation command changes.
- **Monitor:** the snapshot is built on the main loop, the only thread that may touch the contexts; a buffer allocated outside `mgs_get_memory_breakdown` (a new cache or pool) shows up as "other" until a breakdown call reports it. Never route the monitor through the task queue: it would reset the idle timer and wake sleeping models. The router aggregation relies on the child contract (`/api` prefix, no API key). New fixed or bottom-anchored UI elements must add `--status-bar-height`.
- **Shell MCP server:** anyone who can use the API (or open the UI) can run commands as the service user, so it is only for trusted environments and should be combined with an API key. Changing the route, the `shell_mcp_server` property or the `mgs-shell` identifier affects the UI synchronisation and stored settings; changing the Origin or Content-Type checks reopens cross-site command execution; changing `fRunCommand` affects process-group cleanup, timeouts and output limits; changing the JSON fields of `mToolsCallResult` affects what the model reads and `fParseLocalShellResult`, which then shows the whole result as stderr text, and the `result` lines of the call logs; changing `cCallLogFolder`, the file name or the 0700/0600 modes of `server_shell_mcp_call_log` moves the call logs or exposes command output to other users.
- **Web UI settings:** the document is shared by every browser and the last save wins; a save always sends every section, so a store that keeps settings outside `cUiSettingsStore` would lose them on other browsers. Saving before the document loads would overwrite the file with a partial state, which `mSet` prevents. Renaming a section or a config key leaves the old value unread (no migration). The file can hold MCP headers, hence mode 0600; anyone with the API key can read it through the API.
- **sudo password prompts:** the password crosses the browser, the API (HTTPS and API key) and the abstract socket; changing `fParentIsSudo`, the `SO_PEERCRED` check or the token lookup lets a command read the password with a fake prompt; changing `fServerShellMcpAskpassMain` or its position at the start of `mgs_server` breaks the helper or makes ordinary runs of `mgs` inside a command act as it; changing `cAskpassDisplay` or the condition that sets `DISPLAY` makes sudo stop using the helper; starting commands without a session of their own (`POSIX_SPAWN_SETSID`) makes sudo prompt on the terminal that started `mgs` instead; unmounting `DialogLocalShellAskpass` from the root layout leaves the prompts unanswered until they expire; changing `mgs/callId` affects `cMcpStore.mExecuteTool` and the polling of the UI; logging the request bodies of `/mcp/shell/askpass` would write passwords to the logs.
- **Request queue:** the default of one slot gives every request the whole context; raising the default of `-np` (or bringing back an automatic mode) splits the context among the slots and shortens long answers. The `mgs_queue` events only reach requests marked with `mgs_client: "webui"`: sending them to other clients, or in the Anthropic Messages or OpenAI Responses streams, would break their parsers. Every streaming handler must accept a `server_task_result_queue` as its first or a later result, and every new deferral path must go through `mDeferTask` so the waiting requests keep their positions. A requeued task goes to the end of the deferred queue, as upstream does.
- **Removed architectures:** Gemma 4 and every DeepSeek architecture older than V4.1 are gone; reintroducing one means restoring its arch entries, tables, graph, vocab and chat pieces and adding it back to `RulesForThisProjectOnly.md`. GGUFs of other models converted as `deepseek2` (Kimi-K2.x, GLM-4.7-Flash and others) no longer load.
- **Shared DSV4 pieces:** `ggml_dsv4_hc_pre`, `ggml_dsv4_hc_pre_gated`, `ggml_dsv4_hc_comb`, `ggml_dsv4_hc_post`, `ggml_lightning_indexer`, `vDsv4HcMult`, `aDsv4CompressRatios` and the fused hc cparams serve Kimi-K3, GLM-5.3-Flash, Qwen3.8 and DeepSeek-V4.1; a change there affects the four. They have no Vulkan or Metal kernels, so they run on the CPU there.
- **Hybrid index memory:** shared by qwen4exp and glm5-next; KV cells store token ids and `seq_pos` holds (position, cell) pairs, which the n-gram embeddings and the state restore rely on.
- **External tensors:** `cTensorExternal` tensors are never allocated and prefetching stops at the first one; code that walks tensor data (quantization, saving, memory reports) must skip them. The Engram rows need a POSIX `pread` on the model file during the whole run.

Project-specific rules prohibit writing or running tests. Review is static and does not establish runtime, GPU, remote installation or mobile overflow correctness. `tests/` is reserved without executable tests.

Never keep settings in `localStorage`.
- **Queue notice for another client:** a client that wants the `mgs_queue` events sends `"mgs_client": "webui"` with `"stream": true`; another origin value needs a field in `task_params`, its handler in the `mgs_client` field of `fMakeMgsCmplSchema`, its own counter in `mCountRunning`, `mDeferTask`, `mNotifyQueuePositions` and `server_task_result_queue`, and a translated text in `fQueueStatusText` and the 15 catalogues.
